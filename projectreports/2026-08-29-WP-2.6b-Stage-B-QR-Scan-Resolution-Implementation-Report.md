## 3. Architecture

### 3.1 The sequence, and why the order is load-bearing

```
POST /api/qr/{code}/scan
  → throttle:qr-scan          (two ceilings; a rejected burst never reaches the app)
  → QrScanResolver::resolve   (server-side; the caller supplies no target)
  → RecordQrScan::handle      (ALWAYS — before any authorization question)
  → disclosure decision       (coarse; deliberately not the classification)
```

**Resolve, log, then decide.** The log is written before any authorization
question is asked and regardless of its answer. That is what keeps it honest
about attempts that were refused, which is exactly the class of attempt worth
finding later (DD-47).

### 3.2 Classification (FR-QR-006)

| Result | Condition |
|---|---|
| `success` | Active code resolving to a live target |
| `invalid` | Unknown code, or a value that could not be a code |
| `expired` | Code `inactive`/`revoked`, **or** target retired / disposed / archived |
| `mismatch` | **Never produced** — reserved (OD-6) |

The target is loaded `withTrashed()` on purpose: an archived machine classifies
as `expired` — a truthful *"this label no longer points at live equipment"* —
rather than `invalid`, which would say the sticker was never real. Asset liveness
reuses `AssetStatus::isLive()` rather than restating "not retired and not
disposed", so the widened Phase 2.5 domain cannot drift from a second copy.

`mismatch` is deliberately unreachable, per your approved OD-6. FR-QR-006 defines
it against a *claimed* target, and there is no claim: `qr_codes` binds its target
directly and the URL carries only the code. Manufacturing a caller-supplied
"claimed target" parameter purely to make the enum case reachable would
reintroduce exactly the client-supplied state DD-48 exists to keep out. **A
dedicated test guards that nobody later adds one.**

### 3.3 The three answers

| `next` | When | Payload |
|---|---|---|
| `sign-in` | No session — **for every classification** | `{"next":"sign-in"}` and nothing else |
| `refused` | Authenticated but not entitled, or the label is unusable | `next`, `reason`, `message`; HTTP 403 |
| `panel` | Authenticated, entitled, success, PC target | `next`, `scan_id`, `code`; HTTP 200 |

The endpoint returns a **routing decision and nothing else**. It never carries a
name, code, location, status, specification, ticket or maintenance detail — not
even to an authorized caller, who gets that from the panel endpoint after a
second authorization check. A scan resolves *where to go next*; the panel decides
*what may be seen*.

### 3.4 Rationed reasons — the second oracle, closed

A caller who clears the permission floor is staff doing maintenance, and telling
them *"this label was revoked"* is the difference between a technician who
fetches a new sticker and one who assumes the system is broken.

A caller who does **not** clear it gets one flat refusal for every cause. Without
that, the endpoint would answer *"does this code exist?"* to anyone with any
account — the enumeration oracle of FR-QR-013 in a different costume, costing one
login. A test asserts a teacher's response to a real code and to an invented one
are identical JSON.

### 3.5 Rate limiting

`qr-scan` is the only limiter in this application that returns **two** `Limit`
objects, because FR-QR-013 is explicit: *"rate-limited per client **and** per
account"*. Both apply to every request and the stricter wins.

Keyed per IP **and** per user — not the usual "user, falling back to IP" — because
this route is reachable with no session at all. The IP ceiling is what resists an
anonymous enumeration sweep, and **signing in must not lift it**. A test asserts
exactly that.

Defaults: 20/min per client, 30/min per account, both in `config/security.php`.
Per minute rather than per hour because enumeration is a burst and legitimate
scanning is not.

### 3.6 Deliberate design choices worth recording

- **`last_scanned_at` is stamped even for a revoked label.** A revoked sticker
  still being scanned is a fact an administrator needs: it means the old label is
  still physically on the machine. Stamping only successes would make exactly
  that situation invisible (FR-QR-004).
- **Throttled attempts are not logged.** The throttle runs ahead of the
  controller. FR-QR-005's "record every scan attempt" covers attempts the
  application processes; logging a rejected flood would turn an enumeration
  attempt into a way to fill the audit table.
- **No `activity_logs` row for a scan.** A scan is an attempt, not an
  actor-initiated business event, and it happens with no actor at all more often
  than not. The split mirrors `login_history` versus `activity_logs`, drawn since
  Phase 2.2. Proof of work — which *is* a business event — writes to
  `activity_logs` in Stage E.
- **Asset labels resolve but have no workflow.** Assets carry labels
  (FR-QR-001), but WP-2.6b's panel is the technician's PC job. An asset label
  logs `success` and then answers `no_workflow` rather than pretending a
  destination exists.
- **Half a coordinate fix is discarded.** A lone latitude is not a location, and
  storing half a fix would make the column lie about what was known.

### 3.7 Interim authorization seam — replaced in Stage C

`QrScanController::mayProceed()` currently checks only the **permission floor**:
`maintenance.view` OR `tickets.update`. The approved predicate (FR-QR-012, DD-49)
is that floor **and** "the unit is reachable through their assigned work"; the
second half needs `ScannedPcAccess` and `PcUnitPolicy::viewScanned`, which land
with the panel in Stage C.

The interim gate is **wider than the final rule and narrower than no rule** —
never the other way round — so no intermediate state of this branch is more
permissive than the finished one. A Teacher, holding neither ability, is already
refused. It is deliberately **not** an `assets.*` check: a Technician holds no
asset permission at all (DD-38), and the scan panel exists precisely so they can
reach the machine they are working on without one (FR-AST-013).

The seam is documented in the code as such.

## 5. One flaky test — investigated, not hand-waved

`AssetDirectoryTest` → *"it finds an asset by every field the enterprise search
covers"* failed **once in four** full-suite runs. It passed **8/8** when run in
isolation, and the other three full runs were 575/575.

**Root cause identified.** That Phase 2.5 test searches 16 literal terms and
asserts each returns *exactly one* row. Several terms are short — `'SCI'` (a
building code), `'Rivera'` (a technician surname), `'Lab 3'`, `'Contoso'`. Its
decoy row is created as
`Asset::factory()->create(['asset_tag' => 'ZZZ-9999', 'name' => 'Unrelated', 'serial_number' => 'SN-ZZZ'])`
— only three fields pinned, so the decoy's supplier, hardware model,
manufacturer, room, floor, building and custodian are all randomly generated. The
search is `ILIKE '%term%'` across every one of those joined tables
(`AssetDirectoryQuery::applyAssetSearch`), so a random building code of `SCI`, or
a faker `lastName()` of `Rivera`, makes the count 2.

Full-suite runs advance the faker sequence differently from isolated runs, which
is why it surfaces there and not under `--filter`.

**Not caused by Stage B.** Nothing in this stage touches the asset search path,
`AssetDirectoryQuery`, `AssetFactory` or the location factories. The failure
arises from random data alone.

**Not silently fixed.** It is a Phase 2.5 test and altering it is outside this
authorization. It is recorded in Auto Memory
(`sccit-flaky-asset-directory-search-test`) with the suggested remedy: pin the
decoy's related records to non-colliding values, or relax the assertion to
"contains PRN-0001 and excludes ZZZ-9999" instead of a strict count. **Raised
here as a cleanup item for your decision.**
