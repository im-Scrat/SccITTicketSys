## 2. Exact gate behavior

**`scripts/gates.sh`** runs nine gates, each through `run_gate`, strictly one at a time —
plain sequential shell, no `&`, no job control. Every gate is always attempted, so one
invocation reports everything that is broken. **Exit status is the count of failed gates.**

**`scripts/deploy-prod.sh`**, step 2 of 8:

```sh
if sh "$REPO_ROOT/scripts/gates.sh" --stack dev; then
    GATES_RESULT='passed'
else
    die "quality gates failed — deployment stopped before anything was changed."
fi
```

Binary. Any non-zero exit — one failed gate or nine — is fatal, and the halt precedes
the pre-deploy backup (step 3), the image build (step 4) and every other mutation.
`GATES_RESULT` can hold exactly two values, `passed` or `skipped`, and that single
string is the entirety of `verification.gates` in the release manifest.

### Why the known technical debt returns non-zero

It cannot do anything else. A failing Vitest run increments `FAILED`; `FAILED` becomes
the script's exit code; any non-zero exit is fatal to the deployment. There is no state
between "gate passed" and "gate bypassed entirely."

## 6. Pest contention verification

**Pest passes when run alone: 943 passed, 3,704 assertions, exit 0.** The 2026-09-11
Pest failure was not a regression and is not reproducible here.

### The recorded diagnosis is mechanically wrong

The 2026-09-11 report states the cause as *"`scripts/gates.sh` runs Pest and Vitest
within one sequence."* `gates.sh` **cannot** run them concurrently:

- `run_gate` is a blocking shell function call; gates execute strictly in order.
- There is no backgrounding, no `&`, and no job control anywhere in the script.
- There is no `paratest` and no `--parallel` in `composer.json`, `phpunit.xml` or
  `tests/Pest.php` — Pest is single-process.
- Playwright is independently pinned to `workers: 1` for the same shared-database reason.

### The actual contention source is outside the gate

- `sccit_node` runs a **persistent Vite dev server** (`npm run dev -- --host 0.0.0.0`)
  for the entire life of the dev stack. The gate neither starts nor stops it.
- `vite.config.ts` sets `server.watch.usePolling: true, interval: 300`, because Docker
  Desktop on Windows does not forward native filesystem events into the container.
  That is a continuous poll of the frontend tree.
- Measured idle baseline: **15–20% CPU doing nothing at all.** The 555% observed on
  2026-09-11 is that same process under churn.
- Vitest and the production build then run **inside that same container**, alongside
  the polling watcher.
- The test database (`school_it_service_management_test`) is a dedicated database
  inside the shared `sccit_postgres` container, so contention with dev-stack workloads
  is CPU and I/O level rather than row level.

**The orchestration problem is real, but it is environmental rather than a sequencing
defect in `gates.sh`.** The gate serialises its own work correctly. It simply runs on a
host where an unrelated, permanently-running, CPU-hungry process competes with two
latency-sensitive suites, and nothing in the gate can observe or control that.

No test suite was redesigned and no application code was touched.

## 9. Does the gate represent the project's approved quality policy?

**No.**

The project operates a **three-category** policy — the WP-2.7e closure register formally
classifies six items as *"pre-existing non-blocking technical debt"* — while the gate
implements a **two-state** one. The gate is **stricter than the policy the project
actually runs under**, and the gap is not a bug in any script; it is a missing concept.

The practical consequence is already visible. Under the standing F-5 instruction (do not
fix, do not weaken, do not modify the timeout), **no release can ever pass this gate.**
`--skip-gates` is therefore not an escape hatch, it is the only remaining door — which is
precisely why it should not be walked through casually.

## 10. Is `--skip-gates` actually necessary?

**Structurally, yes — and that has not changed.** Given a Vitest gate that fails and may
not be repaired, and no exception mechanism, there is no other way to reach step 3 of 8.

**But its meaning has changed, and this is the heart of the finding.**

On 2026-09-11, `--skip-gates` would have bypassed **one** accepted, causally-proven,
client-classified flake. Today it would additionally bypass **two previously unreported
failures that no one has assessed and no client decision covers** — 9 Pint issues and 12
Prettier files that are direct evidence the tree is not the verified artifact.

The 2026-09-11 recommendation rested on this premise:

> *"Every gate has been run manually against this exact commit and passes, with the sole
> exception of a flake the Client has twice classified as non-blocking."*

**That premise is no longer true**, on two counts: the commit no longer exists, and two
further gates fail.

## 11. Recommended deployment decision

**DO NOT deploy yet — and do not authorize `--skip-gates` on the current evidence.**

Not because of F-5. Because of three things F-5 has nothing to do with.

### 1. The release is unverified as it stands

The evidence package names a commit that does not exist, and three of its nine gate
results no longer reproduce.

### 2. Two backend tests are missing relative to the verified release

One is traced to `DailyDigestCommandTest`. That is lost verification coverage, not
cosmetics.

### 3. The rollback safety net is degraded

`releases/` was destroyed in the workspace loss and does not exist. Both
`sccit/app:prod-2df17db` and `sccit/web:prod-2df17db` images survive, so
`rollback-prod.sh 2df17db` still functions — but with no manifest it takes this branch:

```sh
warn "no manifest for $TARGET — rolling back the images only"
TARGET_MIGRATIONS=''
```

**That disables the schema-ahead guard.** The warning is conditional on
`TARGET_MIGRATIONS` being non-empty:

```sh
if [ -n "$TARGET_MIGRATIONS" ] && [ "$LIVE_MIGRATIONS" -gt "$TARGET_MIGRATIONS" ]; then
    warn "the live schema is AHEAD of the target release by …"
```

After a 30 → 32 migration, rolling back to a 30-migration image against a 32-migration
database would proceed **without the warning the script exists to give.**

Additionally, `deploy-prod.sh` will find no `releases/current`, announce itself as
*"the first tracked deployment"*, and — on smoke-test failure — **print no rollback
command at all**, because that line is conditional on `$PREVIOUS` being non-empty.

**This is a live deployment hazard, independent of every gate question in the brief.**

### The path recommended for the owner's decision — not taken

- Authorize a **formatting-only** reconciliation: `pint` and `prettier --write` across
  the 21 affected files. This is not weakening anything — it is applying the project's
  own committed formatters, and it touches no logic, no assertion and no timeout. It
  would clear 2 of the 3 failing gates honestly.
- Authorize reconstructing the **one missing digest test** from the WP-2.7e report's
  enumeration, restoring 943 → 944.
- Re-run the full gate. It will then fail on **F-5 alone**, restoring the exact, clean
  decision the 2026-09-11 report intended to put in front of the owner.
- Separately decide the rollback question: either accept an images-only rollback with
  the schema guard disabled, or authorize reconstructing
  `releases/2df17db/manifest.json` (`migration_count: 30`) before deploying.

None of this is authorized, and none of it has been done.
