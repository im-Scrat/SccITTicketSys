# WP-2.7c — Announcements Completion Report

Announcements are implemented end to end: an administrator composes a draft,
publishes it to a targeted audience, and that audience — and only that audience
— receives an in-app notification and can read the announcement. **No email is
sent, and that is now a property of the dispatch path rather than a promise.**

Nine Project Owner decisions were implemented as approved. No schema change was
made, no permission was added, and no requirement document was touched.

## 3. WP-2.7c-1 results — the channel-exclusion mechanism

`ProjectNotification::via()` is `final`, and before this change it could only
ever widen delivery: `forcedChannels()` bypassed the preference gate and nothing
could refuse a channel. That is correct for a notification addressed to one
person about their own work, and wrong for a broadcast.

The reason exclusion had to exist at all is arithmetic, not taste. Preferences
are **opt-out** — an absent `notification_preferences` row means *enabled* — so
on a fresh system the gate would have allowed email for every recipient, and a
single `audience = all` announcement would have mailed the entire organisation.
Seeding email off for every user was explicitly rejected by the owner and is
also not a guarantee: a user can switch it back on, and every future user would
need seeding forever.

```php
public function excludedChannels(): array   // default: []
{
    return [];
}
```

Inside `via()`, exclusion is checked **first** and wins outright — over the
forced list as well as the preference gate. Where the two exceptions could
contradict each other, the reading that sends *less* wins.

`backend/tests/Feature/Notifications/NotificationChannelExclusionTest.php` — 7 tests:

1. defaults to excluding nothing, so existing notifications are unaffected
2. refuses an excluded channel even when the preference allows it
3. lets exclusion outrank a forced channel
4. still honours a forced channel when nothing excludes it
5. still honours a disabled preference when nothing forces or excludes it
6. can exclude the in-app channel too, leaving mail only
7. sends nothing at all when every channel is excluded

**Regression evidence.** Test 1 exists specifically to prove the default is
inert. The pre-existing WP-2.7a notification suites — `NotificationTriggerTest`,
`NotificationDispatcherTest`, `NotificationPreferenceGateTest`,
`NotificationChannelTest`, `NotificationDisclosureTest`,
`NotificationAuthorizationTest`, `SlaDetectionTest` — were kept as the gate and
all pass unmodified. **No existing notification behaviour changed.**

## 6. Notification results — FR-NOT-003 trigger 12

`AnnouncementPublished` → `NotifyOnAnnouncementPublished` → recipients from
`NotificationAudience::forAnnouncementAudience()` (active accounts only) →
`AnnouncementPublishedNotification`.

Payload:

```php
'title'      => $announcement->title,
'message'    => $renotified ? 'Announcement re-sent by an administrator.' : null,
'data'       => ['announcement' => $uuid, 'pinned' => (bool) $is_pinned],
'action_url' => '/app/announcements/'.$uuid,
```

The announcement **body is deliberately absent** even though it is plain text
and would fit — DD-61: notifications carry structural facts, never borrowed
prose. The notification says *that* something was announced and links to it.

**Idempotency.** `dedupe_key` is `announcement.published:{uuid}`, so a retried
job, a double-clicked button or a re-published announcement cannot leave a user
with two rows saying the same thing. A deliberate re-notification appends the
dispatch id, because there the point *is* that the audience is told again.

`AnnouncementNotificationTest.php` — 12 tests, including: sends NO email when
published · writes an in-app notification for the targeted audience · does not
notify a role outside the audience · does not notify the publishing
administrator · carries an internal destination the client is allowed to follow
· does not carry the announcement body · does not duplicate on a second publish
· notifies nobody when merely edited · notifies again when explicitly asked ·
sends no email on a deliberate re-notification either · notifies nobody when
withdrawn.

FR-NOT-003 therefore moves from **nine of twelve** implemented triggers to
**ten of twelve**. The two still outstanding — low-stock reorder and procurement
approval/rejection — remain blocked on WP-2.4b and are untouched.

## 7. Authorization results

The guarantee the owner asked for is structural, not asserted. `scopeReadable()`
(the list) and `canRead()` (the single record) are **the same rule in one
service**, and `AnnouncementPolicy::view()` calls `canRead()`. A list filter
that could disagree with the single-record check *is* an IDOR; here they cannot
disagree.

Reading is scoped by five conditions: `is_active`, audience ∈ {`all`, the
reader's own}, `starts_at` null-or-past, `ends_at` null-or-future. Managing is
scoped by permission and is deliberately **unscoped by audience** — an
administrator managing announcements must see drafts, expired rows and other
audiences' announcements, because those are the ones needing attention.

An administrator is *not* simply allowed everything: on the **reader** surface
they are just another audience member, so their announcements page shows what an
administrator was told, not the estate. Collapsing the two would hide targeting
mistakes from the person most able to fix them.

`AnnouncementAuthorizationTest.php` — 16 declarations, 28 executed cases:

- every management route refused to a technician (7 cases) and to a teacher
  (7 cases), and to an unauthenticated caller
- an announcement absent from a reader's list is **refused by uuid** (403)
- an unpublished announcement is refused by uuid even to its own audience
- a not-yet-open window and a closed window are both refused by uuid
- the reader is audience-scoped **even for an administrator**
- the management surface shows an administrator everything

## 8. Security results

| Concern | Outcome |
|---|---|
| IDOR | List rule and uuid rule are one service; asserted directly against the encoded payload |
| Internal key disclosure | `id` on the wire is the **uuid**; the bigint PK and the raw `created_by` FK never leave. Asserted. |
| Draft-state disclosure | `is_active`, `updated_at` and `created_by` are `when($manages)` — structurally absent from a reader's payload, not filtered client-side. Asserted. |
| XSS | `content` is plain text; React escapes it. A test feeds `<img src=x onerror="alert(1)">` and asserts no `<img>` node is created. `dangerouslySetInnerHTML` appears nowhere in the frontend. |
| Open redirect | `action_url` is an internal `/app/` path built by the server; the WP-2.7b client-side prefix gate (DD-65) still applies. No external URL is introduced. |
| Accidental broadcast | `is_active` is unwritable by any request; publishing and re-notifying are separate endpoints with separate audit actions |
| Mass email | Structurally impossible for this notification — the channel is refused before the gate is consulted |
| Audit | Six `ActivityAction` values (created / updated / published / unpublished / renotified / deleted), each written in the same transaction as the change |
| Deletion | Soft delete — the row survives for the audit trail, `withTrashed` is not offered on any surface |

## 18. Risks and limitations

- **The shared dispatch path was modified.** This is the real risk of WP-2.7c.
  It is mitigated by the default being inert (`excludedChannels()` returns `[]`),
  by a dedicated seven-test suite covering the precedence lattice, and by the
  entire WP-2.7a notification regression suite passing unchanged — but it is a
  change to code every notification runs through, and it deserves that framing.
- **`audience = all` resolves to every active user.** On a large estate this is
  one queued job per recipient. It is bounded by the existing per-recipient
  failure isolation (DD-59) and the queue, and no announcement in the fixtures
  exercises a large audience. Volume behaviour has not been load-tested.
- **The notification is in-app only.** A user who has switched announcements off
  in-app receives nothing at all — no email fallback exists by design. This is
  the accepted consequence of the D5 policy, not an oversight.
- **Nothing is deployed.** Production bakes code into its image, so `:8081` does
  **not** have announcements until the image is rebuilt. Development parity was
  verified; production parity was not, because deployment was not authorised.
- **Announcement audience is derived from role slug.** `audienceFor()` maps
  `administrator`/`technician` and treats everything else as `teacher`. If a
  fourth role is ever added it will silently fall into the teacher bucket. That
  is the same assumption the seeded three-role model makes everywhere else, but
  it is an assumption.
