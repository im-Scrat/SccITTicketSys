## 3. Migration release analysis (read-only)

Production is two migrations behind. Neither was run and production was not
altered.

| | Repository / dev / test | Production |
|---|---|---|
| Migration files | 32 | **30** (absent from the image, not pending in the database) |
| Applied | 32 | 30 |

**The two outstanding migrations**

| | WP-2.7a | WP-2.7e |
|---|---|---|
| Filename | `2026_09_05_100000_add_dedupe_key_to_notifications.php` | `2026_09_07_100000_add_digest_channel_and_digest_log.php` |
| Tables touched | `notifications` only | `notification_preferences` (CHECK), `notification_digests` (create) |
| Schema change | Adds nullable `dedupe_key`; partial unique index `(user_id, dedupe_key) WHERE dedupe_key IS NOT NULL` | Widens `notification_preferences_channel_check` to add `digest`; creates `notification_digests` with `UNIQUE (user_id, digest_date)` and FK → `users` cascade |
| Destructive | No | No |
| Additive | Yes | Yes — the channel domain is a strict superset |

**Ordering and dependencies.** Filename order applies WP-2.7a first. They touch
**disjoint tables**, so there is no data or structural dependency between them —
the order is safe either way, and Laravel's is deterministic. WP-2.7e's only
external dependency is `users`, which production has.

**Idempotency.** Laravel's `migrations` table prevents re-application of either.
WP-2.7e's `up()` is additionally re-runnable in isolation
(`DROP CONSTRAINT IF EXISTS`). WP-2.7a's `up()` is not re-runnable by hand
(`CREATE UNIQUE INDEX` without `IF NOT EXISTS`), which is harmless under normal
migration control but worth knowing before any manual intervention.

**Interaction with the existing production schema — the decisive finding.**
Production already has `notifications` and `notification_preferences`, both
carrying **zero rows**, and its channel CHECK is still the two-value domain.
`notification_digests` does not exist. So both migrations would run against
empty tables:

- adding a nullable column and a partial index to a 0-row table is effectively
  instant, with no backfill and no lock contention;
- dropping and re-adding a CHECK on a 0-row table revalidates nothing;
- creating a new table is unconditioned.

This is the lowest-risk shape a schema migration can have. It also means the
`down()` data-loss hazard DD-63 records — deleting `digest` preference rows —
has **nothing to delete** in production today.

**Rollback implications.** WP-2.7e's `down()` drops `notification_digests`,
deletes `digest` preference rows, then restores the narrow domain; it was
executed against a live `digest` row during implementation and succeeded.
WP-2.7a's `down()` drops the index and the column, discarding every
`dedupe_key`. Rolling both back returns the schema to migration 30 exactly, at
the cost of any digest preferences and idempotency keys accumulated by then.

**Also carried by the same release.** WP-2.7c requires no migration, and the
tables its code needs (`announcements`, `activity_logs`) are baselined and
present in production. So the code half of WP-2.7b and WP-2.7c ships with this
release without further schema work.

### Conclusion

**Yes — the two migrations should be treated as one controlled Phase 2.7
deployment unit.**

This is not merely advisable, it is unavoidable: Laravel applies all pending
migrations in filename order within a single `migrate` invocation, so deploying
WP-2.7e necessarily applies WP-2.7a first. Attempting to separate them would
require deliberately withholding a migration file from an image, which would
leave the repository and production diverged in a way no tooling tracks.

They are safe together — disjoint tables, both additive, both against empty
production tables — and the release should be planned, snapshotted and
rehearsed as **the first production release of Phase 2.7 in its entirety**
(WP-2.7a, WP-2.7b, WP-2.7c and WP-2.7e), not as a WP-2.7e deployment.

## 5. Digest length — recorded product decision

The absence of a maximum digest length is recorded as a **non-blocking product
decision**. No cap was invented and WP-2.7e was not modified.

For the record, so a future decision has the evidence: live verification
produced a digest listing **112 items** for one fixture account. That is
artificial test accumulation rather than realistic daily volume, but it
demonstrates that the digest is unbounded by design. FR-NOT-008 specifies no
limit.

A future product decision may determine whether a **maximum length, grouping by
notification type, pagination, or summarisation** ("and 40 more") is desirable.
Nothing in the current implementation forecloses any of those.
