# WP-2.7b — Notification Experience Planning & Implementation Proposal

Planning and reconnaissance only. **No application code, schema, migration,
test, configuration, Docker file or specification document was created or
modified, and no commit was made.** Every statement below was read from the
repository, the running development stack (read-only queries) and the
specification documents.

---

## 1. Executive summary

WP-2.7b is the **user-facing half** of the notification feature: the surfaces
that let a person see what the system told them, act on it, and control what it
tells them next. WP-2.7a built everything behind that and left an API; this work
package consumes it and adds no notification logic of its own.

**The scope is smaller than it looks, for three reasons.**

**The backend is complete and needs no changes.** Eight endpoints already cover
list, badge count, single record, mark read, mark unread, mark all read, and the
preference matrix. The paginator envelope already matches the existing
`Pagination` component's props exactly. §19 recommends **zero** backend or
database changes.

**The design system already decided the hard question.** `DESIGN.md` §5 states
the top bar holds *"global search, environment/org switcher, **notifications**,
and the user menu"*. Placement is therefore not an open design question — it is
an existing, documented decision this work package implements.

**Every primitive already exists.** `Badge`, `EmptyState`, `Pagination`,
`Skeleton`, `Spinner`, `Alert`, `Drawer`, `Tabs`, `Checkbox`, `Surface`,
`Button` and `StatusPill` are all in `components/ui/`. WP-2.7b composes them; it
should not introduce a new visual vocabulary.

**What genuinely needs deciding is in §24.** The largest is **D1 timing** — build
the preference screen for today's 18-cell matrix, or make the approved-but-unbuilt
digest channel a prerequisite so it is built once for 27 cells. §16 recommends
**Option A (18 cells now)** and explains why.

**Two premises in the authorization need correcting**, both in the project's
favour — see §2.4 and §18.

### 2.4 Correction — the stack has no Inertia

The authorization's *Architectural Impact* section lists "Inertia" among the

verified by searching `docs/`, `frontend/src`, `frontend/package.json` and
`backend/composer.json`.

first-party cookies (SDD §7.3, DD-04): Nginx serves the built SPA and proxies

page bridge. This matters for planning because it means **notification state is
client-side cache state** — TanStack Query — rather than props delivered with a
page render. Every design choice below assumes that model.

## 5. UI/UX architecture

The UI/UX analysis below follows the **Impeccable `shape` flow**
(`.claude/skills/impeccable/reference/shape.md`), which is the sub-command
whose stated purpose is *"plan UX/UI before writing code"*.

`shape` requires a discovery round **unless DESIGN.md already answers the needed
inputs**. It does, for almost everything: `DESIGN.md` and
`.impeccable/design.json` (schema v2, generated by Impeccable for this repo) pin
the colour strategy, the theme model, the named anchors, the layout philosophy,
the component vocabulary and the bans; the authorization pins scope, breadth and
anti-goals. The residual genuine unknowns are **not assumed** — they are raised
in §24.

*Visual direction probes are skipped: this harness has no native image
generation, and the surface is not directionally ambiguous — it must look like
the application it lives in.*

### 5.1 Design brief

**Feature summary.** A place for a person to see what the system told them,
act on it, and control what it tells them next. Three roles use it with
different content but the same mechanics.

**Primary user action.** *Read the thing I was told, then go to the record it is
about.* Everything else — filtering, marking, preferences — is secondary. The
list exists to be left.

**State of mind.** A technician glancing between jobs; an administrator
triaging; a teacher checking whether their fault report moved. All three are
**interrupted**, not exploring. This argues for scannability over density and
for a destination link that is unmissable.

**Design direction — inherited, not invented.**

| Input | Value | Source |
|---|---|---|
| Colour strategy | **Restrained** — Signal Blue ≤10%, neutrals and type carry the rest | design.json *One Voice Rule* |
| Theme | Dual-mode; light and dark are equal citizens, verified at AA | design.json |
| Scene | *"An operations console read in a bright corridor on a phone between jobs, and on a desktop under fluorescent light all afternoon."* | forces both themes and a real mobile case |
| Anchors | **Linear, Stripe dashboard, GitHub** | DESIGN.md §1, verbatim |

**Scope.** Production-ready; a whole surface (centre + entry + preferences);
shipped-quality components; polish until it ships.

**Anti-goals.** Not a social feed. Not a chat. Not a toast system. Not a
red-dot dopamine loop. **The biggest risk of getting this wrong is making the
badge feel like an alarm** — the north star is *"exactly one indicator light
means something the moment it turns on"*, and an indicator that is always lit
means nothing.

### 5.2 The four design constraints that actually bind

**① Red is unavailable for the badge.** design.json's *Reserved-Red Rule*:
*"Red is only destructive, critical, or offline. It is never a brand color,
decorative accent, or emphasis."* The conventional red notification dot is
therefore **banned by the project's own design system**. The badge uses
`--primary` (Signal Blue), which is exactly the documented use — *"primary
action, current selection, active nav, focus"* — and is the literal "one
indicator light" of the north star.

**② Colour alone cannot carry unread.** NFR-ACC-004 and design.json both forbid
it. Unread must be conveyed by **at least two of** a leading dot, a weight
change, a text label, and the accessible name. The existing `StatusPill` shows
the house pattern: subtle wash + strong same-hue text + an 8px leading dot,
with the label carrying the meaning.

**③ Icons are never alone — except in the top bar, where there is a
precedent.** `AppLayout`'s directive is explicit: *"every one is paired with its
text label, at 32px, so the meaning does not depend on recognising a glyph."*
But the top bar already contains an icon-only control — `ThemeToggle`, a 36px
button with `aria-label` **and** `title`. That is the precedent a notification
bell should follow, and §6 uses it rather than inventing a third pattern.

**④ Shadow means "floating".** *Flat-Plane Rule.* A dropdown panel may cast; the
list rows underneath may not, and cards may not nest.

### 5.3 Composition

Every element maps to an existing primitive. **No new `components/ui/`
primitive is required.**

| Element | Built from |
|---|---|
| Notification row | `Surface` + `Badge` + relative time; **not** a nested card |
| Type/topic label | `Badge` with an existing tone |
| Unread marker | leading dot + `font-semibold` + accessible name |
| Filters | `Tabs` (unread/all) + `Select` (type) |
| Pager | `Pagination` — props already match the API envelope |
| Empty | `EmptyState` — teaching copy, never "No data" |
| Loading | `Skeleton` rows; `Spinner` for in-flight actions |
| Error | `Alert` with a retry action |
| Preferences grid | `Checkbox` in a `Table` |
| Dropdown panel | `Drawer` on mobile / a positioned `Surface` with overlay shadow on desktop |

## 6. Navigation design

### 6.1 Placement — already decided by DESIGN.md

`DESIGN.md` §5 (Components → Top bar): *"`--surface` with a bottom `--border`,
holding global search (command palette, ⌘K), environment/org switcher,
**notifications**, and the user menu."*

So the entry belongs in the **header utility cluster**, to the left of
`ThemeToggle` and the account menu — **not** as a fourteenth item in the primary
nav row.

**Why not the primary nav row.** That row is already 8–13 items wide depending
on role, scrolls horizontally on narrow screens, and each item is a 60px
labelled target. Adding notifications there would push it wider, and — decisively
— a badge on a horizontally scrolling row can scroll out of sight, which is the
one thing a notification indicator must never do. The header cluster is sticky
and always visible.

### 6.2 The entry itself

Following the `ThemeToggle` precedent: a 36px icon button (`Bell`,
lucide-react, already a dependency) with `aria-label` and `title`. This clears
NFR-ACC-009's 24×24 minimum comfortably.

The accessible name is **dynamic and states the count**:

- 0 unread → `"Notifications"`
- n unread → `"Notifications, 3 unread"`

The visible badge shows the number in tabular figures, capped at `99+` so the
control cannot change width and shift the header.

### 6.3 Route

One new authenticated route, `/app/notifications`, declared inside `AppLayout`'s
children in `App.tsx` alongside `/app/account`.

**No `RequirePermission` wrapper.** Every authenticated user has notifications,
no `notifications.*` permission exists, and inventing a guard here would imply a
permission that WP-2.7a deliberately did not create. This matches `/app/account`,
which is likewise ungated.

## 7. Notification centre design

### 7.1 Topology — panel *and* page

**Recommended: both, sharing one data layer.**

- **Dropdown panel** from the header button — the most recent ~8, unread first,
  with *Mark all read* and *See all*. Serves the interrupted glance, which is the
  dominant case.
- **Full page** at `/app/notifications` — pagination, filters, the complete
  history. Serves triage and search-back.

They share the same query hooks and the same row component, so "both" costs one
extra container, not two implementations. A panel alone cannot satisfy
FR-NOT-005's filtering or offer a stable URL; a page alone makes the badge a
link to a context switch, which fights the glance.

*Alternative if the owner prefers minimum surface: page only. See §24-Q2.*

### 7.2 Row anatomy

```
┌──────────────────────────────────────────────────────────────────────┐
│ ●  Ticket TKT-000123 assigned to you              [Assignment]  2h   │
│    Projector in Laboratory 4 will not power on                       │
│    → Open ticket                                    [Mark as read]   │
└──────────────────────────────────────────────────────────────────────┘
   ▲                                                  ▲            ▲
   unread dot + semibold title                     type badge   relative
   (never colour alone)                                          + title=
                                                                absolute
```

- **Title** from `title`; **body** from `message`; both plain text, rendered as
  text — never as HTML.
- **Type badge** from `type` (nine values), with the finer `topic` used only to
  pick the icon. Filtering is by `type`, because that is what the API accepts.
- **Timestamp** relative in the label, absolute in `title` and `dateTime` on a
  `<time>` element. Tabular figures.
- **Action** renders only when `action_url` is present — `account.locked`
  deliberately has none.

### 7.3 Interaction model

| Action | Behaviour |
|---|---|
| Click the row's link | Navigate to `action_url`, marking read optimistically |
| *Mark as read* | Explicit control, so reading without leaving is possible |
| *Mark all read* | Confirmed only if >20 unread; otherwise immediate with undo-by-reopening |
| Filter change | Refetch with `placeholderData: keepPreviousData` — no layout collapse |
| Page change | Same, matching every other list in the app |

**Optimistic updates with rollback** for read/unread, using TanStack Query's
`onMutate`/`onError` pattern, then invalidating both the list key and the
unread-count key. This is the one place the UI writes; everything else reads.

### 7.4 Grouping

**Recommended: no grouping in v1** — a flat reverse-chronological list, with
"unread first" available as a filter rather than as a sort. Grouping by day is
the obvious next step and is cheap to add later; grouping by topic fights the
chronological mental model of an inbox. Raised as §24-Q3 rather than assumed.

## 8. Badge / unread design

| Question | Answer | Why |
|---|---|---|
| Colour | **Signal Blue** (`--primary`) | Reserved-Red Rule forbids red; blue is the documented indicator hue |
| Shape | Small rounded rect with the count, tabular figures | A bare dot cannot say "how many" |
| Zero state | **Badge absent**, name reverts to `"Notifications"` | An always-lit indicator means nothing |
| Cap | `99+` | Fixed width; the header must not reflow |
| Screen reader | Count in the button's accessible name | A visual badge is invisible to AT |
| Live announcement | `aria-live="polite"` on a visually-hidden text node, **debounced** | See below |

**Freshness without real time.** FR-NOT-007 (Reverb) is P4 and out of scope, so
the count is polled. The global `queryClient` sets `refetchOnWindowFocus: false`
and `staleTime: 30s`, so the badge query must **override both locally** —
`refetchInterval` plus `refetchOnWindowFocus: true`, since returning to the tab
is exactly when a person expects the count to be current.

**Recommended cadence: 60s**, only while the tab is visible. Cheap (one indexed
`COUNT` on a partial index), invisible to the user, and honest about not being
real time. Raised as §24-Q4 because it is a load decision, not purely a design
one.

**The live region needs care.** Announcing every poll would make a screen reader
speak over the user's work. Recommendation: announce only when the count
*increases*, at most once per polling interval, as a short polite message
("3 unread notifications"). Never `assertive`.

## 9. Notification preferences design

`GET /api/notification-preferences` already returns the complete matrix with
gaps resolved and `meta.default_enabled: true`, so the client renders what it is
given and never re-implements the opt-out rule.

**Layout: a table, types as rows, channels as columns.**

|  | In-app | Email |
|---|:--:|:--:|
| Assignment | ☑ | ☑ |
| Ticket update | ☑ | ☐ |
| … (nine types) | | |

- Each cell is a labelled `Checkbox`; the accessible name is the **pair**
  ("Email notifications for ticket updates"), because a bare checkbox in a grid
  is meaningless to a screen reader.
- Column headers use `scope="col"`, row headers `scope="row"`.
- **Save is explicit**, batching every changed cell into one `PUT` — the endpoint
  accepts an array precisely so a flaky connection cannot half-save eighteen
  switches.
- On narrow screens the table becomes stacked groups per type; nine groups of two
  is legible where an 18-cell grid is not.

**Copy must state the default**, once, above the table: *"Everything is on until
you turn it off."* Otherwise a never-visited user cannot tell whether the ticks
are their choice or the system's.

**One honest limitation to surface in the copy:** the account-lockout security
email cannot be switched off. `AccountLocked` forces the email channel. The
`system` row's email cell should be rendered **disabled with an explanation**
rather than silently ignoring the user's click.

**Placement:** a section on `/app/account` (which exists and is ungated) or a
tab on the notification centre. **Recommended: `/app/account`**, because that is
where a user already goes to change things about themselves. §24-Q5.

## 10. Role / authorization matrix

Derived from the WP-2.7a listeners and visibility services. **No new permission
is introduced.** "By designed path" means the role reaches that notification
through the workflow as built.

| | **Administrator** | **Technician** | **Teacher** |
|---|---|---|---|
| **Types received** | `warning` (SLA), `maintenance` (due, work-support submitted), `system` (lockout); plus `assignment`/`ticket_update` where they personally participate | `assignment`, `ticket_update`, `warning` (own SLA), `maintenance` (scheduled/due/rescheduled, own decisions), `system` | `ticket_update` (own tickets, and tickets they commented on), `system` |
| **Topics by role** | T4, T5b, T9, T11 | T1a, T1b, T2, T3, T4, T5a, T5b, T6, T10, T11 | T2, T3, T11 |
| **Never receives** | — | T9 (administrator audience) | T1, T4, T5, T6, T9, T10 — **no designed path**, and internal comments never reach them |
| **Destinations** | `/app/tickets/{uuid}`, `/app/maintenance/{uuid}`, `/app/work-support/manage` | `/app/tickets/{uuid}`, `/app/maintenance/{uuid}`, `/app/work-support` | `/app/tickets/{uuid}` |
| **Actions** | read, unread, mark all read, filter, set own preferences | identical | identical |
| **Preference controls** | all 18 cells; `system`+email disabled (forced lockout email) | identical | identical |
| **Restrictions** | **no override** — cannot see another user's notifications | own only | own only |

**Destination reachability was verified**, not assumed: every destination a role
can receive is a route that role can open. `/app/tickets/:id` is gated by
`tickets.view`, held by all three. `/app/maintenance/:id` is gated by
`maintenance.view`, which Teachers lack — and Teachers receive no maintenance
notification by any designed path. `/app/work-support` is technician-only by role
and T10 goes only to the submitting technician; `/app/work-support/manage` is
administrator-only and T9 goes only to administrators. **No dead links.**

**The UI must still handle a dead link gracefully** — the Forbidden page — because
an administrator could in principle name any user as a maintenance technician,
and role membership can change after a notification is written.

## 11. API integration

### 11.1 Contract, as returned by the running application

`GET /api/notifications`

```jsonc
{
  "data": [{
    "id": "64366ab7-…",            // uuid — the public identifier
    "type": "ticket_update",       // one of nine; what filtering accepts
    "topic": "ticket.commented",   // one of eleven; icon + grouping only
    "title": "New comment on ticket TKT-000123",
    "message": "Projector in Laboratory 4 will not power on",
    "payload": { "topic": "…", "ticket": "…", "ticket_number": "TKT-000123" },
    "action_url": "/app/tickets/64366ab7-…",   // always relative, may be null
    "is_read": false,
    "read_at": null,
    "created_at": "2026-09-05T06:49:32+00:00"
  }],
  "links": { "first": "…", "last": "…", "prev": null, "next": null },
  "meta": { "current_page": 1, "from": 1, "last_page": 1, "per_page": 20,
            "to": 1, "total": 1, "path": "…", "links": [ … ] }
}
```

`GET .../unread-count` → `{"unread": 3}` ·
`PATCH .../read-all` → `{"marked": 12}` ·
`GET/PUT /api/notification-preferences` →
`{"data":[{channel, notification_type, is_enabled}], "meta":{channels, types, default_enabled}}`

**`meta` maps onto the existing `Pagination` component with no adapter:**
`page ← current_page`, `lastPage ← last_page`, plus `total`, `from`, `to`.

### 11.2 Proposed slice

```
src/features/notifications/
  api/notificationsApi.ts     fetchNotifications, fetchUnreadCount,
                              markRead, markUnread, markAllRead,
                              fetchPreferences, updatePreferences
  hooks/queries.ts            useNotifications, useUnreadCount, usePreferences
  hooks/mutations.ts          useMarkRead, useMarkUnread, useMarkAllRead,
                              useUpdatePreferences
  components/                 NotificationRow, NotificationList,
                              NotificationFilters, NotificationBell,
                              NotificationPanel, PreferenceMatrix
  pages/NotificationsPage.tsx
  types.ts
```

Query keys namespaced per SDD §7.2:

```ts
export const notificationKeys = {
  all: ['notifications'] as const,
  list: (unread?: boolean, type?: string) => ['notifications', 'list', unread ?? false, type ?? 'all'] as const,
  unreadCount: () => ['notifications', 'unread-count'] as const,
  preferences: () => ['notifications', 'preferences'] as const,
}
```

Every mutation invalidates `list` **and** `unreadCount`, because marking read
changes both and a stale badge beside a cleared list is the most visible
possible bug.

### 11.3 Rules

- **Use the API's filtering and pagination.** Do not fetch everything and filter
  in the browser: the server already filters, and a client-side filter would drift
  from the server's semantics and grow without bound.
- **Do not re-derive read state.** `is_read` is authoritative.
- **Do not reconstruct destinations.** Use `action_url` verbatim; the server built
  it, which is the FR-QR-011 open-redirect discipline applied here. Validate that
  it starts with `/app/` before routing, and fall back to no link if not.

## 12. Accessibility plan

Targets NFR-ACC-001..009 and the WP-2.7d `axe` gate, whose baseline currently
allows **only** two `link-in-text-block` entries on public pages. **Any new
violation on any new surface fails the build.**

| Concern | Plan |
|---|---|
| Badge | Count in the button's accessible name; never colour-only; `99+` cap |
| Live region | Visually-hidden `aria-live="polite"`, announcing only **increases**, debounced to the poll interval; never `assertive` |
| List semantics | `<ul>`/`<li>`; each row a list item with one primary link; **not** a table (rows are not tabular) |
| Unread state | Dot **and** weight **and** accessible text ("Unread") — NFR-ACC-004 |
| Timestamps | `<time dateTime>` with absolute in `title`, relative in text |
| Filters | Native `Tabs`/`Select` with labels; `aria-current` on the active tab |
| Buttons/links | A link that navigates, a button that acts — never a `div` |
| Keyboard | Full traverse; panel opens on `Enter`/`Space`, closes on `Escape` |
| Focus management | Opening the panel moves focus in; closing returns it **to the bell**; the page's heading receives focus on route entry |
| Focus ring | 2px at 2px offset, inherited from the token layer (NFR-ACC-003) |
| Target size | ≥24×24 (NFR-ACC-009); the bell is 36px |
| Zoom / reflow | Usable at 200% and at 320px width (NFR-ACC-007) |
| Motion | Panel transition 150–250ms, disabled under `prefers-reduced-motion` (NFR-ACC-005) |
| Contrast | Badge and dot verified in **both** themes (NFR-ACC-002) |

**Two specific hazards worth naming now.** A panel that traps focus is a
keyboard trap and fails NFR-ACC-003 — it must close on `Escape` and return
focus. And a live region that fires on every poll will talk over the user; the
increase-only rule exists to prevent that.

**Baseline discipline:** the a11y baseline file is documented as *"DEBT, not
policy. Entries should be deleted, never added."* **WP-2.7b must add no
entries.**

## 13. Testing strategy

Matches the existing conventions — Vitest + Testing Library, `vi.mock` of the
API module, assertions on **text** rather than styling *"because that is what
survives grayscale, colour-blindness and a screen reader."*

### Component / unit (Vitest)

## 14. E2E strategy

Runs through `sh scripts/e2e.sh` on the committed WP-2.7d harness (dev `:8080`,
one worker, no retries, deterministic fixtures).

**A precondition the harness does not yet meet:** the three fixture accounts
exist, but `sccit:e2e-fixtures` seeds **no notifications**. A notification-centre
E2E test needs deterministic notification rows. Two options — extend the fixture
command, or have the spec *cause* notifications by driving a real workflow (sign
in as administrator, assign a ticket to the fixture technician, then assert the
technician sees it). **Recommended: the second**, because it proves the whole
chain end to end and adds nothing to a seeder that other suites depend on.
Raised as §24-Q6.

| Role | Flow |
|---|---|
| **Administrator** | Sign in → a support request is submitted → badge increments → open panel → open centre → the T9 notification is present → follow it to `/app/work-support/manage` → mark all read → badge clears → set a preference and confirm it persists |
| **Technician** | Sign in → an administrator assigns them a ticket → badge increments → open the notification → land on the ticket → mark read → filter unread and confirm it is gone |
| **Teacher** | Sign in → their ticket's status changes → they see it → **an internal comment is added and they do NOT see it** → they cannot reach another user's notification by uuid (403) |

The Teacher spec carries the two most valuable assertions in the suite: the
internal-note exclusion and the ownership boundary, both proven **through a
browser** rather than in-process.

### Accessibility E2E

Add to `a11y.spec.ts`'s per-role route lists:

- administrator, technician, teacher → `/app/notifications`
- plus one audit **with the panel open**, since a dropdown's semantics are not
  exercised by auditing the page behind it.

## 15. Security analysis

| Control | Plan |
|---|---|
| Ownership | **Server-enforced**; the client adds no filtering of its own and never sends a user identifier |
| Administrator override | **None** — must not be added; §10 says so and `NotificationPolicy` enforces it |
| New permissions | **None.** The §8.4 matrix does not change (OD-4 precedent) |
| Internal ids | Not exposed — the API returns `uuid` as `id` and omits `user_id` |
| `dedupe_key` | Not exposed by the API; the client must not attempt to derive or display it |
| Payload rendering | `payload` is a free-form bag. **Render only known keys**, as text. Never `dangerouslySetInnerHTML`, never spread into the DOM |
| Destinations | Use `action_url` verbatim, and assert it begins with `/app/` before routing — no absolute URLs, no open redirect |
| Sensitive content | Already excluded server-side by the WP-2.7a content rule; the client adds no second source |
| Session | Existing axios interceptor handles 401/419; no new auth path |
| Caching | Notification data lives in the TanStack cache, which is cleared on logout by the existing principal reset — **verify this explicitly**, since a cached list surviving a logout on a shared machine would be a real leak |

**The one new risk WP-2.7b introduces** is client-side: rendering
attacker-influenced text. `title` and `message` derive from ticket titles, which
are user-authored. React escapes by default, so the rule is simply *never reach
for `dangerouslySetInnerHTML`* — stated here so it is a decision rather than an
accident.

## 16. D1 digest decision analysis

**The choice.** Build the preference screen for today's **2 × 9 = 18 cells**
(Option A), or make D1 a prerequisite and build it once for **3 × 9 = 27 cells**
(Option B).

| | **Option A — 18 cells now** | **Option B — D1 first, 27 cells** |
|---|---|---|
| Blocks WP-2.7b | No — starts immediately | **Yes** — a migration, an enum change and the `via()` fix must land first |
| Rework later | The matrix is generated from `meta.channels`, so a third column appears **without a component change**. Copy and the responsive stacking need a revisit | None |
| Risk | Low | **Carries WP-2.7a's regression risk into WP-2.7b.** Adding `NotificationChannel::Digest` throws `UnhandledMatchError` in `via()` for **every notification to every recipient** until that is fixed |
| Delivers digest | No | No — the schema alone sends nothing; a scheduled command, an aggregate template and a watermark are still needed |
| Honesty | The screen shows exactly what the system does | A digest column that does nothing yet is a promise the system does not keep |

**Recommendation: Option A.**

Three reasons. The preference matrix is **rendered from `meta.channels`**, so
adding a channel is a data change, not a component change — the rework Option B
avoids is largely imaginary. The schema change alone **delivers no digest**, so
Option B pays a real cost for no user-visible gain. And a visible-but-inert
digest column is exactly the kind of promise that erodes trust in a settings
screen.

**What Option A requires of the implementation**, so the later widening is
genuinely cheap:

1. Render the matrix from `meta.channels`, never from a hard-coded pair.
2. Make the responsive stacking layout channel-count agnostic.
3. Do not encode "two columns" in any test — assert against the returned matrix.

If the owner prefers Option B, D1 must be implemented as a **separate,
authorized, tested change landing before WP-2.7b starts** — not folded into it.

## 17. D5 announcement compatibility

D5 is accepted: publishing an announcement creates an **in-app notification and
no email**. WP-2.7c builds it; **WP-2.7b builds none of it**.

What WP-2.7b must do is ensure the future notification renders correctly the day
it first appears — which costs nothing if three things are true:

1. **`announcement` is already a `NotificationType`** and will already appear in
   the preferences matrix and the type filter, because both are generated from
   the enum rather than from a hard-coded list. **Nothing to add.**
2. **The row must not assume `action_url` is present.** An announcement may have
   no destination — the same shape `account.locked` already has. The absent-link
   case is already in the §13 test list.
3. **The icon map must have a default.** Mapping `topic` to an icon with an
   exhaustive `match`/`switch` would break on the first unknown topic. **A
   default arm is required** — this is the same class of failure the D1 analysis
   found in `via()`, and it is cheap to avoid before it exists.

That is the whole of WP-2.7b's D5 obligation: a generated type list, a nullable
link, and a defaulted icon map.
