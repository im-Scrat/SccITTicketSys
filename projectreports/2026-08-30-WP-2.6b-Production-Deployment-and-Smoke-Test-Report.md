## 1. A blocker found before deployment — the rollback baseline was gone

Step 1 of the authorized sequence is *record the current image digest*. Doing so
revealed that the named rollback image **no longer existed**:

```
docker image inspect sha256:81180836ee55…   →  No such image
docker image inspect sha256:13eda83bc86b…   →  No such image
```

**Cause, and it was mine.** When I rebuilt `sccit/app:prod` and `sccit/web:prod`
in earlier rounds, the tags moved to the new builds and the previous images
became untagged. Docker then garbage-collected them. The containers kept running
because a running container holds its own reference — but there was nothing left
to roll *back* to. This is precisely the failure mode your instruction
*"do not rely solely on a mutable Docker tag for rollback"* anticipated, and it
had already happened.

`docker commit` also failed — the underlying content layers were gone too:

```
NotFound: content digest sha256:32274469bb9e… not found
```

**Resolution — captured from the live containers, which was the last moment it
was possible:**

| Artifact | Detail |
|---|---|
| `docker export` of `sccit_prod_app` | 673 561 600 bytes |
| `docker export` of `sccit_prod_nginx` | ~48 MB |
| Re-imported with full config | `ENTRYPOINT`, `CMD`, `WORKDIR`, `USER`, `PATH` replicated from the release image, so rollback is a drop-in, not an improvisation |
| `sccit/app:rollback-preWP26b` | `447a5636fcc6` — **verified: 8 domains, no `WorkSupport`, 28 migration files** |
| `sccit/web:rollback-preWP26b` | `358004355bec` |
| Offline tars | retained in the session scratchpad |

Rollback capability is now **stronger** than the tag you were asked to rely on:
two tagged images plus two offline tars, contents verified as genuinely
pre-WP-2.6b.

**I proceeded rather than stopping** because the blocker was fully resolved
before the running stack was touched, no application code, schema or
configuration was involved, and deployment was explicitly authorized. If you
would have preferred a stop-and-ask at that point, say so and I will treat that
as the rule next time.

## 6. Two test-harness faults, corrected — reported rather than hidden

Both were faults in my test driving, not in the application. Both are recorded
because the first produced a **false PASS** that I had to retract.

**1. A false PASS on proof of work.** The first technician run asserted proof
submission by scanning the page for error text, and reported PASS. The database
disagreed: `resolution` empty, status still `scheduled`, zero evidence rows. A
**422** in the console was the real answer — the submission had been refused.
Re-driven properly, the API's message was:

> *"Attach at least one photograph of the work before submitting proof."*

That is **FR-MNT-010 working exactly as specified**. The corrected run attached a
photograph and the submission succeeded, with persistence verified in the
database rather than inferred from the page.

**2. Teacher ticket creation 422.** My payload omitted the required `category`.
Supplying a valid slug produced **201** and `TKT-2026-00003`. Again correct
application behaviour meeting an incomplete test.

I also briefly mis-read the nginx logs: a pattern matching ` 5xx ` caught the
**response byte size** (554, 525) rather than the status field and suggested 15
server errors. Re-checked against the status field, there are **zero 5xx**.
