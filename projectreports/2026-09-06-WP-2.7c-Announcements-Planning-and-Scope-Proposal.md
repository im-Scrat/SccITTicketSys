# WP-2.7c — Announcements Planning & Scope Proposal

Reconnaissance and planning only. No code, schema, migration, test,
configuration or document was modified, and no commit was created.

---

## 1. Executive Summary

Discovery changed the picture in two material ways, and both change the shape of
WP-2.7c.

**① Announcements are already half-built.** The accepted documentation says
*"No announcement domain code, publishing surface or trigger exists."* **That is
wrong, and I wrote it** during the reconciliation four hours ago. In fact the
repository already contains an `Announcement` model, an `AnnouncementAudience`
enum, a **baselined `announcements` table**, a working audience-filtered
dashboard widget, a frontend `AnnouncementList` component, and **six passing
backend tests**. What exists is the **reading** half — **FR-NOT-011 is
substantially satisfied**. What does not exist is the **writing** half:
FR-NOT-010, publishing, and the FR-NOT-003 trigger. This is recorded as a
documentation conflict in §16 and is the first thing to correct.

**② D5 cannot be implemented as the infrastructure stands.** The accepted
decision is *"publishing creates an in-app notification and sends no email."*
`ProjectNotification::via()` is **`final`**, iterates every channel, and admits
a channel when it is **forced or preference-allowed**. `forcedChannels()` can
only *add*. **There is no mechanism to suppress a channel.** Because preferences
are opt-out (absent row = enabled), an announcement dispatched today would be
**emailed to every recipient who has not explicitly opted out** — the exact
school-wide blast D5 was written to prevent. WP-2.7c therefore requires a small,
deliberate change to WP-2.7a infrastructure. This is the **blocker**, detailed
in §13.

Everything else is genuinely reusable: the dispatcher, the preference gate, the
notification centre, the badge and the row component all work unchanged. **No
second notification system is needed** (§8).

Nine decisions are genuinely undetermined by the existing documentation and are
raised in §19 rather than invented.

## 4. Existing Announcement Implementation (Discovery D, G, H, I)

**This section is the reason the work package is smaller than the documentation
implies.**

### Database — already baselined, no migration needed

`announcements` exists with every column FR-NOT-010 names:

```
id · uuid (unique, gen_random_uuid) · created_by (nullable) · title · content
audience (enum: all|teachers|technicians|admins, default all)
starts_at (tz, nullable) · ends_at (tz, nullable)
is_active (default true) · is_pinned (default false)
created_at · updated_at · deleted_at   [soft deletes]
indexes: created_by, is_active
CHECK announcements_date_order_check (ends_at IS NULL OR starts_at IS NULL OR ends_at > starts_at)
```

The `ends_at > starts_at` rule FR-NOT-010 requires is **already enforced by the
database**.

### Backend — model and enum exist

- `App\Models\Announcement` — soft deletes, `HasUuidRouteKey`, casts, `createdBy` relation.
- `App\Enums\AnnouncementAudience` — `all · teachers · technicians · admins`.
- `Database\Factories\AnnouncementFactory` — exists.
- **No** controller, request, action, service, policy or route.

### The display half is implemented — FR-NOT-011

`DashboardService::announcements()` composes a dashboard widget that:

- filters `is_active = true`;
- matches audience as **`All` + the caller's role audience**, resolved from
  `$user->role->slug` **server-side**;
- applies the window (`starts_at <= now`, `ends_at >= now`, nulls open-ended);
- orders **`is_pinned` first**, then newest;
- limits to **3**;
- returns **`uuid` as `id`** — no internal key leaks;
- returns `null` when empty, so the panel disappears rather than showing "none".

Frontend `features/dashboard/components/AnnouncementList.tsx` renders it: pin
icon with an accessible label, relative timestamp, prose capped at 65ch.

### Tests already covering it — 6

`backend/tests/Feature/Dashboard/DashboardAnnouncementsTest.php`:
omits the panel when empty · shows an all-audience announcement to every role ·
targets an audience-specific announcement to that role only · hides inactive and
out-of-window · puts pinned first · addresses announcements by uuid.

**Consequence:** FR-NOT-011 is satisfied *for the dashboard surface, bounded at
three rows*. Whether the requirement also demands a dedicated, complete,
paginated list is a **project-owner decision** (§19 D2).

## 13. Notification Impact — and the blocker

### The blocker, stated precisely

D5 requires **in-app only, no email**. The current contract cannot express it.

```php
final public function via(object $notifiable): array   // ← final
{
    $forced = $this->forcedChannels();                  // ← can only ADD

    foreach (NotificationChannel::cases() as $channel) {
        $allowed = in_array($channel, $forced, true)
            || $gate->allows($notifiable, $channel, $this->topic()->type());
        ...
    }
}
```

Three facts combine into the defect:

1. `via()` is **`final`** — a notification cannot override channel selection.
2. `forcedChannels()` **only adds**; its default is `[]` and there is no
   counterpart that removes.
3. Preferences are **opt-out** — an absent `notification_preferences` row means
   *enabled*, and the API states `default_enabled: true`.

**Therefore:** an `AnnouncementPublishedNotification` dispatched today would be
**emailed to every recipient who has not explicitly disabled email for the
`announcement` type** — which, on a fresh system, is everyone. That is precisely
the school-wide email blast D5 exists to prevent, and it would reach the whole
audience on the first publish.

Relying on the preference gate is **not** an acceptable substitute: it is a user
preference, not a system guarantee, and D5 is a system guarantee.

### The proposed remedy (WP-2.7c-1)

Add an `excludedChannels(): array` hook, default `[]`, consulted in `via()` with
**exclusion winning over both forced and preference-allowed**. `AnnouncementPublishedNotification`
returns `[NotificationChannel::Email]`.

This is small but sits in the hottest path in the notification system, which is
why it is its own sub-package, lands first, and is verified before anything
depends on it.

### Everything else is reuse

One new `NotificationTopic` case, one `type()` arm mapping it to
`NotificationType::Announcement`, one listener, one audience method. **The
WP-2.7b frontend needs no change.**

### Scale note — not a blocker

An `all` announcement fans out to every active user (dev: **21** — 4
administrators, 8 technicians, 9 teachers; production will be larger). The
dispatcher isolates per recipient and defers to `afterCommit`, but does not
chunk. Worth measuring before a large deployment; recorded as a risk (§17 R4),
not a blocker.

## 15. Testing Strategy

The current baseline must stay green: **backend 844** · **frontend 295** ·
**E2E 35** · **axe 24** · **2** a11y baseline entries.

### Backend
- `AnnouncementAuthorizationTest` — a dedicated file asserting **403 role by role** on every write endpoint, plus list and single-record-by-uuid for a non-administrator (the CLAUDE.md §6 IDOR rule).
- `AnnouncementLifecycleTest` — create, edit, publish/unpublish, pin, soft delete; the `ends_at > starts_at` constraint asserted at the **database** level with the constraint name.
- `AnnouncementValidationTest` — audience enum, window ordering, required fields.
- `AnnouncementNotificationTest` — publishing notifies exactly the audience; **asserts `Mail` was never sent**; re-publish does not duplicate; the actor is excluded if in-audience (owner decision D7).
- `ProjectNotificationChannelTest` — the three-way precedence: excluded beats forced beats preference.
- Existing `DashboardAnnouncementsTest` (6) must stay green.

### Frontend
- `AnnouncementForm` — validation, audience select from server metadata, window ordering surfaced as text.
- `AnnouncementList` (admin) — rows, empty, loading, error.
- Mutations — invalidation, rollback.

### E2E — all three roles
- **Administrator:** sign in → create → target `teachers` → publish → confirm it appears in the admin list.
- **Teacher:** receives the notification, sees it in the centre and on the dashboard.
- **Technician:** **does not** receive an announcement targeted at teachers — the audience-boundary assertion, proven in a browser.
- **Negative:** a technician and a teacher get 403 on the write API and the Forbidden page on the URL.

### Accessibility
- axe on `/app/announcements` and the create/edit surface as administrator; **no new baseline entries**.
