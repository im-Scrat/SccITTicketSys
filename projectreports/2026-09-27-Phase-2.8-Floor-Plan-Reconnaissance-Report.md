# ACTION — PHASE 2.8 FLOOR PLAN RECONNAISSANCE REPORT

## 1. Executive summary

The Interactive Floor Plan is **the most thoroughly pre-specified feature in this
project**. It was designed at bootstrap, baselined into all three controlled
documents, given a database schema that has been migrated since day one, given
seeded permissions and settings, given a sequence diagram, given a status enum
written specifically for it — and it is already **publicly promised on the shipped
marketing site**.

What does *not* exist is any of its code. The `FloorPlan` domain holds **0 PHP files
and 13 `.gitkeep` placeholders**. There are **zero** floor-plan tests. Laravel Reverb
is **not installed** in any form.

Phase 2.8 is therefore best understood as **wiring up existing preparation**, not
greenfield design. The requirements do not need to be invented; they need to be
recovered, and this report recovers them.

**Headline recommendation.** Deliver a genuinely interactive, persistent, accessible,
admin-only floor plan for the presentation using **SVG rendering + a polling
synchronisation channel**, and stage **Laravel Reverb as a post-presentation
upgrade**. Polling is not a shortcut invented here: **SDD DD-16 already specifies
"Reverb for real-time (P4) *with polling fallback* … degrade gracefully."** This
satisfies the observable behaviour of FR-FP-007 while avoiding four coupled
infrastructure changes four days before a client presentation.

| Question | Finding |
|---|---|
| Is the data model sufficient? | **Yes, completely.** No schema change is required for the core feature. |
| Is the authorization model ready? | **Yes.** `floorplan.view` / `floorplan.manage` are seeded and live. |
| Is Reverb ready? | **No. It does not exist** — no package, no config, no channels, no client. |
| Is real-time therefore blocked? | **No.** DD-16 approves a polling fallback. |
| Is there frontend preparation? | **Yes** — a working static `FloorPlanVisual.tsx` and a reserved feature seam. |
| Is there demo data? | **Yes** — 4 layouts and 20 positions are already in the dev database. |
| Largest schedule risk | Reverb's deployment surface, and the production image predating Phase 2.7. |
| Largest specification conflict | Admin-only. The **original client brief** says admin-only; **the SRS grants technicians `floorplan.view`**, and they hold it today. |

### 2.2 Why the schema looks like this — the recovered design history

`docs/database/database_architecture_report.md:47`, decision **D3**:

> Generalize locations: `laboratories` → `rooms` (with `room_type`); new `floors`
> between buildings and rooms; `laboratory_layouts` → `room_layouts` (+ `grid_size`,
> `version`, `is_active`); **positions moved off `pc_units` into
> `floor_plan_positions` (layout-scoped)** … makes the Interactive Floor Plan
> addable "without major refactoring."

The original review finding (`docs/database/database_design_review.md:163`, M4)
explains *why* positions are layout-scoped: *"Position currently lives on
`pc_units.pos_x/pos_y`, which breaks when a PC moves between rooms or when a room
has multiple/versioned layouts."* That is FR-FP-008 solved in the schema.

**A recommended constraint that was deliberately not implemented**
(`docs/database/database_design_review.md:268-269`):

> Coordinates within layout bounds: `pos_x BETWEEN 0 AND layout.width` (app-level if
> cross-table), `pos_y BETWEEN 0 AND layout.height`.

The shipped database enforces only `>= 0`. **Upper-bound containment is therefore
application-layer work that Phase 2.8 must do** — a recovered requirement, not a new
proposal.

   `connect-src 'self'`, with the inline comment *"there is no HMR socket here"*. It is
   covered by a regression test, `backend/tests/Feature/Security/ContentSecurityPolicyTest.php`,

4. **A production image rebuild** — code plus config/route/event caches are baked in.

## 8. Functional specification

### 8.1 Coordinate system

| Concern | Specification |
|---|---|
| Space | Layout-local pixels, origin top-left, matching `room_layouts.width/height`. |
| Storage | `decimal(10,2)` as migrated — exact, no floating-point drift. |
| Lower bound | `pos_x >= 0`, `pos_y >= 0` — already enforced by the DB CHECK. |
| Upper bound | `pos_x <= layout.width`, `pos_y <= layout.height` — **application-layer**, per the deferred design-review recommendation. |
| Snap | `round(v / grid_size) * grid_size`, then clamped to bounds **after** rounding. |
| Authority | **The server snaps and clamps.** The client's snap is a preview only. This matches the P4 diagram exactly. |
| Grid source | `room_layouts.grid_size` is authoritative per room; `floor_plan.default_grid_size` seeds new layouts; `floor_plan.snap_to_grid` is the default editor toggle, overridable per session. |
| Rotation / z-index | Columns exist and are persisted; **editing them is deferred** (see §13). |

### 8.2 Data model changes — two additive migrations, no destructive change

**Migration A — public route keys (required).** Add `uuid` to `room_layouts`
following the exact established pattern of

### 8.4 API design

All under the existing chain: `auth:sanctum` → `active` → `AuthenticateSession` →
`password.current` → `prefix('admin')` → `whereUuid([...])`.

| Method | Route | Gate |
|---|---|---|
| GET | `/admin/floor-plan/floors/{floor:uuid}` | `can:floorplan.manage` |
| GET | `/admin/floor-plan/rooms/{room:uuid}` | `can:floorplan.manage` |
| GET | `/admin/floor-plan/rooms/{room:uuid}/updates?since=<iso8601>` | `can:floorplan.manage` |
| POST | `/admin/floor-plan/rooms/{room:uuid}/layouts` | `can:floorplan.manage` |
| POST | `/admin/floor-plan/layouts/{layout:uuid}/activate` | `can:floorplan.manage` |
| PATCH | `/admin/floor-plan/layouts/{layout:uuid}/positions/{pcUnit:uuid}` | `can:floorplan.manage` |
| DELETE | `/admin/floor-plan/layouts/{layout:uuid}/positions/{pcUnit:uuid}` | `can:floorplan.manage` |

`PATCH` body: `{ pos_x, pos_y, rotation?, z_index?, expected_updated_at? }`. The
response returns the **server-snapped** position so the client reconciles to truth.

The `updates` endpoint is the DD-16 polling channel, and is deliberately shaped so its
payload is **identical to the future broadcast event** — the Reverb upgrade then swaps
only the transport.

*(Gating reads on `floorplan.manage` rather than `floorplan.view` is what makes the
feature admin-only without touching seeded permissions — see D2.)*

## 9. UX / UI and digital-twin interaction specification

**Render with inline SVG + React, adding no new dependency.** This is not a
compromise; it is the project's demonstrated instinct. Phase 2.4 rendered dashboard
distributions with *"no charting dependency, no colour-only encoding"*, and
`FloorPlanVisual.tsx` already renders this exact picture with hand-rolled positioned
nodes. At the real scale — **24 PC units total, ~5–20 per room** — a canvas library,
virtualization and WebGL are all premature. SVG additionally gives keyboard focus,
`aria-*` and text labels for free, which a `<canvas>` would have to reimplement to
satisfy FR-FP-009.

```
features/floor-plan/
  api/floorPlanApi.ts
  hooks/queries.ts       floorPlanKeys.{all,floor,room,updates}
  hooks/mutations.ts     useUpsertPosition — optimistic, rolled back on error,
                         reconciled to the server's snapped coordinates
  stores/useFloorPlanStore.ts   viewport (zoom/pan), selection, move-mode, snap
                                toggle — ephemeral only, never server truth
  components/  FloorPlanCanvas.tsx    <svg> viewBox pan/zoom, grid <pattern>
               PcNode.tsx             focusable node: colour + icon + label
               FloorPlanToolbar.tsx   zoom, fit, reset, snap toggle, grid size
               MovePanel.tsx          the non-drag placement control (FR-FP-009)
               PcInspectorPanel.tsx   FR-FP-005 details
               FloorPlanLegend.tsx    reuses StatusPill
  pages/FloorPlanPage.tsx
  types.ts
```

- **Zoom/pan** via the SVG `viewBox` — one attribute, no library, no layout thrash.
- **Grid** via `<pattern>`, sized from `layout.grid_size`.
- **Drag** via native pointer events with `setPointerCapture`; a drag preview carries
  a shadow, which the Flat-Plane Rule explicitly sanctions.
- **"Gamified" is interpreted as** a spatial, responsive, immediately-legible map with
  smooth movement, hover/focus affordances and clear state — **not** game mechanics,
  points or avatars. The asset data remains the source of truth.

**Wiring is three edits**, matching existing convention: a `lazy()` route in
`App.tsx` wrapped in `RequirePermission`; one `NAV_ITEMS` entry in
`layouts/AppLayout.tsx`; one route added to `e2e/specs/a11y.spec.ts`.

**Shell constraint:** `AppLayout` has no sidebar — horizontal sticky nav, and `<main>`
is full-bleed single-column, which suits a wide canvas.

## 10. Accessibility specification

Accessibility is why SVG was chosen, not a later polish pass. Targets `NFR-ACC-008`,
WCAG 2.2 **2.5.7 Dragging Movements**, **2.1.1 Keyboard**, **2.5.8 Target Size**.

- Every PC node is a focusable `<button>` in the tab order whose accessible name
  carries **identity + status + position** — e.g. *"PC-07, under maintenance, column
  4, row 2"*.
- **Move mode is the non-drag equivalent:** focus a node → `Enter`/`Space` enters move
  mode → arrow keys nudge **one grid cell** (`Shift`+arrow = one pixel) → `Enter`
  commits, `Escape` cancels and restores the original position.
- `MovePanel` provides numeric X/Y entry as a third, pointer-free path.
- A `role="status" aria-live="polite"` region announces each committed move, following
  the existing `UnreadAnnouncer.tsx` pattern.
- Status is **never colour-only**: colour + icon shape + text label (FR-FP-004,
  NFR-ACC-004, the `StatusPill` contract).
- Toolbar controls are real buttons with labels; zoom offers explicit +/−/Fit/Reset
  rather than wheel-only. Targets ≥ 44×44 px.
- The global `:focus-visible` 3px ring at 2px offset already applies
  (`frontend/src/index.css:253`).
- `usePrefersReducedMotion` suppresses node transitions (NFR-ACC-005).
- Room/floor navigation reuses the `LocationTree` precedent: *"a native nested list
  with `aria-expanded` buttons rather than a `treeitem` widget"*.

> **Inherited gap, reported not silently fixed:** `Drawer` and `Modal` implement no
> focus trap and no focus restore. The inspector panel should therefore be a
> **non-modal side region**, which sidesteps the gap and matches the WP-2.7b decision
> to make the notification panel non-modal.

## 11. Real-time synchronisation specification

**Presentation build — polling, under DD-16.**

`GET /admin/floor-plan/rooms/{room:uuid}/updates?since=<iso8601>` returns positions
and PC statuses changed since the timestamp. The client polls on a ~5 s interval,
paused while the tab is hidden and while a drag is in flight.

This satisfies FR-FP-007's observable behaviour — *Administrator B sees Administrator
A's move without refreshing* — with **zero new containers, zero nginx changes, zero
CSP changes**, and no risk to the production image.

| Concern | Handling |
|---|---|
| Authorization | The endpoint is gated identically to every other write path. |
| Ordering | Server `updated_at` is authoritative; the client applies by timestamp. |
| Duplicate events | Upsert semantics make re-application idempotent. |
| Stale clients | `since` is always the last successfully applied server timestamp. |
| Reconnect | Trivial — the next poll carries `since`; no session to re-establish. |
| Optimistic UI | Applied locally, then **reconciled to the server's snapped answer**. |
| Conflicts | Per D3 — recommended `expected_updated_at` → `409`. |

**Post-presentation — Reverb (`WP-4.1`).** Private channel
`private-floor-plan.room.{roomUuid}`, authorized in a new `routes/channels.php`
against the floor-plan permission. **Proxy Reverb through the same nginx origin** (for
example `/reverb`) to preserve the project's single-origin Sanctum architecture and
keep `connect-src 'self'` valid. Add the service to **both** compose files; rebuild
the production image; update the CSP regression test.

PostgreSQL remains the source of truth in both modes; Reverb is a transport.

## 12. Security model

- **Admin-only enforced in the backend**, not the UI: every route carries
  `can:floorplan.manage`, and each policy re-checks per record.
- **Route gate + policy + action** — the project's three-layer chain; `Gate::before`
  resolves permission strings, so an unregistered policy fails open. Registration in
  `AppServiceProvider` is mandatory.
- **Coordinate bounds validated server-side** against the layout's own
  `width`/`height` — the DB only guarantees `>= 0`.
- **Room-ownership validation:** the PC unit must already belong to the layout's room.
  This blocks cross-room reassignment through the position endpoint, which would
  otherwise be an asset-transfer path bypassing `assets.transfer`.
- **Active-layout requirement:** edits are accepted only against the room's active
  layout.
- **UUID route keys only** — numeric ids are never addressable (`NFR-SEC-001`,
  `AC-G2`), which is why Migration A exists.
- **Auditability:** every accepted move writes an `activity_logs` row with actor, IP,
  user agent and before/after coordinates.
- **CSRF/auth consistency:** inherits the existing Sanctum single-origin cookie flow
  and the `password.current` middleware already applied to every admin route.
- **IDOR:** per CLAUDE.md §6, a room absent from a user's list must be equally
  unreachable by direct UUID — asserted by test, not assumed.
