### Cleanup strategy — and my recommendation

```php
// Ordered to respect the foreign keys. Run inside one transaction.
$ids = User::whereIn('email', [
    'verify.admin@sccit.local', 'verify.tech@sccit.local', 'verify.teacher@sccit.local',
])->pluck('id');

DB::transaction(function () use ($ids) {
    $tickets = Ticket::whereIn('reporter_id', $ids)->pluck('id');
    DB::table('ticket_status_history')->whereIn('ticket_id', $tickets)->delete();
    DB::table('ticket_updates')->whereIn('ticket_id', $tickets)->delete();
    DB::table('technician_assignments')->whereIn('ticket_id', $tickets)->delete();
    Ticket::whereIn('id', $tickets)->forceDelete();
    DB::table('login_history')->whereIn('user_id', $ids)->delete();
    DB::table('activity_logs')->whereIn('user_id', $ids)->update(['user_id' => null]);
    User::whereIn('id', $ids)->forceDelete();
});
```

**`activity_logs` rows are nulled, not deleted** — the audit trail should record
that something happened even when the actor is removed, which is the stance the
rest of this system takes.

**Can cleanup safely occur before deployment?** *Yes — and I recommend after,
not before.* These accounts are the only way to exercise the three roles against
production. Deleting them first removes the means of verifying the deployment
that is about to happen. The safe order is: **deploy → verify with the verify.\*
accounts → then clean up.**

**No cleanup has been performed. It is not covered by this release
authorization and needs your explicit approval.**
