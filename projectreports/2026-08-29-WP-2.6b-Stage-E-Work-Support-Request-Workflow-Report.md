## 1. A schema discrepancy you should see first

§11 of the authorization listed the fields to use. Five of those names do not
exist in the approved Stage A schema. Rather than add columns — §19 says preserve
it exactly — Stage E used the real ones. The mapping, verified against the live
database:

| §11 named | What exists | Why |
|---|---|---|
| `decision_note` | `decline_reason`, `reschedule_reason`, `clarification_reason` | **Three purpose-specific notes, not one.** FR-WSR-004 forbids overwriting a prior decision in place; one shared note column would be overwritten by the next decision, which is exactly what the requirement rules out. A request asked about face-to-face *and then* declined keeps both. |
| `required_by` | `rescheduled_to` (+ `proposed_meeting_at`) | The schema models the **administrator's answer** ("work goes ahead on this date"), which is what FR-WSR-006 asks for. There is no technician-supplied deadline field in DR-020. |
| `requested_item` | the `work_support_request_items` **table** | FR-WSR-002 requires "one or more line items", so items are rows — a catalogue model *or* free text, quantity > 0, both database-enforced. A single column could not hold a list. |
| `reason` | `explanation` | The technician's written justification. NOT NULL with a non-blank CHECK. |
| `created_by` | `technician_id` | A support request is always opened by the technician it belongs to, so Stage A deliberately did not add a second column — it would only be somewhere for the two to disagree, and `technician_id` is the row-scope column FR-WSR-009 depends on. |

**No second schema was created, no table duplicated, no alternate model
introduced.** If any of these names was meant literally rather than as a
paraphrase, say so and it becomes a schema change to authorize.

## 4. Technician workflow

```
scan → authorized panel → "Can't finish this job?" → items + explanation (+ evidence)
     → submitted → track on "My requests" → acknowledge a new date, or withdraw
```

The request is bound to the **scanned machine**, and to the maintenance job when
one is unambiguous. FR-WSR-001 explicitly permits a request with no job, so a
technician reachable through a ticket assignment alone can still raise one — a
live-verified path.

## 5. Administrator workflow

| Decision | Endpoint | Requires | Effects |
|---|---|---|---|
| **A — Approve & reschedule** | `/approve` | `rescheduled_to` | `status=approved`, `decided_by`, `decided_at`; pushes the date onto the linked maintenance record **preserving the previous value in the audit**; moves a linked ticket to `on-hold` where the WP-2.6 map permits it |
| **B — Face-to-face** | `/request-clarification` | `clarification_reason` | `status=clarification_requested`; **`decided_by`/`decided_at` deliberately not written** — asking to talk is not a decision, and stamping them would make the request look settled to the inbox's own filter |
| **C — Decline** | `/decline` | `decline_reason` **mandatory** | `status=declined`, `decided_by`, `decided_at`, reason |

Plus `/close` to conclude a decided request.

**The decline reason is refused in three independent places** (DR-020): the
FormRequest (`required|min:5`), the lifecycle service (re-trimmed and re-asserted
for callers that are not HTTP), and the database's own CHECK. A test proves the
third by bypassing the application entirely and asserting the constraint name.

## 6. Decision-state transitions

```
submitted ──────► clarification_requested   (admin)
    │                     │
    ├──► approved ◄───────┤                 (admin)
    ├──► declined ◄───────┤                 (admin)
    └──► cancelled ◄──────┘                 (submitter OR admin)

approved ──► closed        declined ──► closed        (admin)
cancelled ──► ✗            closed ──► ✗               (terminal)
```

The map carries **who** as well as **what** — `TicketLifecycle`'s shape, which
Maintenance did not need. `submitted → cancelled` is legitimate for the
submitting technician; `submitted → approved` is an administrator's alone.

**No decision is ever replaced.** `approved` and `declined` reach only `closed`,
so a second decision is refused by the map rather than overwriting the first.
Each transition re-reads its row `FOR UPDATE` and re-asserts state *inside* the
transaction, so two administrators seconds apart produce one decision and one
clean 422 — verified by test.

**Acknowledgement is not a status.** It sets `acknowledged_at` on an approved
request and is idempotent; a second acknowledgement writes no second audit row.

## 8. IDOR verification

**Nothing the client sends identifies anything.** `technician_id`,
`created_by`, `pc_unit_id` and `ticket_id` are derived server-side and there is
no field to supply them — so the forgery tests assert that sending them
**changes nothing**, which is stronger than rejecting them.

| Attack | Result |
|---|---|
| Forged `technician_id` / `created_by` in the body | Ignored; caller recorded |
| Forged `pc_unit` / `pc_unit_id` in the body | Ignored; scanned machine used |
| Another technician's `maintenance_id` | **422** |
| A maintenance record on another machine | **422** |
| A completed / cancelled maintenance record | **422** |
| An invented uuid vs a real forbidden one | **byte-identical error bodies** |
| Another technician's request by uuid | **403**, and absent from the list |
| Administrator inbox as a technician | **403** |
| Technician deciding their **own** request | **403** — the self-approval an unguarded workflow eventually permits |
| Technician cancelling / acknowledging another's | **403** |
| Teacher, any endpoint | **403** · unauthenticated: **401** |
| Revoked label | **403**, and the response does not contain the unit code |

The load-bearing assertion is the pair: a request absent from a technician's
**list** is refused **by uuid** as well. Both directions, one test.

## 9. Auditability

`activity_logs` only — **no parallel audit table**, the DD-55 stance restated.
Seven new `ActivityAction` verbs, one per transition, so the timeline reads as
the sequence of decisions it was and a reader can filter for declines without
parsing properties. (No migration needed: `activity_logs.action` carries no
CHECK constraint — verified against the live schema.)

Every transition writes its row **inside the same transaction** as the change,
carrying `from`, `to`, the actor, and the superseded values of anything that
moved — including `previous_scheduled_for` when an approval reschedules a job.
That is what makes FR-WSR-004's "recoverable from the request's history" true
without a second table. A test asserts the exact four-verb sequence of a
submit → clarify → decline → close.

## 10. Frontend

Impeccable was loaded this session; `context.mjs` run, `PRODUCT.md` and
`DESIGN.md` read, the product register followed, the existing design system
inspected before any component was written.

**Decisions.** One card component for both surfaces — the roles differ in which
**rows** they reach, not in what a request looks like, and two cards would have
been two places to add a field and one to forget the decline reason. The raise
form is **collapsed behind a button** on the scan panel, below proof of work,
because they are different moments: proof is what you submit when the job is
done, a support request is what you submit when it cannot be. Item rows take
**free text first** — a technician needs to ask for a part the catalogue never
carried, and a mandatory picker would block exactly the requests that matter.
Three decision **buttons and dialogs, never a status dropdown**, because the API
has no endpoint a dropdown could call.

**States**: loading (skeletons in the page's own shape), empty (which teaches
the flow rather than saying "nothing here"), error (the server's own sentence
relayed), success. Both nav items are permission-gated, and the inbox
additionally role-gated (FR-WSR-009/010 each ask for a dedicated item).

2. **FR-WSR-013 — procurement linkage is not implemented.** The column
   (`procurement_request_id`) exists and stays null. §21 excludes scope
   expansion and §14 lists only the three decisions, so bridging to
   `procurement_requests` is left to a later stage. Recorded, not forgotten.

3. **OD-9's automatic close is not implemented.** An administrator may close
   explicitly. The plan also proposed auto-closing when the linked maintenance
   record completes; that would mean reaching into `MaintenanceLifecycle`, which
   Stage D delivered and you approved as it stands. **Still an open decision.**

4. **FR-WSR-012 (notifications) deferred by instruction.** No notification code,
   no email, no fake behaviour. The lifecycle emits one distinct audited event
   per transition, which is the seam a notification layer attaches to cleanly.

5. **A linked ticket in `open` is left unchanged** on approval, and the audit
   records `ticket_hold: skipped_no_legal_transition` with the status. This is
   approved decision OD-2: the WP-2.6 map has no `open → on-hold` edge, and
   adding one would change a shipped, verified map.

6. **Two pre-existing flakes remain untouched**, as instructed:
   `AssetDirectoryTest` and `LocationArchiveTest`, both random-factory
   collisions in Phase 2.4/2.5 code. Neither recurred in the runs above.

7. **Accessibility and browser verification deferred** (§10), per §4 of the
   authorization.
