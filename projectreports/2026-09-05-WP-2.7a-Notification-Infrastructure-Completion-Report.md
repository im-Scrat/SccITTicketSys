# WP-2.7a — Notification Infrastructure — Completion Report

---

## 1. Executive summary

WP-2.7a delivers the backend notification infrastructure Phase 2.7 was gated
on: the project database channel driver ([DD-52](#)), a preference gate, a
failure-isolated dispatcher, a recipient-resolution service, an authorization
boundary with its API, and **ten of the twelve** FR-NOT-003 triggers wired to
the existing domain write paths.

Three things are worth stating plainly at the top.

**The schema was already there.** `notifications` and `notification_preferences`
were baselined in the Phase-1 data layer, with the cascade foreign keys and the
`notifications_unread` partial index the badge count needs. This work package
added **one column** — `notifications.dedupe_key` — and one partial unique index
behind it. No table was created; no baselined column was reshaped.

**The debt WP-2.6b booked against itself is paid.** FR-WSR-012 — notify the
Administrators when a technician raises a work support request, and notify the
technician on every decision — shipped without a channel to deliver on. Both
halves now work end to end and are covered by tests that drive the real HTTP
endpoints.

**Two triggers remain unsatisfied, and are named rather than glossed.** T7
(low-stock reorder) and T8 (procurement approval/rejection) depend on
`consumables` and `procurement_requests`, which have baselined tables and no
domain code. **Phase 2.7 therefore cannot claim FR-NOT-003 as fully satisfied**;
it satisfies ten of twelve. A unit test asserts their absence so the gap cannot
close by accident.

Two owner decisions were requested and given before implementation began (T3
comment recipients, T4 SLA recipients); no recipient was invented.

**Classification: GREEN — complete and ready for WP-2.7b.**

## 4. Architecture

New domain `App\Domains\Administration\`, following the existing domain shape.

```
Administration/
  Notifications/
    ProjectNotification.php          abstract base — via(), toMail(), dedupeKey()
    Channels/DatabaseChannel.php     the DD-52 driver
  Services/
    NotificationPreferences.php      the opt-out gate (FR-NOT-002)
    NotificationAudience.php         recipient resolution and filtering
    NotificationDispatcher.php       the failure-isolation boundary
  Listeners/                         nine listeners — the FR-NOT-003 matrix in code
  Policies/NotificationPolicy.php    ownership, and nothing else
  Http/{Controllers,Requests,Resources}/
  Providers/NotificationServiceProvider.php
```

Notification **classes** live with the domain that raises them
(`Tickets/Notifications/`, `Maintenance/Notifications/`,
`WorkSupport/Notifications/`, `Identity/Notifications/`), following the existing
`Domains/Identity/Notifications/` precedent. **Listeners** live in
`Administration` so that "who is told what, and what may it contain" has one
folder to audit — which is the security review this work package had to pass.

### The four load-bearing decisions

**1. A project `database` channel, registered over the framework's name
(DD-52).** Laravel's stock `DatabaseChannel` writes a morph with a uuid primary
key and a class-name `type`; this project's `notifications` table has a direct
`user_id`, a bigint key with a separate public uuid, and a `type` constrained by
CHECK to nine values. The driver is replaced, not the schema.

**2. `NotificationTopic` is separate from `NotificationType`.** The type column
is fixed at nine values by a CHECK constraint and is the *display and
preference* vocabulary; the topic is the *trigger identity*, one case per matrix
row. Collapsing them would mean widening a baselined constraint no requirement
asks to widen, or losing the ability to tell three maintenance triggers apart.
The topic is PHP-only and travels in `notifications.data.topic`.

**3. Failure isolation is a property of the dispatcher, not of each caller.**
See §7.

**4. Idempotency is enforced by the database.** See §5 and §7.

## 7. Queue / Redis behaviour

The existing infrastructure was used; none was added. `QUEUE_CONNECTION=redis`,
dedicated `queue` worker containers in **both** stacks
(`--tries=3 --backoff=5 --max-time=3600`), `scheduler` containers running
`schedule:work`.

**What is queued.** All notification delivery. `ShouldQueue` sits on the base
class, so no subclass can accidentally send inline on the request thread.

**What is synchronous.** Recipient resolution and the preference lookup — both
are indexed reads, and doing them at dispatch means a notification routed
nowhere never becomes a job at all.

### The guarantee

> Nothing about notifying anybody may change the outcome of the thing that
> caused the notification.

Three mechanisms, in order:

1. **`DB::afterCommit()`.** Delivery runs immediately when no transaction is
   open, defers to commit when one is, and is **dropped on rollback**. The
   try/catch lives *inside* that callback, which is what makes the isolation
   hold in both cases — the notification's own `$afterCommit` flag alone would
   surface a failure in Laravel's commit callback, outside any handler of ours,
   and turn a successful write into an error response.
2. **Per-recipient isolation.** One `send()` per recipient, so one person's
   failure cannot silently truncate the list for everybody after them.
3. **A synchronous in-app fallback.** If the queue push fails — Redis
   unreachable, the realistic outage — the in-app row is written directly
   through the same channel and the same idempotency key, and a warning is
   logged. The notification centre keeps working while the queue is down; only
   email is lost. **The fallback still respects the preference gate**: an outage
   is not licence to write into a centre a user asked to be kept out of.

**Retry behaviour.** Three attempts, five-second backoff — the existing worker
configuration, unchanged.

**Idempotency and duplicate prevention.** `notifications.dedupe_key` is
generated **at dispatch** and serialized into the job, so every retry of one
dispatch carries the same key and Postgres refuses the second insert
(SQLSTATE 23505, caught and treated as already-delivered). Two *separate*
dispatches produce two rows, correctly. Scheduled detectors override the key
with a semantic one:

| Trigger | Key | Effect |
|---|---|---|
| T1 | `ticket.assigned:{assignment id}` | one hand-off, one notification |
| T3 | `ticket.commented:{comment uuid}` | one comment, one announcement |
| T4 | `ticket.sla_threshold:{ticket}:{stage}` — **no date** | each of four crossings announced **once in a ticket's life**, however often the hourly sweep runs |
| T5b | `maintenance.due:{record}:{overdue}:{date}` | one reminder per record per day, plus one on the day it tips into overdue |
| T6 | `maintenance.rescheduled:{record}:{new date}` | a second genuine move is news; a retry of the same move is not |
| T10 | `work_support.decided:{request}:{decision}` | a clarification and the decision that follows it are two answers |

**The insert is wrapped in its own transaction**, which on Postgres is not
decoration: a unique violation aborts the *enclosing* transaction (SQLSTATE
25P02), so catching 23505 without isolating the insert would leave the caller
holding a connection on which nothing else can run. `DB::transaction()` opens a
SAVEPOINT when one is already in progress.

**Observability.** Queue failures are `report()`ed; the synchronous fallback
logs a warning naming the topic and the recipient uuid.

**No new infrastructure** — no Horizon, no dedicated queue, no outbox table.
The residual exposure an outbox would close is a notification lost only if the
queue push *and* the synchronous fallback both fail, which means Redis and
Postgres are both unavailable — at which point the business action did not
happen either.

## 8. Authorization and security

### The boundary

A notification belongs to **exactly one person**. Every query is scoped on
`user_id`; `NotificationPolicy` re-asserts the same rule per record. The list
rule and the single-record rule are therefore the same rule — the DD-40
property, so a notification absent from someone's list is unreachable by its
uuid.

**There is deliberately no administrator override.** Every other module opens
completely for an administrator. A notification is not work — it is a message
addressed to a person, carrying material drawn from tickets, machines and
colleagues' requests — so an administrator reading another user's list would be
a second, unaudited route into records the first route scopes carefully. No
requirement asks for it.

**No `notifications.*` permission was invented.** The Client's §8.4 matrix has
no notification module, and OD-4 set the precedent in WP-2.6b. Ownership is the
whole rule.

### The content rule

> **A notification carries structural facts. Free text a person typed is never
> copied into one.**

Structural facts are ticket numbers, statuses, priorities, machine codes and
dates. Excluded everywhere: comment bodies, transition remarks, technicians'
explanations, administrators' decline and clarification reasons, and the names
of other people.

The rule is deliberately broader than "redact what this recipient may not see",
because that version needs a per-field, per-role judgement at every trigger and
is wrong the first time somebody adds a trigger without making it. Each of the
following is asserted **against the stored payload**, so a field cannot leak
back in through a later change to the resource:

| Check | Result |
|---|---|
| Transition remarks never reach the reporter | ✅ |
| The technician who moved a ticket is never named to a teacher | ✅ |
| Comment bodies reach nobody | ✅ |
| A teacher is never told an internal note exists | ✅ |
| The reporter is never named to the assignee | ✅ |
| No `cost` / `labor_hours` in any maintenance notification | ✅ |
| The technician's explanation is not copied to administrators | ✅ |
| The decline reason is not copied to the technician | ✅ |
| Lockout notices carry the duration, never the IP, user agent or attempt count | ✅ |
| `action_url` is always a relative `/app/…` path — never absolute (FR-QR-011) | ✅ |
| `dedupe_key`, `user_id` and internal ids never leave the application | ✅ |

**Email is narrower than in-app by construction.** `mailLines()` defaults to the
notification's own title; a subclass may add lines it composed itself from
structural facts, and none adds user-authored text. That is what makes
FR-NOT-006's "safe for external delivery" checkable rather than a judgement call
per message.

**The one forced channel.** `AccountLocked` forces email past the preference
gate, because a locked-out user cannot sign in to read an in-app message and a
security notice a user silenced six months ago is a security notice that does
not exist. Nothing else forces anything — asserted by test.

**Enumeration.** Notifications are addressed by uuid only; a numeric id is a
404. Another user's notification is a 403 with no body. No endpoint accepts a
user identifier, so there is nothing to tamper with on the preferences path.

**Audit.** No `activity_logs` rows are written for notifications. The business
events that cause them are already audited by the existing write paths, and the
`notifications` row is itself the durable record of what was said to whom. A
second entry per notification would double the audit volume without adding a
fact.

**Existing authorization was not weakened.** No policy, visibility service,
permission or transition map was modified.

## 16. Known limitations

1. **A notification can be lost if Redis and Postgres are both unavailable.**
   The queue push fails, the synchronous in-app fallback fails, and the failure
   is reported rather than replayed. A durable outbox table would close this and
   was declined as a new entity for a window in which the business action did
   not happen either. **The application stays correct**; the notification is
   simply not written.

2. **Email is lost, not queued, during a Redis outage.** The fallback writes the
   in-app row only. Mail has no synchronous path, because sending it inline is
   exactly the request-blocking behaviour the queue exists to prevent.

3. **The nine-value `type` enum cannot distinguish triggers for preference
   purposes.** A user silencing `maintenance` email silences due reminders,
   reschedules *and* work-support decisions together. This is a property of the
   baselined schema, not of the implementation; `NotificationTopic` preserves
   the distinction for display and grouping, and a finer preference grain would
   need the CHECK widened.

4. **T3 "followed" means demonstrated participation, not subscription.** There
   is no follow/unfollow control, so a person cannot leave a conversation they
   commented on once, other than by silencing `ticket_update`. This was your
   chosen option; a follower entity remains available later.

5. **Prior-commenter resolution scans at most the 200 most recent comments** on
   a ticket, bounding fan-out on a long thread. The distinct author set is far
   smaller in practice, and the most recent commenters are the ones still
   watching.

6. **`tickets:detect-sla` runs hourly, so a breach is announced within the hour
   rather than at the instant.** Announcing at the instant would need a
   per-ticket scheduled job or Reverb; FR-TKT-017 asks for detection and
   notification, not for real time.

7. **The queue worker has not been exercised against a real Redis queue in this
   work package.** Tests run with `QUEUE_CONNECTION=sync`, which proves the
   delivery path and the failure isolation but not the worker's serialization of
   these particular jobs. The `queue` containers are running in both stacks with
   the same `--tries=3 --backoff=5` configuration every other queued job would
   use. First real exercise comes at deployment.

8. **Nothing is deployed.** Production runs the pre-WP-2.7d image, has 30
   migrations, and has no `Administration` domain. Every result in this report
   is from development and test.

### Two defects were found and fixed inside this work package

Both were introduced by WP-2.7a and never left the working tree. They are
recorded because each was a *silent* failure of exactly the kind this layer must
not have.

- **Recipients arriving without a `status` column were dropped, with no error
  and no log line.** `maintenance:detect-due` eager-loads
  `technician:id,uuid,first_name,last_name`, so the model had no `status`
  attribute and the filter read the missing value as "not active" — the sweep
  reported the overdue visit on the console and notified nobody.
  `NotificationAudience::isActive()` now treats a missing attribute as *unknown*
  and answers with one indexed existence check. Two regression tests hold it.

- **A top-level `data` key in the resource suppressed Laravel's own `data`
  wrapper**, so a single notification came back unwrapped while a list came back
  wrapped — two shapes for one resource. The jsonb column is now exposed as
  `payload`. WP-2.7b would otherwise have discovered this itself.

**Two things WP-2.7b should know before starting.**

The preference model is **opt-out**: an absent row means *enabled*. The API

screen that assumes "no row means off" is not.

`message` and `action_url`; treat `payload` as supplementary and always
optional.
