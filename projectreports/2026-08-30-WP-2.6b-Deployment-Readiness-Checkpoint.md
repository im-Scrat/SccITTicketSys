### 3.3 Idempotency — the honest answer

Neither migration is *internally* idempotent (re-running `up()` by hand would
fail on a duplicate column or table). **That is normal and correct**: Laravel's
`migrations` table provides idempotency at the runner level, and each migration
records its batch on success. The relevant guarantee — *running `php artisan
migrate` twice is safe* — holds.

**Both are safe to run.** Combined operational risk: **low**. Both are additive,
both have working rollbacks, and the only table they modify is empty in
production.

## 7. Proposed deployment procedure — **PLAN ONLY, NOT EXECUTED**

**Every command must carry `-p sccit_prod -f compose.prod.yaml`.** Omitting it
silently targets the development stack — CLAUDE.md flags this as a mistake that
has already bitten this project.

> **Gap found:** **no script in `scripts/` targets production.** All eleven
> (`backup.sh`, `migrate.sh`, `up.sh`, `down.sh`, `restore.sh`, `fresh.sh`,
> `test.sh`, the two verify scripts) use bare `docker compose` and therefore hit
> **dev**. In particular **`scripts/backup.sh` would back up the wrong
> database.** Step 1 below is written out explicitly for that reason. This is
> an operational gap, not a code defect, and no script was modified.

**1 — Backup (explicit, not the script)**
```
docker compose -p sccit_prod -f compose.prod.yaml exec -T postgres_prod \
  sh -lc 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' | gzip > backups/prod-preWP26b-<ts>.sql.gz
```
Verify the archive is non-empty and gunzip-readable before continuing.

**2 — Confirm image digests** match §5.1 exactly.

**3 — Deploy both together**
```
docker compose -p sccit_prod -f compose.prod.yaml up -d app_prod nginx_prod queue_prod scheduler_prod
```
`queue_prod` and `scheduler_prod` share `sccit/app:prod` and must be recreated in
the same step, or they keep running the old code.

**4 — Apply migrations 28 → 30**
```
docker compose -p sccit_prod -f compose.prod.yaml exec -T app_prod php artisan migrate --force
```
Expect exactly two migrations, ending at 30.

**5 — Caches** — automatic. `prod-entrypoint.sh` rebuilds config/route/event
caches on container start; no manual `optimize` is needed or wanted.

**6 — Service health** — all of `app_prod`, `nginx_prod`, `postgres_prod`,
`redis_prod` report healthy; `queue_prod` and `scheduler_prod` running.

**7 — Database connectivity** — `php artisan migrate:status` returns 30 Ran.

**8 — Health check** — `curl -sS -o /dev/null -w '%{http_code}' http://localhost:8081/up` → `200`.

**9 — Smoke tests** — §8.

**10 — Rollback decision point** — after step 9. Roll back if `/up` fails, any
smoke test in the "must pass" column fails, or migrations error.

**11 — Rollback procedure**
```
# a. revert code: recreate containers from the previous image
docker tag <previous app digest> sccit/app:prod
docker tag <previous web digest> sccit/web:prod
docker compose -p sccit_prod -f compose.prod.yaml up -d app_prod nginx_prod queue_prod scheduler_prod

# b. revert schema (only if needed — see below)
docker compose -p sccit_prod -f compose.prod.yaml exec -T app_prod php artisan migrate:rollback --step=1 --force
```
**Record the current digests before deploying** — `81180836…` for the running
app image — or the tag-based rollback has nothing to point at.

**Rollback is genuinely possible**, with one nuance worth stating: both
migrations have working `down()` methods, and rolling them back destroys only
data created *by* WP-2.6b (the three WorkSupport tables and two `qr_scan_logs`
columns). Since production holds **zero** rows in all of them today, **rollback
is presently lossless.** That stops being true the moment real support requests
are filed.
