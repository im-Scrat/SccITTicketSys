**There is deliberately no route-level `can:` gate on the panel.** No permission

## 3. Exact authorization flow

```
GET /api/qr/{code}/panel
  → auth:sanctum          unauthenticated → 401
  → active                suspended account → 403
  → AuthenticateSession
  → password.current      forced reset pending → 403
  → QrScanResolver::resolve(code)            server-side; no client claim accepted
  → ScannedPcAccess::hasFloor(user)          false → 403 {reason: not_authorized}   [flat, non-disclosing]
  → outcome->isSuccess()                     false → 403 {reason: label_inactive | label_unknown}
  → outcome->pcUnit() !== null               null  → 403 {reason: no_workflow}
  → authorize('viewScanned', $pcUnit)        false → 403                            [THE control]
  → loadPanel() with scoped relations
  → ScannedPcUnitResource
```

The floor is checked **before** the classification is disclosed, so a caller
without maintenance entitlement receives one flat refusal for an unknown code, a
revoked code and a real code alike — the Stage B non-disclosure rule restated on
this endpoint because it is reachable on its own.

**No `qr_scan_logs` row is written by the panel.** The scan was logged at
`/scan`; logging the panel read too would double-count one physical event.

## 4. Exact reachability predicate

`ScannedPcAccess::scope()` — the whole rule, in one place:

```
Administrator (role slug)                        → every machine, unrestricted
Otherwise:
  floor:  maintenance.view  OR  tickets.update   → false ⇒ no machines at all
  AND at least one of:
    (a) an OPEN maintenance record on this pc_unit that is the caller's own
        · statuses: MaintenanceVisibility::OPEN_STATUSES (scheduled, in_progress, on_hold)
        · ownership: MaintenanceVisibility::scopeOwn()  ← delegated, not restated
    (b) an OPEN ticket on this pc_unit the caller is ACTIVELY assigned to
        · ticket_statuses.is_open = true
        · TicketVisibility::scopeAssigned(..., WRITABLE_ASSIGNMENT_STATUSES)  ← delegated
```

### One predicate, three uses

| Use | Implementation |
|---|---|
| **Authorization** | `PcUnitPolicy::viewScanned()` → `ScannedPcAccess::canReach()` |
| **Single-record access** | `canReach()` = `scope(PcUnit::query(), $user)->whereKey($id)->exists()` |
| **List / query scope** | `scope()`, `scopeRelevantMaintenance()`, `scopeRelevantTickets()` |

`canReach()` **does not re-implement** the rule for one record — it runs the same
query narrowed to one key. There is no second implementation that could drift.
That equivalence is asserted directly by a test that iterates four machines and
requires `canReach()` to agree with `scope()` for every one.

### Two deliberate decisions

- **Delegation, not restatement.** "Work I own" is already defined
  authoritatively by `MaintenanceVisibility::scopeOwn()` (FR-MNT-011) and
  `TicketVisibility::scopeAssigned()`. Both are **called**, never copied — a third
  definition of ownership that disagreed with its own module would be an IDOR.
- **Active assignment, not merely readable.** `READABLE_ASSIGNMENT_STATUSES`
  keeps a *completed* job readable on the ticket page because a technician needs
  their history. The panel is an on-site working surface, so it uses
  `WRITABLE_ASSIGNMENT_STATUSES` — finishing the job ends the entitlement to
  stand at the machine. Tested both ways.

### Not an `assets.*` check

`hasFloor()` reads `maintenance.view` / `tickets.update` only. A Technician holds
no asset permission whatsoever (DD-38, SRS §8.4); gating on `assets.view` would
either lock out every technician or force a grant that reopens the whole Asset
module (FR-AST-013).

Three issues arose during the stage and were fixed:

1. **Type error** — eager-load constraint closures receive a `Relation`, not an
   `Eloquent\Builder`. Fixed by passing `$query->getQuery()` rather than widening
   the service signature, so the scoping methods stay strictly typed and are the

   also guarantees JSON arrays rather than objects.

   introduced by a scripted edit. Both auto-fixed.

## 10. Stage B test fixtures updated — behaviour change, reported

Stage C replaced the interim `mayProceed()` seam with the final rule, and **10
Stage B tests failed as a direct result**. This is a correct tightening, not a
regression, and it is reported rather than quietly patched.

**What changed:** on `POST /api/qr/{code}/scan`, a technician who clears the
permission floor but has **no work on the scanned machine** previously received
`next: panel`. They now receive `403 {reason: not_reachable}`.

That is the approved final rule (FR-QR-012, AC-QR-012). The Stage B tests
encoded the interim seam by giving the technician no work at all.

**Fix applied:** the `beforeEach` in `QrScanTest`, `QrScanLoggingTest` and
`QrRateLimitTest` now creates a genuine open maintenance record for the
technician on the machine under test, so those files continue to test
*classification, logging and throttling* rather than authorization by accident.
**No Stage B production code was changed** beyond the seam replacement Stage C
was required to make.

## 12. Judgment calls flagged for the Client

**`brand` and `model` are included.** FR-QR-012's approved list names "the
relevant technical specification"; brand and model are ordinarily part of that,
and a technician sourcing a power supply needs to know it is a Dell. They are not
administrator-only data — no price, no supplier, no warranty. **OD-7 did not
name them either way.** Say the word and they come out.

Everything OD-7 *did* name — serial number, asset tag, hostname, IP, MAC — is
excluded, and `notes` was excluded on the same reasoning.
