The frontend notification experience is implemented, tested and committed. No

---

## 1. Implementation summary

WP-2.7b builds the surface that WP-2.7a's API was written for. Three things
now exist that did not before:

| Surface | Route | What it is |
|---|---|---|
| **Notification centre** | `/app/notifications` | The full history, with unread and type filters, server-side pagination, and read/unread controls |
| **Header entry** | every authenticated screen | A bell in the top-bar utility cluster with an unread badge and a dropdown panel |
| **Preference matrix** | `/app/account` | The channel × type grid (2 × 9 = 18 cells today), saved in one batched request |

The panel and the page share **one data layer and one row component**. The
panel is a different container around the same list, not a second
implementation, so the two cannot disagree about what a notification is or
what marking one read does.

### The six Client decisions, as built

| # | Decision | Realised as |
|---|---|---|
| **Q1** | Option A — 18 cells now, no digest | The matrix is generated from `meta.channels` × `meta.types`. No `digest` enum case, no CHECK-constraint change, no migration. It widens on its own when a channel is added. |
| **Q2** | Panel **and** page | `NotificationMenu` (bell + panel) and `NotificationsPage`, both on `useNotifications` / `useUnreadCount` and both rendering `NotificationRow`. |
| **Q3** | Flat list | Reverse-chronological, exactly as the server orders it. No day grouping, and no client-side re-sorting. |
| **Q4** | 60s poll, visible tab only | `UNREAD_POLL_INTERVAL_MS = 60_000`, with `refetchIntervalInBackground` left at its default of `false` — which is what confines the poll to a visible tab — plus a local `refetchOnWindowFocus: true` override, because returning to the tab is when a person looks at the badge. |
| **Q5** | `/app/account` | `PreferenceMatrix` renders below the existing name and password cards. |
| **Q6** | Drive real workflows | The E2E suite performs an actual ticket conversation each run. `sccit:e2e-fixtures` was **not** modified. |

### Three decisions worth recording

**The badge is Signal Blue, not red.** DESIGN.md's *Reserved-Red Rule* makes red
mean destructive, critical or offline and nothing else, so the conventional red
notification dot is banned by this project's own design system. The badge is
absent at zero (an always-lit indicator means nothing), caps at `99+` so the
header cannot reflow, and states its count in the button's **accessible name** —
a visual badge is invisible to a screen reader.

**The panel does not trap focus.** It renders on every authenticated screen in
the product, so a focus trap here would be a focus trap everywhere. It is a
non-modal disclosure: `Escape` closes it and returns focus to the bell, tabbing
out closes it behind you, and a pointer-down outside dismisses it.

**`action_url` is validated before it is followed.** It is server-built today,
but it is *stored data*, and treating stored data as a trusted destination is
how open redirects happen. Requiring the literal `/app/` prefix refuses an
absolute URL, a protocol-relative `//host` payload, a `javascript:` scheme and
any path outside the application in one rule — FR-QR-011's discipline applied to
a second surface.

### The one real finding, and what was done about it

The proposal asked to *"verify this explicitly"*. Verified — and it was **not**
true. `useLogout` cleared only the principal and the `registrations` key.
TanStack Query keeps cached data after a query's observers unmount, so on a
shared machine the previous user's inbox would render from cache for as long as
the refetch took. Notifications are the most personal thing this client caches.

`useLogout` now calls `removeQueries({ queryKey: notificationKeys.all })`,
following the existing `registrations` precedent. It is asserted **through a
browser**, not only in a unit test: the E2E signs out through the application's
own control (not by clearing cookies, which would end the session without ever
running the eviction) and confirms the technician's assignment is absent for the
teacher who signs in next.

**35 passed / 35** in a single run (24.0m): the 27 pre-existing tests plus 8 new.

| Role | Flow |
|---|---|
| Administrator | badge → panel → centre → mark all read (answering the >20 confirmation when it appears) → badge clears → follow the notification → preference change persists across a reload |
| Administrator | the lockout security email is disabled and explained |
| Technician | assignment notification → open the ticket → unread filter drops it → All shows it as "Read." → restore to unread |
| Technician | type filtering through the server |
| Teacher | sees status and **exactly two** comment notifications from two public comments and one internal note |
| Teacher | cannot reach the technician's notification by uuid — **403** on `GET`, `PATCH …/read` and `PATCH …/unread` |
| Teacher | reaches the centre and preferences with no permission |
| Session | signing out through the UI clears the cached inbox before the next principal renders |

Notifications are produced by driving a **real ticket conversation** each run —
a teacher reports a fault, an administrator assigns it, the technician comments,
the administrator adds an internal note. That proves the whole chain: an event
fires, a listener resolves an audience, a preference gate lets it through, a row
is written, an endpoint scopes it to its owner, and a browser renders it. A
seeded row would prove only the last step.

**Two test defects were found and fixed during the gate**, both mine and both
data-dependence rather than application faults: the administrator test first
assumed "Mark all as read" would act immediately (it correctly asks above twenty
unread), then assumed something would be unread when the previous run had
cleared the backlog. The bulk action now runs *before* the single one, so there
is always something for it to do.

## 13. Known limitations

1. **The forced-cell rule is mirrored, not published.** `AccountLocked` declares
   `forcedChannels() === [Email]` server-side, but the preferences endpoint does
   not say which cells are forced — so `PreferenceMatrix` carries a
   `FORCED_CELLS` constant that duplicates it. The alternative was a checkbox
   that accepts a click the server then ignores, which is worse because it lies
   about what it did. **Mirrors drift**: if another notification declares a
   forced channel, this constant must be updated with it. The proper fix is for
   the API to publish it in `meta` — a backend change, so it is reported here
   rather than made.

2. **The badge can be up to 60 seconds stale.** By design (Q4). It is a poll,
   not a live feed, and nothing in the UI claims otherwise.

3. **The panel does not fetch until it is opened.** Deliberate — this component
   renders on every authenticated screen, so the badge is the standing cost and
   a twenty-row list is not. The first open is therefore a request, not instant.

4. **The E2E suite accumulates data.** Each run creates one ticket and its
   conversation on the dev stack. Consistent with how the existing QR suite
   behaves, and the reason the assertions key on the run's own ticket number.

5. **Reported, not touched (CLAUDE.md §8):** `useLogout` still leaves *other*
   features' cached data in place after sign-out — tickets, maintenance, assets.
   Notifications were in WP-2.7b's scope and are fixed; the rest is a
   pre-existing condition and a wider decision than this work package.

6. **`useUiStore` remains dead scaffolding**, as the proposal noted. Still
   holding `sidebarOpen` for a sidebar removed in Phase 2.5. Untouched.
