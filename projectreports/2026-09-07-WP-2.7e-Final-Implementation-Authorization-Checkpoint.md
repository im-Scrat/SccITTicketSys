## 1. The crash-window decision closes the last open item

**OPTION (i) — AT-MOST-ONCE DELIVERY** is recorded as the authoritative policy:

| Clause | Recorded |
|---|---|
| 1 | Claim `(user_id, digest_date)` atomically in PostgreSQL |
| 2 | Mark committed/sent **before** the SMTP send |
| 3 | Once claimed as sent, never sent again for that user/date |
| 4 | A crash after DB confirmation but before/during SMTP delivery **may miss** that digest |
| 5 | Never retry a digest already marked sent |
| 6 | Handled failures **before** commit remain retryable |
| 7 | The `(user_id, digest_date)` unique constraint is the authoritative idempotency mechanism |
| 8 | Redis scheduler locks are concurrency protection only |

**Accepted guarantee: at-most-once.** A digest may be missed in the irreducible
crash window; a successful digest is never duplicated for the same
`(user_id, digest_date)`.

This is internally consistent and fully determines the implementation. Two
consequences follow directly from clauses 2, 5 and 6, and are recorded here so
they are decided rather than discovered:

**(a) SMTP failures are not retryable.** Because the record is committed *before*
the send (clause 2), an SMTP failure occurs *after* commit, so clause 5 forbids a
retry. Clause 6's "failures before the digest is committed" therefore scopes to
claim conflicts, query errors, rendering errors and eligibility checks — not to
transport errors. That is the deliberate cost of at-most-once, and it matches
clause 4.

**(b) `sent_at` records commitment, not delivery.** Under this policy `sent_at` is
stamped before SMTP is contacted, so it is evidence that the system *committed to
sending*, not proof the message arrived. The documentation must say so plainly;
recording it as "delivered" would be a claim the mechanism cannot support.

Neither point requires a further decision.

## 5. Verification of the window boundaries

Re-confirmed in both PostgreSQL and PHP/Carbon, which agree exactly. For a
digest delivered **2026-09-08 07:00 Asia/Manila** summarising **2026-09-07**:

```
window start   2026-09-07T00:00:00+08:00  =  2026-09-06T16:00:00Z   inclusive
window end     2026-09-08T00:00:00+08:00  =  2026-09-07T16:00:00Z   exclusive
delivery       2026-09-08T07:00:00+08:00  =  2026-09-07T23:00:00Z
digest_date    2026-09-07                 the day summarised, not the delivery day
```

The summarised day closes seven hours before delivery. `Asia/Manila` is UTC+8
with no DST, so these offsets hold year-round.
