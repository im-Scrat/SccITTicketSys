## 3. Database release state

Read-only throughout. **No migration was run and production was not altered.**

| | Repository / dev / test | Production |
|---|---|---|
| Migration files | 32 | **30** |
| Applied (`migrations` table) | 32 | **30** |

**The two outstanding migrations**

| | Migration 31 — WP-2.7a | Migration 32 — WP-2.7e |
|---|---|---|
| File | `2026_09_05_100000_add_dedupe_key_to_notifications.php` | `2026_09_07_100000_add_digest_channel_and_digest_log.php` |
| Batch (dev) | 6 | 7 |
| Tables | `notifications` | `notification_preferences`, `notification_digests` |
| Change | Nullable `dedupe_key`; partial unique index `(user_id, dedupe_key) WHERE dedupe_key IS NOT NULL` | Widens the channel CHECK to add `digest`; creates `notification_digests` with `UNIQUE (user_id, digest_date)`, FK → `users` cascade |
| Additive / destructive | Additive / no | Additive / no |
| `down()` | Drops index, drops column (loses `dedupe_key`) | Drops table, deletes `digest` preference rows, restores the two-value domain — **tested against a live `digest` row** |

**Ordering and dependencies.** Filename order applies 31 before 32. They touch
**disjoint tables**, so no dependency exists between them and the order is safe
either way — Laravel's is deterministic.

**Production-schema compatibility, verified directly.** Production already has
`notifications` and `notification_preferences`; `notification_digests` does not
exist; the channel CHECK is still the two-value domain. Both migrations would
therefore apply cleanly to a schema that already matches their expectations.

**Existing production data compatibility — the decisive finding.** Production's
`notifications` and `notification_preferences` both hold **zero rows**. So:
adding a nullable column and a partial index involves no backfill and no lock
contention; dropping and re-adding a CHECK revalidates nothing; creating a table
is unconditioned. It also means DD-63's `down()` data-loss hazard has **nothing
to delete** in production today.

**A safety property worth recording.** `php artisan migrate --pretend` inside
the production container returned **"Command cancelled"** — Laravel's production
confirmation guard refused to proceed without an interactive confirmation.
Nothing executed, and production's `migrations` table still reads 30. Accidental
migration of production is guarded by the framework, not only by process.

**A distinction that matters for the gate.** Production is not "two migrations
pending" — the two files are **absent from the production image** (30 files
inside the container against 32 in the repository). The release is therefore an
**image rebuild followed by migration**, not a bare `migrate`. `deploy-prod.sh`,
`rollback-prod.sh` and `releases.sh` (WP-2.7d) are the tooling for exactly that.

### Conclusion

**The 30 → 32 transition is appropriate for one controlled Phase 2.7 release.**

It is also unavoidable: Laravel applies all pending migrations in filename order
within a single `migrate`, so releasing WP-2.7e necessarily applies WP-2.7a
first. Separating them would require withholding a migration file from an image,
leaving repository and production diverged in a way no tooling tracks. The two
are safe together — disjoint tables, both additive, both against empty
production tables.
