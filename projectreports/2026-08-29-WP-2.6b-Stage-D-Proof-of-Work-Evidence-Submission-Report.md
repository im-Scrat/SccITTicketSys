## 1. The rule Stage D implements

The Client's flow, restated as the four things that must independently hold
before a byte is written:

```
QR scan                    identifies the machine — and nothing else
→ authenticated technician identifies the person
→ authorized access        PcUnitPolicy::viewScanned  (Stage C, unchanged)
→ explicit job selection   MaintenanceVisibility::canWork (the module's own rule)
→ proof submitted          evidence through the single attachment boundary
→ completion               MaintenanceLifecycle — gates unchanged, not re-implemented
```

The load-bearing property: **the scan never appears in any authorization
decision.** A caller holding a perfectly valid code and a perfectly valid scan
identifier for a machine they have stopped working on is refused, and the tests
below make every refusal while holding both.

## 3. Routes and endpoints added

```
GET  api/qr/{code}/work    QrProofOfWorkController@index
POST api/qr/{code}/proof   QrProofOfWorkController@store
```

Middleware on both:
`api → auth:sanctum → EnsureAccountIsActive → AuthenticateSession → password.current → can:maintenance.update`,
plus `throttle:qr-proof` on the POST. `code` is constrained to
`[A-Za-z0-9-]{1,64}` at the route.

**Why `can:maintenance.update` here when the Stage C panel deliberately has no
route gate.** Attaching evidence and moving a record *is* a maintenance write,
and this is the identical floor the module's own evidence route carries. It
remains a floor, never the control: *which machine* is `viewScanned`, *whose
record* is `canWork`.

**The rate limiter is an addition beyond the literal Stage D scope**, and is
flagged as such. One limit, per account only — the endpoint is authenticated, so
there is no anonymous sweep to resist and an IP ceiling would ration a whole
school behind one address. It bounds file uploads under a retrying client.

## 4. The proof-of-work lifecycle

```
POST /api/qr/{code}/proof
  { scan_id, maintenance_id?, resolution, diagnosis?, outcome, evidence[], evidence_type }

  route      can:maintenance.update                    -> 403
  request    shape only; file rules from AttachmentSecurity -> 422
  controller resolve code server-side                   -> 403 label_unknown / label_inactive / no_workflow
             hasFloor                                   -> 403 not_authorized
             authorize('viewScanned', $pcUnit)          -> 403
             resolve the scan (yours, this machine, success) -> 422 scan_id

  DB::transaction:
    L3  SELECT ... FOR UPDATE on qr_scan_logs
    L4  pg_advisory_xact_lock(machine, technician)
    1.  resolve the target  (replay | named | single | refuse-to-guess | create)
    2.  attach evidence via AttachRepairImage (PROFILE_MAINTENANCE), deduplicated
    3.  assert the record carries evidence               -> 422 evidence
    4.  scheduled -> in_progress via MaintenanceLifecycle (started_at, PC effect)
    5.  resolution/diagnosis/root_cause via UpdateMaintenanceRecord (audited diff)
    6.  outcome via MaintenanceLifecycle::transition      -> 422 status (gates)
    L2  bind qr_scan_logs.maintenance_record_id, once
    7.  ActivityAction::MaintenanceProofSubmitted, carrying the scan uuid
```

**No completion logic exists in Stage D.** A submission may *ask* to complete;
`MaintenanceLifecycle` decides, and its gates — required checklist items, a
resolution, evidence for non-preventive types — are the same wall the
maintenance module's own button hits. Test §8 proves that by hitting the
checklist gate from the scanned path and getting the module's own refusal.

**Why a scheduled record is started first.** Proof of work asserts work
happened. Moving it through the lifecycle stamps `started_at` once and puts the
machine into `under_maintenance` with its previous status remembered — exactly
as pressing Start in the maintenance module would. Writing `in_progress`
directly would skip both effects and the audit row with them.

## 5. Maintenance-record selection — "do not guess"

| Situation | Behaviour |
|---|---|
| Scan already bound to a record | **Replay.** Re-target that record; re-check `canWork` from scratch. |
| Replay naming a *different* record | **422.** One scan describes one job. |
| `maintenance_id` supplied | Resolved **through** the scoped query; unknown / another technician's / another machine's / closed all give the **same** 422. |
| Exactly one workable job | Used. Not a guess — there is one answer. |
| More than one | **422 with the candidates attached.** The server does not choose. |
| None, and the caller holds `maintenance.create` | A corrective record is opened, linked to the originating ticket **when that is unambiguous**. |
| None, and the caller does not | **422, and nothing is created** (AC-MNT-009). |

`ScannedWorkTargets` composes rather than defines:

- **Which rows** — `ScannedPcAccess::scopeRelevantMaintenance()`, the identical
  call the Stage C panel renders from. A job the panel did not show can never be
  submitted against.
- **May this actor write** — `MaintenanceVisibility::canWork()`, the identical
  call the maintenance module makes for its own edit, checklist and evidence
  paths.

`find()` is `scope()` narrowed by uuid, exactly as `ScannedPcAccess::canReach()`
is `scope()` narrowed by key — so a record absent from the chooser is unreachable
by pasting its identifier. **Verified by grep: `technician_id` and `created_by`
appear nowhere in Stage D's code.** Ownership is called, never copied.

## 6. Authorization model

| Question | Answered by | Where |
|---|---|---|
| May you do maintenance at all? | `can:maintenance.update` | route + FormRequest |
| Is the label usable? | `QrScanResolver` | controller |
| Do you work on **this machine**? | `PcUnitPolicy::viewScanned` → `ScannedPcAccess` | controller (Stage C, unchanged) |
| Is this scan **yours**, for this machine, and successful? | `QrScanLog` lookup on four conditions | controller |
| May you write **this record**? | `MaintenanceVisibility::canWork()` | inside the transaction |
| May it be completed? | `MaintenanceLifecycle` | inside the transaction |

The scan appears in exactly one of these, and only as *"is this identifier
yours"* — never as an entitlement. A held scan identifier does not survive the
work it was issued for: test §8 shows a technician's replay refused at the
machine gate once their only job on it is finished.

## 7. Attachment security — reused, not re-created

`AttachRepairImage` with `AttachmentSecurity::PROFILE_MAINTENANCE`, called
unchanged. Stage D introduces **no second upload path**, which FR-MNT-010
forbids outright.

Preserved and verified live: server-side `finfo` MIME detection · allow-list
re-check inside the action · SHA-256 checksum · file size · original filename
kept as data · server-composed storage path · private `local` disk · re-checked
type and safe disposition on download.

`evidence.*` validation rules are **built from
`AttachmentSecurity::rules(PROFILE_MAINTENANCE)`**, never restated, so the
profile stays the single place a type is added or removed.

### A correction worth recording

The first version of the "never trusts the client MIME type" test used
`UploadedFile::fake()->create('payload.jpg', 8, 'image/jpeg')` **and passed for
the wrong reason** — Laravel's testing fake returns its constructed mime type
from `getMimeType()` as well as `getClientMimeType()`, so a faked file can never
disagree with its own declaration. The test now uses a **real** `UploadedFile`
over a file whose bytes are not an image, and fails if the server ever believes
the client. Any future maintainer copying the fake pattern should know it proves
nothing.

## 8. Idempotency — six layers, and what each actually enforces

| Layer | Mechanism | Enforced by |
|---|---|---|
| **L1** | `qr_scan_logs.uuid` as the client's handle on a physical scan | Schema |
| **L2** | `qr_scan_logs.maintenance_record_id` — **one nullable FK, set once** | **Column cardinality — structural** |
| **L3** | `SELECT … FOR UPDATE` on the scan row for the whole transaction | **Database row lock** |
| **L4** | `pg_advisory_xact_lock(machine, technician)` around resolve-or-create | **Database advisory lock** |
| **L4b** | Evidence deduplicated on (record, SHA-256, stage) | Application, under lock |
| **L5** | `MaintenanceLifecycle::transition()` no-ops on an unchanged status | Existing WP-2.6 code |

**L4 is new relative to the plan and closes a race the plan acknowledged as
residual**: two *different* scans of the same label seconds apart, both finding
no record and both creating one. L3 locks different rows in that case and would
not serialize them. The advisory lock is transaction-scoped, so it releases at
commit or rollback with nothing to leak and no cleanup path to forget.

**A unique index on "one open record per machine" is deliberately not the
mechanism.** `ConcurrentMaintenanceFinder` records the WP-2.6 Client decision
that a machine may legitimately carry a scheduled preventive visit and an active
corrective repair at once. L2 and L4 give the database-enforced guarantee where
it is well posed — per scan, and per machine-and-technician — without
contradicting that decision.

## 9. Concurrency — what was tested, and what honestly could not be

**Tested directly.** The submission is watched with `DB::listen()` and asserted
to emit both `pg_advisory_xact_lock` and a `for update` against `qr_scan_logs`.
Atomicity is asserted separately: a submission that fails at the evidence gate
after taking the create branch leaves **no record, no binding and no evidence**.

**Not simulated, and deliberately not faked.** Laravel wraps each test in one
transaction, so a second connection cannot see the first's uncommitted rows — a
"concurrent" test would be theatre. What a genuine race resolves to is covered
by the sequential replay tests, which exercise the same code path the loser of a
race takes: it reads the binding the winner wrote and replays onto it.

This is stated plainly rather than reported as a passing concurrency test.

## 12. Frontend

Impeccable was loaded and its product-register reference followed. `PRODUCT.md`
and `DESIGN.md` both exist; the existing design system was read before any
component was written.

**Design decisions, and why.**

- **The scene**: a technician crouched beside a lab PC, phone in one hand, poor
  light, one thumb free. That forced mobile-first, the largest type in the
  product on the unit code, and `capture="environment"` so the camera opens
  directly instead of a file browser.
- **No new visual vocabulary.** Every control is an existing component
  (`Surface`, `Button`, `Field`, `Select`, `Textarea`, `Alert`, `Skeleton`) on
  existing tokens. The product register's rule is consistency over novelty, and
  a scan surface that looked like a different product would fail it.
- **One column, not a card grid.** Identity → the form → reference detail.
  Putting the specification above the form would put reference material between
  someone and the task they came to do.
- **No decorative motion.** Product register: motion conveys state only. The
  submit button has a loading state; the confirmation replaces the form in place.
- **A refusal is the page, not a strip on it** — it gets the room to say why and
  what to do instead, and it never names the equipment the server withheld.

**States shipped**: loading (skeletons in the page's own shape, not a spinner),
error (field-level, plus the lifecycle's own blocked-completion sentence relayed
verbatim), empty ("nothing to record against", which explains rather than
offering a form the server would certainly reject), and success (which
distinguishes *attached* / *opened* / *replayed*, and reports deduplicated
photographs so silence never reads as loss).

### Accessibility

Verified by test through the accessibility tree — every query in
`ProofOfWorkForm.test.tsx` is by role and accessible name, so the suite passes
only if a keyboard and screen-reader user reach the same controls a mouse user
does. Also: `fieldset`/`legend` grouping for the photograph and outcome
questions, `aria-describedby` on the evidence hint, `aria-invalid` on errored
controls, `role="status"` on the confirmation, `sr-only` text carrying checklist
state that colour alone would otherwise convey, visible `focus-visible` rings,
and controls at 48–60 px — the design system's existing floor, comfortably above
44 px.

**Honest limits.** No automated axe/WCAG scan was run: `axe-core` is not a
dependency of this project and adding one is outside Stage D's scope. **No
browser rendering or screenshot verification was performed** — no browser
automation is available in this environment. Contrast is inherited from the
committed token system rather than re-measured for these screens.

### A scope note the Client should see

Stage D's frontend necessarily included the **scan-flow UI** (`/qr/:code`, the
sign-in resume, `/app/qr/:code`), which the original plan listed as its own
sub-work-package **D**, sitting before proof of work. There was no QR frontend
of any kind before this stage, so a proof-of-work form had no surface to live
on. It was kept to the minimum that makes Stage D usable and nothing beyond it.

### FR-QR-011 — the open-redirect defence

`pendingScan.ts` stores a **code, never a path**, and `resumePath()` is the only
function that builds a destination — by composition into a fixed relative
template. Fifteen unit tests assert it discards absolute URLs,
protocol-relative paths, `javascript:`, `data:`, traversal, app paths,
over-long values, and a poisoned value written directly into `sessionStorage` by
something else on the origin.

## 16. Remaining known issues

1. **A second pre-existing flake, found and not fixed.** The full suite failed
   once on `LocationArchiveTest > it cascades a floor archive to its rooms` with
   `duplicate key … floors_building_id_floor_number_unique`. Root cause:
   `FloorFactory` picks `floor_number` from `1..10` at random and the test
   creates **two floors in the same building** — a 1-in-10 collision, structurally
   identical to the known `AssetDirectoryTest` flake. It passed 3/3 on re-run,
   and the final clean full-suite run reported in §10 did not reproduce it. It is
   **Phase 2.4 code, entirely unrelated to Stage D**. Reported, not repaired, per
   the standing instruction not to expand scope into unrelated phases.

   **A methodology note worth recording.** Two intermediate runs reported
   failures that were **not real**: a background full-suite run overlapped
   foreground per-file runs against the same test database, and the contention
   produced spurious errors. Every figure in §10 comes from a serialized run with
   nothing else touching the database. Never trust a Pest result from this
   project taken while another run is in flight.

2. **A rate limiter beyond the literal scope.** `qr-proof`, 12/minute per
   account. Flagged in §3; say the word and it comes out.

3. **Scan identifiers have no time-to-live.** A scan id stays quotable for as
   long as the caller still passes every authorization check. No FR asks for an
   expiry, and adding one would be inventing a business rule — recorded as a
   considered non-decision rather than an oversight.

4. **No browser-rendered or automated-accessibility verification** (§12).

5. **`WorkSupportStatus` and the `work_support_requests` tables from Stage A
   remain unused** — they are Stage E's, as planned.

6. Carried forward: production parity and the image rebuild; the SRS/SDD/SPMP
   reconciliation for WP-2.6b; the `AssetDirectoryTest` flake.
