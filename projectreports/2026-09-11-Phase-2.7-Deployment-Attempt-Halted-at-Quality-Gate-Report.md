## 4. Failure analysis — both re-run individually

Neither failure was accepted at face value; each was reproduced in isolation.

### backend: Pest — **contention artifact, not a regression**

```
Tests:    945 passed (3709 assertions)
Duration: 505.97s
exit=0
```

Run alone, the backend suite passes completely. `scripts/gates.sh` runs Pest and
Vitest within one sequence, and `sccit_node` was observed at **555% CPU** while
the backend suite was executing. This is the hazard recorded in project memory as
*"Pest runs must be serialized — one shared test DB; concurrent runs fabricate
failures that look like real regressions."*

**Not a Phase 2.7 defect.**

### frontend: Vitest — **the documented pre-existing flake**

```
FAIL  src/test/app.test.tsx > public routing > renders the landing hero and sections on /
FAIL  src/test/app.test.tsx > public routing > renders the sign-in entry on /sign-in
Test Files  1 failed | 34 passed (35)
     Tests  2 failed | 311 passed (313)
```

This fails **consistently**, not intermittently, in the current environment. It
is WP-2.7d's **F-5**, and it is **proven not to be a Phase 2.7 defect**: during
the Phase 2.7 final verification every WP-2.7e frontend change was stashed and
the suite re-run at `HEAD`, reproducing the identical two failures. Every line
WP-2.7e changed under `frontend/src` is a comment or a test title.

The Client classified this at the WP-2.7c closure:

> *"Treat the `app.test.tsx` landing-hero timeout as **PRE-EXISTING
> NON-BLOCKING TECHNICAL DEBT**. Do not modify its timeout. Do not weaken the
> test. Do not include it as a WP-2.7e defect."*

**Not a Phase 2.7 defect, and not permitted to be fixed.**

## 6. Why the deployment was not retried

Three paths exist, and only one is mine to take.

**Retry unchanged — unlikely to succeed.** Pest would probably pass on a quieter
run, but the frontend flake currently reproduces reliably. A retry would most
likely consume another ~25 minutes and fail again at the same gate.

**Fix the flake — explicitly forbidden.** The remedy is to raise the
`app.test.tsx` timeout, which the Client has twice instructed must not be done.

**`--skip-gates` — available, but an owner decision.** The script supports it and
warns plainly (*"the gates were NOT run for this release"*), writing
`verification.gates: "skipped"` into `releases/6cd219e/manifest.json` — a
permanent record that the first production release bypassed its gate. The
deployment authorization also said **"DO NOT improvise"** on failure. Choosing to
skip a production quality gate is not a judgement to make unilaterally.

## 8. Recommendation

**Deploy with `--skip-gates`.**

The justification is unusually strong. Every gate has been run manually against
this exact commit and passes, with the sole exception of a flake the Client has
twice classified as non-blocking and forbidden from being fixed. Blocking a
verified release on it would mean the release can never deploy while that
instruction stands.

If authorized, the deployment report will record explicitly that the script-level
gate was skipped and that each gate was verified independently, with the §5
evidence — so the manifest's `"skipped"` value is never read as *unverified*.

**Alternatives, if you prefer not to skip:**

- Authorize raising the `app.test.tsx` timeout — this reverses an earlier
  instruction and would let the gate pass honestly.
- Retry unchanged and accept the likely repeat failure.
- Defer the deployment until the flake is addressed as separate technical-debt
  work.
