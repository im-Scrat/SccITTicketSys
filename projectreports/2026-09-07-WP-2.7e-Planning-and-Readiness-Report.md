# WP-2.7e PLANNING & READINESS REPORT

## 1. Executive summary

WP-2.7e is genuinely unbuilt, and the recovered design (D1 / DD-63) is sound in
its core choice: **a digest is a delivery *channel*, not a tenth notification
type.** The schema delta is one widened CHECK constraint on a table that a proven
project precedent already shows how to migrate.

Reconnaissance nonetheless found **four things the design record does not
currently say**, one of which is a correction to DD-63 rather than an addition.

| # | Finding | Impact |
|---|---|---|
| A | DD-63 understates its own first hazard. Because the preference gate is **opt-out**, adding the `Digest` enum case would throw `UnhandledMatchError` on essentially **every notification to every user immediately** — not "on the first digest-enabled user". | Correction to DD-63 |
| B | DD-63's implied fix ("`via()` must gain a `digest` arm") is the **wrong shape**. Mapping `Digest` to a Laravel channel would attempt per-notification digest delivery, contradicting "a digest aggregates unread rows, it does not create one". | Design correction |
| C | **Digest idempotency has nowhere to live.** DD-63 leaves `notifications` untouched and the digest writes no row, so the existing `dedupe_key` mechanism cannot record "user X already received 2026-09-08's digest". | Design gap — owner decision |
| D | An undocumented **`notifications.digest_enabled` system setting** already exists, seeded to `false`. Neither D1, DD-63, the SRS nor the SPMP mentions it. | Owner decision |

Plus the single largest undefined requirement: **"daily" has no defined
timezone.** The application runs **UTC**, `system_settings` carries
`system.timezone = "Asia/Manila"`, and there is **no per-user timezone column**.

**Classification: YELLOW** — planning is complete and no blocker was found, but
**eight Project Owner decisions** (§21) must be settled before implementation can
begin without guessing.

## 3. FR-NOT-008 requirements

SRS §22, verbatim:

> **FR-NOT-008** — Support a daily digest email aggregating unread items,
> selected per user as a **delivery channel** on `notification_preferences`
> (`channel = 'digest'`) rather than as a notification type.
> *Class M · Rel P2 · Ver T*

Status block: *not implemented*. The SRS also records a correction worth
carrying forward — an earlier wording named a column
`notifications.digest_enabled`, and **that column has never existed**. (It is
not a column. It *is* a system setting — finding **D**.)

SRS **UCS-10** alternate flow *A1*: "a daily digest email aggregates unread
items (FR-NOT-008)."

What FR-NOT-008 fixes: it is an **email**, it aggregates **unread** items, it is
**per-user opt-in via a channel preference**, and it is **daily**. What it does
not fix: when "daily" is, in which timezone, what happens when nothing is
unread, what content each entry carries, or how repeats are prevented.

## 4. DD-63 design recovery

SDD §40, verbatim intent:

> **D1 — the daily digest is a delivery *channel*, not a tenth notification
> type. Approved 2026-09-05; NOT implemented.** `notification_preferences.channel`
> widens from `('in_app','email')` to `('in_app','email','digest')`;
> `notifications` and `notifications_type_check` are untouched.

Rationale recovered: a digest is *how* a user is reached, not *what* they are
told. Modelling it as a type would have required widening two CHECK constraints
and "inventing a notification that is about other notifications". As a channel it
needs **one** constraint widened.

DD-63 records two hazards before the work starts. Both were checked against
current code, and both need amendment:

**Hazard 1 — `via()` must handle the new channel.** *Confirmed live, and more
severe than stated.* `ProjectNotification::via()` is `final` and iterates
`NotificationChannel::cases()`, ending in an exhaustive
`match ($channel) { InApp => 'database', Email => 'mail' }`. DD-63 says an
exhaustive match without a digest arm "throws on the first digest-enabled user".
In fact `NotificationPreferences::allows()` returns
`matrixFor($user)->get($key, true)` — **default true**. With no preference rows,
digest is *enabled for everyone by default*, so the loop reaches the `match` for
every recipient and throws `\UnhandledMatchError` on **the first notification of
any kind to any user**. This is a total outage of the notification system, not a
narrow failure.

**Hazard 1b — and the obvious fix is wrong.** Adding `Digest => 'digest'` to the
match would route each notification to a digest channel at dispatch time, which
directly contradicts "a digest aggregates unread rows, it does not create one".
The correct shape is the opposite: **`Digest` must be excluded from the
per-notification dispatch loop entirely** — `via()` answers "where does *this*
notification go now", and the answer for digest is "nowhere now". The channel
exists only as a *preference selector* read later by the scheduled command. This
is the same conceptual move WP-2.7c's `excludedChannels()` made, and the
implementation is a one-line skip in the loop rather than a match arm.

**Hazard 2 — `down()` will fail once anyone opts in.** *Confirmed valid.*
Re-narrowing the CHECK re-validates the table, and a `digest` row violates it. The
rollback must delete `channel = 'digest'` rows **before** restoring the narrower
constraint. §6 shows the project already has a proven precedent for exactly this.

**Hazard 3 — a stale premise, newly observed.** DD-63 argues the constraint is
widened "on a table holding zero rows". That is **no longer true**:
`notification_preferences` now holds **1 row in dev** (`channel = 'email'`),
created through WP-2.7b's preference screen. Production still holds **0**.
Widening remains safe regardless — the new domain is a superset — but the
premise as written has drifted and the rollback hazard is now live rather than
theoretical.

## 5. Existing notification architecture

Verified through Graphify, codebase-memory-mcp and direct reads.

| Component | Role | Digest relevance |
|---|---|---|
| `NotificationChannel` (enum) | `in_app`, `email` | Gains `Digest` |
| `NotificationType` (enum) | nine values, matching `notifications_type_check` | **Untouched** |
| `NotificationTopic` (enum) | twelve trigger identities | **Untouched** — a digest is not a trigger |
| `ProjectNotification::via()` | `final`; exclusion → forced → gate → channel map | Must **skip** `Digest` (§4) |
| `ProjectNotification::excludedChannels()` | DD-66 refusal hook | Precedent for the skip; may be reusable |
| `NotificationPreferences::allows()/matrix()` | opt-out gate; absent row = enabled | Grows to 3 × 9 = 27 cells |
| `NotificationDispatcher::send()` | `afterCommit`, per-recipient isolation (DD-59), actor exclusion | **Not used** by the digest — it sends no notification |
| `notifications.dedupe_key` | per-user idempotency (DD-60) | **Unusable** for digest — no row is written (finding C) |
| `NotificationPolicy` | no admin override (DD-62) | Digest inherits self-only access |
| DD-61 structural-facts rule | titles yes, quoted prose no | **Digest must list titles, never `message`** |

The last row is a derived constraint, not an invention: `mailLines()`'s default
deliberately excludes `payload['message']` because "that is where quoted human
text lives and that is exactly what must not be mailed". A digest that listed
messages would breach DD-61 and FR-NOT-006.

**No parallel notification system is needed or proposed.** The digest reads the
existing `notifications` table and the existing preference gate.

## 6. Database impact

**Current state, read directly from the live schema:**

```
notification_preferences
  id, user_id, channel varchar(255), notification_type varchar(255),
  is_enabled boolean default true, created_at, updated_at
  UNIQUE (user_id, channel, notification_type)  -- notification_preferences_unique
  INDEX (user_id)
  CHECK notification_preferences_channel_check
        channel IN ('in_app','email')
  CHECK notification_preferences_notification_type_check
        notification_type IN (9 values)
  FK user_id -> users(id) ON DELETE CASCADE
```

`notifications` already carries everything a digest query needs and requires **no
change**: the partial index `notifications_unread btree (user_id) WHERE read_at
IS NULL` and `notifications_user_id_created_at_index (user_id, created_at)` serve
"this user's unread rows in a window" directly.

**Exact schema delta required:**

1. `NotificationChannel` gains `case Digest = 'digest';`
2. One migration replacing `notification_preferences_channel_check` with the
   three-value domain. **Nothing else.**

**Migration characterisation:**

| Property | Assessment |
|---|---|
| **Additive** | Yes — every previously legal value stays legal; the domain is a strict superset |
| **Destructive** | No — no column renamed, retyped or dropped; no data rewritten |
| **Reversible** | Yes, **but only with a data step**. `down()` must `DELETE FROM notification_preferences WHERE channel = 'digest'` before restoring the two-value CHECK, or the re-validation fails (DD-63 hazard 2) |
| **Idempotent under Laravel semantics** | Yes for `up()` — `DROP CONSTRAINT IF EXISTS` then `ADD CONSTRAINT` is safe to re-run. Laravel's `migrations` table prevents double-application anyway |
| **Compatible with existing rows** | Yes — dev holds 1 row (`email`), prod 0; both satisfy the widened domain |
| **Compatible with current production state** | Yes for the constraint itself; see §14 for the deployment coupling |

**A proven precedent exists in this repository.**
`2026_08_26_100000_extend_asset_status_domain.php` widens enum CHECK domains with
exactly the needed technique — `DROP CONSTRAINT IF EXISTS` + `ADD CONSTRAINT …
CHECK (col IN (…))`, driven from the PHP enum's `::values()`, with a `down()`
that **normalises offending rows first**. WP-2.7e should follow it rather than
invent a new pattern; it is the same DD-18/DD-32 technique that motivated the
"PHP-enum-mirrored CHECK" design in the first place.

## 7. Scheduler / queue impact

**Scheduler.** Defined in `backend/routes/console.php` (Laravel 11+ style, no
`Kernel`), executed by a **dedicated `scheduler` container** running
`php artisan schedule:work` in **both** the dev and production stacks
(`sccit_scheduler`, `sccit_prod_scheduler`). No host cron is involved.

Existing entries, and the house style WP-2.7e should match:

| Command | Cadence | Guards |
|---|---|---|
| `tickets:close-stale` | `dailyAt('02:15')` | `withoutOverlapping()`, `onOneServer()` |
| `maintenance:detect-due` | `dailyAt('06:30')` | `withoutOverlapping()`, `onOneServer()` |
| `tickets:detect-sla` | `hourly()` | `withoutOverlapping()`, `onOneServer()` |

WP-2.7e needs **one new entry** and one new Artisan command. `onOneServer()`
requires a shared lock store — `cache.default = redis`, so this is satisfied.

**Note on `dailyAt()`:** it resolves against the scheduler's configured timezone,
which is `config('app.timezone')` = **UTC** unless `->timezone(...)` is given.
See §9.

**Queue.** `queue.default = redis`; the `queue` / `queue_prod` containers run
`queue:work --tries=3 --backoff=5 --max-time=3600 --sleep=3`. **No queue
change is required** — the existing worker and retry policy suffice, provided the
digest job is idempotent (§10), because `--tries=3` means a mid-send crash *will*
re-run the job.

**Failure observation.** Failures land in `failed_jobs`. *Observation, reported
not fixed:* that table currently holds **27 rows**, all dated 2026-08-27 →
2026-09-05, all `ErrorException: Undefined property:
Illuminate\Notifications\ChannelManager::$app`. They are WP-2.7a-era development
residue in the dev database — none since 2026-09-05, and production is
unaffected. Not a WP-2.7e blocker; flagged because queue failure handling is in
scope and a reviewer would otherwise meet them cold.

## 8. Notification semantics

Settled by the documents:

- The digest is an **email**. FR-NOT-008 says "daily digest email".
- It aggregates **unread** items — rows with `read_at IS NULL`.
- It **creates no notification row** (DD-63), so it produces no badge count and
  no in-app artefact.
- It is **per-user opt-in through a channel preference**, defaulting to
  *enabled* like every other cell (the gate is opt-out).

Not settled, and therefore owner decisions (§21):

- **Which unread items?** The preference matrix is channel × type, so
  `digest × assignment` most naturally reads as "include assignment items in my
  digest". That is the coherent reading, but it is an inference, not a
  requirement.
- **Does the digest respect the `email` channel preference too**, or is `digest`
  independent of it? A user with all email off but digest on is currently
  undefined.
- **Recipients.** FR-NOT-008 says "per user" with no role restriction; all three
  roles presumably, but unstated.
- **Empty digest.** Send nothing, or send a "nothing new" email? §9.

## 9. Timezone analysis

**This is the largest undefined requirement, and it must not be chosen
silently.**

Facts established by inspection:

| Fact | Value |
|---|---|
| `config('app.timezone')` | **`UTC`** |
| `system_settings['system.timezone']` | **`"Asia/Manila"`** (seeded, `is_public = true`) |
| Per-user timezone column on `users` | **None** |
| Existing scheduled times | `dailyAt('02:15')`, `dailyAt('06:30')` — resolved in **UTC** |

So the project already carries a declared school timezone that the runtime does
not use. A digest scheduled `dailyAt('07:00')` would arrive at **15:00 in
Manila** — an afternoon "morning digest".

Options, with their real costs:

| Option | Consequence |
|---|---|
| **App/server timezone (UTC)** | Simplest, consistent with the three existing jobs, and wrong for readers — the digest lands mid-afternoon locally |
| **School timezone from `system.timezone`** | Matches the seeded setting and user expectation. Requires either a literal `->timezone('Asia/Manila')` or reading a DB setting at schedule-definition time — the latter is a boot-time query on every scheduler tick and a known Laravel pitfall |
| **Per-user timezone** | Truest to "daily" for each reader, but needs a **new `users` column** — a schema change beyond DD-63's "one constraint widened", and a materially larger package |

**Daylight saving:** `Asia/Manila` (PHT, UTC+08) observes **no DST**, so a fixed
local delivery time is stable year-round. That removes the usual argument for
per-user timezone handling and makes the school-timezone option cheap.

Also undefined and needed: the **delivery time**, the **digest window** (rolling
24 h vs. calendar day), the **cutoff** (items created before the run only), and
the **date-boundary rule** if the window is a calendar day.

## 10. Idempotency strategy

**Finding C is a genuine design gap, not an oversight in this report.** DD-60
gives every notification a per-user `dedupe_key` with a partial unique index —
but that lives on `notifications`, and DD-63 explicitly leaves `notifications`
untouched because the digest writes no row. **There is therefore no existing
place to record that a user has already received a given day's digest.**

This matters concretely: `queue:work --tries=3` will re-run a job that crashed
after sending; a container restart, a manual `schedule:run`, or a redeploy can
re-enter the window. `withoutOverlapping()` and `onOneServer()` prevent
*concurrent* runs — they do **not** prevent a *second successful* run.

Candidate strategies, for owner selection:

| Strategy | Idempotency key | Storage | Assessment |
|---|---|---|---|
| **Cache lock** | `digest:{user_id}:{YYYY-MM-DD}` | Redis | Cheapest, no schema change. Weak: a Redis flush or eviction re-opens the window, and it leaves no audit trail |
| **New table** `notification_digests` | UNIQUE `(user_id, digest_date)` | Postgres | Strongest — a database-enforced guarantee in the DD-60 spirit, auditable, survives restarts. **But it is a schema change beyond DD-63's stated scope** and needs explicit approval |
| **Activity log row** | query `activity_logs` before sending | Existing table | No new table; but `activity_logs` is an audit surface, not a uniqueness constraint — a read-then-write race is possible |
| **Scheduler guard only** | — | — | **Insufficient.** Prevents overlap, not repetition. Recorded here so it is not mistaken for a solution |

Recommendation offered, not taken: the **new table** matches how this project has
handled every other exactly-once guarantee (DD-60), and "a guarantee that depends
on Redis not being flushed is not a guarantee" is the same argument that produced
DD-66. It requires the owner to widen WP-2.7e's schema scope by one table.

**Retries and failure handling.** Per-recipient isolation is the established
posture (DD-59): one user's mail failure must not abort the whole run. The digest
command should therefore iterate recipients with per-user try/catch, mark each
user's idempotency record only after a successful send, and let `--tries=3
--backoff=5` handle transport blips.

## 11. Security analysis

| Concern | Rule inherited | Consequence for WP-2.7e |
|---|---|---|
| Ownership | `NotificationPolicy`, **no admin override** (DD-62) | A digest may only ever aggregate the recipient's **own** rows. No cross-user aggregation, no admin "digest of everyone" |
| Preference access | Self-only; WP-2.7b asserts one user cannot set another's | Unchanged — digest is a new column in the same matrix |
| Content | DD-61 structural facts; FR-NOT-006 "no secrets, minimal PII" | **Digest lists titles, never `message`** — see §5 |
| Disclosure | `NotificationDisclosureTest` proves a teacher never learns an internal note exists | The digest must not reintroduce this by aggregating rows the user could not otherwise see. It aggregates only that user's own `notifications` rows, so the boundary holds by construction — **and must be asserted by test** |
| Internal identifiers | `dedupe_key`, `user_id`, bigint keys never published | A digest email must not carry them; links must use uuid `action_url` values |
| Destination | DD-65 `/app/` prefix gate | Digest links are emails, not in-app navigation; they need absolute URLs built from `app.url`, which is a **different** rule and should be stated |

No new permission is required. No new authorization boundary is introduced.

## 12. Accessibility analysis

Frontend impact is close to zero, which is a design win worth stating.

- The preference matrix is **generated** from `meta.channels` and `meta.types`;
  its own docblock anticipates this. A third channel grows the grid from 2 × 9 =
  18 to 3 × 9 = **27 cells with no frontend change**.
- Each switch already carries an accessible name of the form
  `"{channel.label} notifications for {type.label}"`. `HasValues::label()`
  derives **"Digest"** from `digest` automatically, so the new column is named
  correctly without code.
- The axe baseline (`frontend/e2e/a11y-baseline.json`) holds only two
  pre-existing entries and **must not grow**. A third column is structurally
  identical to the existing two, so no new violation is expected — but
  `/app/account` must be re-audited to confirm rather than assumed.
- **Email accessibility** is new ground for this project: the digest is the first
  substantial multi-item email. It should carry a meaningful subject, a text
  alternative, and semantic structure — not a layout table of unlabelled links.

Matching the project's conventions — one rejection assertion per test, negative

- `notification_type = 'digest'` remains **422** (the existing test must stay green).

**Backend — digest behaviour**
- Aggregates only the recipient's own unread rows, only within the window.
- Respects per-type digest preferences.

**Backend — timezone**
- Window boundaries computed in the decided zone; an item just inside/outside the
  boundary is included/excluded correctly.

**Frontend**
- `PreferenceMatrix` renders three columns from `meta`. *(Existing tests use
  local fixtures, so they stay green — verified; only a stale

**E2E / accessibility**

  targets checkboxes by accessible name, so current tests are unaffected —

- Re-run the axe audit on `/app/account`; **no new baseline entry**.

**Production smoke** — after deployment: the scheduler container lists the new

## 14. Migration / deployment risk

**The known divergence, confirmed precisely:** repo/dev/test carry **31**
migrations, production **30**. The gap is exactly
`2026_09_05_100000_add_dedupe_key_to_notifications` — the WP-2.7a migration,
present in dev batch 6 and absent from production. Not resolved here, as
instructed.

| Question | Answer |
|---|---|
| Does WP-2.7e depend on migration 31? | **No.** #31 adds `dedupe_key` to `notifications`; WP-2.7e touches only `notification_preferences`. They are independent tables with no ordering dependency between them |
| Can WP-2.7e be deployed after the gap is resolved? | **Yes**, and that is the safe order |
| Does migration ordering create risk? | **Indirectly, and this matters.** Laravel runs *all* pending migrations in filename order. Deploying WP-2.7e to production would run #31 (WP-2.7a) **first**, in the same `migrate` invocation. A WP-2.7e release is therefore implicitly also the **first production release of WP-2.7a/b/c** — three unreleased packages arriving together |
| Is a production backup required? | **Yes.** `deploy-prod.sh` already snapshots the database (DD-64), and this would be the first production migration since Phase 2.6b |
| Rollback implications | Two layers. Image rollback is a scripted re-tag (DD-64) — **verified to fail safe but never exercised in a real production rollback**. Schema rollback is the DD-63 hazard-2 `down()`, which must delete `digest` rows first. Note a rollback that re-narrows the CHECK **silently discards user preferences** |

**The honest framing:** WP-2.7e's own migration is low risk — additive, one
constraint, on a table holding 0 production rows. The risk is that it is the
carrier for the first production deployment of all of Phase 2.7.

## 16. Proposed WP-2.7e scope

**Objective.** Deliver FR-NOT-008: a daily digest email aggregating each user's
unread notifications, selected per user as a third delivery channel.

**Business purpose.** A user who does not live in the application still learns
what needs attention, without the system emailing every event individually — the
digest is the low-noise alternative to per-event mail, not an addition to it.

**Functional scope**
- `NotificationChannel::Digest`.
- One migration widening `notification_preferences_channel_check`.
- `Digest` **excluded** from `ProjectNotification::via()` (§4).
- An Artisan command that, per opted-in user, aggregates unread notifications in
  the window and sends one email.
- One scheduler entry, matching house style.
- The digest mail itself (titles only, DD-61).
- An idempotency mechanism (§10, pending decision).
- The preference matrix grows to 27 cells — **server-side only**.

**Non-functional scope.** Per-recipient failure isolation (DD-59); queue-safe
under `--tries=3`; `withoutOverlapping()` + `onOneServer()`; no N+1 across
recipients; email content safe for external delivery (FR-NOT-006).

**Affected roles.** All three — administrator, technician, teacher — equally. No
role gains or loses a capability.

**Affected modules.** `Domains/Administration` (notifications) and
`App\Enums\NotificationChannel`. No other domain.

| Impact area | Assessment |
|---|---|
| Database | One widened CHECK; **+1 table if the strong idempotency option is chosen** |
| Backend | Enum case, migration, command, mail, `via()` skip, idempotency |
| Frontend | **None required** — matrix, validation and labels all derive from the enum. One stale comment to update |
| Scheduler | One entry |
| Queue | None — existing worker and retry policy suffice |
| Notification | No new topic, no new type, no notification rows created |
| Security | No new permission, no new boundary; inherits DD-61/62 |
| Accessibility | Re-audit `/app/account`; new ground for email accessibility |

## 17. Explicit exclusions

   dispatch normally and **nothing throws** — finding A is closed.

    baseline **unchanged**.

## 21. Project Owner decisions required

**A — Timezone for "daily".** UTC (matches the three existing jobs), the seeded
`system.timezone = "Asia/Manila"` (matches user expectation; no DST), or per-user
(truest, but needs a new `users` column and enlarges the package). *No default
was assumed.*

**B — Delivery time and window.** What time, and is the window a rolling 24 hours
or a calendar day? Existing jobs use 02:15 and 06:30.

**C — Which unread items.** Confirm that `digest × {type}` means "include this
type in my digest". Also: does the digest respect the **email** channel
preference, or is `digest` independent of it?

**D — Empty digest.** Send nothing, or send a "nothing new today" email? *(Send
nothing is the quieter default, but this is a product choice.)*

**E — Idempotency storage** (§10). Cache lock (no schema change, weaker),
**new `notification_digests` table** (database-enforced, +1 table beyond DD-63's
scope), or activity-log lookup. **This is the decision that most affects scope.**

**F — The undocumented `notifications.digest_enabled` system setting.** It exists,
seeded to `false`, and no design record mentions it. Is it the intended **global
kill-switch** the digest must honour, is it obsolete and to be ignored, or should
it be removed? Ignoring it silently would leave a setting that says one thing and
a system that does another.

**G — Recipients.** All three roles, or administrators/technicians only?

**H — Does DD-63 get amended or superseded?** Findings A, B and the stale
zero-rows premise mean DD-63 as written no longer matches the correct
implementation. Amend it in place at Version 1.0, or record a new DD alongside it?
