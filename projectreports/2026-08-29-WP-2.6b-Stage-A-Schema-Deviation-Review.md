## 1. The exact approved requirement

From the **WP-2.6b Audit & Implementation Planning Report, §22 M2**, which the
Client approved as **OD-1** (plan document line 909):

```sql
CHECK (status NOT IN ('approved','declined') OR (decided_by IS NOT NULL AND decided_at IS NOT NULL))
```

### Its parent requirement

**SRS DR-020** requires the entity to carry:

> "…the decision fields each decision needs (**deciding administrator and
> timestamp**; `decline_reason`; `rescheduled_to` and `reschedule_reason`;
> `clarification_reason` and optional `proposed_meeting_at`; `acknowledged_at`)…"

**This distinction matters for the decision below.** DR-020 requires the two
**columns** to exist. The composite CHECK constraint quoted above was an
Engineering proposal in §22 of the planning report — it is not SRS text, and no
FR-WSR or DR requires the deciding administrator to be enforced by a database
constraint.

## 3. The exact difference

**One clause was dropped from one CHECK constraint: `decided_by IS NOT NULL`.**

That is the entire deviation.

| | Approved | Implemented | Same? |
|---|---|---|:--:|
| `decided_by` column exists, nullable, FK SET NULL | yes | yes | Yes |
| `decided_at` column exists, nullable | yes | yes | Yes |
| CHECK requires `decided_at` on `approved`/`declined` | yes | yes | Yes |
| CHECK requires `decided_by` on `approved`/`declined` | **yes** | **no** | **No** |

Nothing else differs. No column was added, removed, renamed or retyped. No
foreign key, index or other constraint was changed. The other eight CHECK
constraints match the approved schema exactly.

---

## 4. Why the difference exists

`decided_by` is `ON DELETE SET NULL`. Deleting a user issues an `UPDATE` against
every request that user decided — and **that UPDATE re-evaluates every CHECK
constraint on the affected row**.

So the approved constraint would make a routine administrator-account purge fail
with a constraint violation on an unrelated table.

### Empirical demonstration

Both variants were reproduced in **isolated temporary tables inside a rolled-back
transaction**. Nothing was persisted and no project table was touched.

**Variant as approved — the cascade is blocked:**

```
BEGIN;
CREATE TEMP TABLE t_users (id int PRIMARY KEY);
CREATE TEMP TABLE t_req_approved (
  id serial PRIMARY KEY,
  status text NOT NULL,
  decided_by int REFERENCES t_users(id) ON DELETE SET NULL,
  decided_at timestamptz,
  CONSTRAINT variant_as_approved
    CHECK (status NOT IN ('approved','declined')
           OR (decided_by IS NOT NULL AND decided_at IS NOT NULL))
);
INSERT INTO t_users VALUES (1);
INSERT INTO t_req_approved (status, decided_by, decided_at) VALUES ('approved', 1, now());
DELETE FROM t_users WHERE id = 1;

ERROR:  new row for relation "t_req_approved" violates check constraint "variant_as_approved"
DETAIL:  Failing row contains (1, approved, null, 2026-08-29 04:16:05.909406+00).
CONTEXT: SQL statement "UPDATE ONLY "pg_temp_89"."t_req_approved"
                        SET "decided_by" = NULL WHERE $1 OPERATOR(pg_catalog.=) "decided_by""
ROLLBACK
```

**Variant as implemented — the cascade succeeds and the rule still holds:**

```
BEGIN;
... CONSTRAINT variant_as_implemented
      CHECK (status NOT IN ('approved','declined') OR decided_at IS NOT NULL)
INSERT INTO t_users VALUES (1);
INSERT INTO t_req_impl (status, decided_by, decided_at) VALUES ('approved', 1, now());

--- purge the deciding administrator ---
DELETE 1

--- request survives, decision timestamp intact ---
  status  | decided_by | has_timestamp
----------+------------+---------------
 approved |            | t

--- and it still refuses a decision with no timestamp ---
INSERT INTO t_req_impl (status, decided_by, decided_at) VALUES ('declined', NULL, NULL);
ERROR:  new row for relation "t_req_impl" violates check constraint "variant_as_implemented"
DETAIL:  Failing row contains (2, declined, null, null).
ROLLBACK
```

The approved constraint therefore creates a **self-contradiction inside the
schema**: the foreign key says "null this column when the user is deleted", and
the CHECK says "this column may not be null". One of the two has to give, and the
database resolves it by refusing the delete.

The failure mode is also badly placed: it surfaces during an unrelated
administrative action (purging a departed staff account), long after the
migration ran, with an error message pointing at a support-request table the
administrator was not working on. The tempting field fix at that moment would be
to weaken the audit trail rather than the constraint.

### Regression coverage

`WorkSupportSchemaTest` carries a dedicated test — **"it survives deletion of the
deciding administrator"** — which hard-deletes the decider and asserts the
request survives with `decided_by` nulled and its status intact. The reasoning
above is recorded in a comment inside that test so the constraint cannot be
"tightened" later without the test explaining why it must not be.

## 5. Does it affect WP-2.6b correctness?

**No.**

The invariant the constraint exists to protect — *a decision carries the moment
it was made* — is fully enforced, demonstrated in §4 above. An `approved` or
`declined` row without `decided_at` is refused by the database.

The deciding administrator is still captured in three places:

1. **`work_support_requests.decided_by`** — written by the lifecycle service on
   every decision (Stage G). The column is populated in normal operation; it only
   becomes null if that user's account is later hard-deleted.
2. **`activity_logs`** — **FR-WSR-011** already requires *"every submission,
   decision, reschedule, clarification request, acknowledgement and closure"* to
   be recorded *"with actor, subject, and the before/after values of anything
   changed"*. This is the durable record of who decided, and it is unaffected by
   a later user deletion.
3. The **administrator request-management surface** (FR-WSR-005) reads the
   decision history from `activity_logs`, not from `decided_by` alone.

No acceptance criterion is affected. **AC-WSR-008** requires the decline
transition to *"appear in the activity log with its actor"* — which is satisfied
by `activity_logs`, not by this constraint.

---

## 6. Does it affect data integrity?

**On balance it improves it.**

**What is gained:** the schema no longer contains a rule that contradicts its own
foreign-key policy. Under the approved text there exists valid, committed data
that cannot be deleted through the path the FK explicitly declares.

**What is relaxed:** in principle a row could be inserted with
`status = 'approved'` and `decided_by IS NULL` by something bypassing the
application layer. Two things already close that in practice:

- Stage G's `WorkSupportRequestLifecycle` is the **only** write path for a status
  change — DD-54 makes every transition a named, separately-authorized operation
  rather than a settable column, and it writes `decided_by` and `decided_at`
  together in one transaction.
- `activity_logs` records the actor independently, so even a hand-written row
  would leave the audit trail intact.

If the Client wants that residual gap closed at the database level as well, see
Option C in §8.

---

## 7. Does it affect future migrations?

**Yes — as a general rule that is worth keeping, not as a defect.**

Any CHECK constraint naming a column that is `ON DELETE SET NULL` will block that
cascade. This schema has many such columns, including:

- `maintenance_records.created_by`, `.updated_by`
- `qr_scan_logs.scanned_by`
- `asset_attachments.uploaded_by`, `repair_images.uploaded_by`
- `work_support_requests.cancelled_by`, `.procurement_request_id`
- `procurement_requests.approved_by`

None of them currently carries such a CHECK, so nothing existing is affected.

The rule has been recorded in Auto Memory as
`sccit-postgres-check-constraints`, together with the separate `btrim()` finding
from the same stage.

**It has deliberately NOT been added to CLAUDE.md.** That is the Client's call —
it was raised as a recommendation in Stage A report §9 and is repeated here:
if these two Postgres rules should be project law rather than remembered
guidance, they belong in CLAUDE.md, and Engineering will add them on
instruction.

## 8. Accept as-is, or correct?

| Option | Effect | Cost / consequence |
|---|---|---|
| **A. Accept as implemented** | Invariant enforced; cascade works; no contradiction | **None** — already built, tested and verified |
| **B. Restore the approved text verbatim** | Enforces `decided_by` at the database level | Reinstates the blocked cascade. Would additionally require changing the FK from `SET NULL` to `RESTRICT`, which contradicts the schema's "optional context + actor/audit columns preserve history" policy stated in `2026_06_30_100090_add_foreign_keys.php`, and would mean a departed administrator can **never** be purged while any request they decided exists |
| **C. Accept, plus an insert-time trigger** | Also enforces `decided_by` on INSERT/UPDATE by the application, while letting the FK cascade pass | Adds a trigger mechanism this schema otherwise uses only once (`audit_logs_immutable`). Closes a gap the single lifecycle write path already closes |

---

## 9. Engineering recommendation

**Accept as implemented — Option A.**

Reasoning:

1. It enforces the requirement's actual intent, proven in both directions.
2. It removes a self-contradiction between the FK policy and the CHECK that the
   approved text would have introduced.
3. **Option B is not viable on its own.** Making it work requires changing the FK
   to `RESTRICT`, which is a larger and worse change: it makes a departed
   administrator permanently undeletable and breaks the documented ON DELETE
   policy the whole schema follows.
4. **Option C is defensible but does not earn its keep.** The gap it closes is
   already closed by DD-54's single write path, and the actor is durably recorded
   in `activity_logs` by FR-WSR-011 regardless.

If the Client prefers belt-and-braces, **Option C is the better of the two
alternatives** — Option B should not be adopted.

Because DR-020 requires the *columns* and not the *constraint*, accepting Option
A leaves the Version 1.0 documentation accurate as written; no SRS amendment is
required either way.
