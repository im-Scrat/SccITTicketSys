## 6. Rollback verification

No destructive rollback was performed.

| Requirement | Status | Evidence |
|---|---|---|
| Release artifact can be identified | **FAIL (nothing exists)** | `releases/` absent; `releases.sh list` → "No releases recorded yet"; **zero `sccit/{app,web}:prod-<sha>` tags** |
| Previous artifact can be identified | **FAIL (nothing exists)** | same — there is no release history to point at |
| Rollback commands/procedure complete | **PASS** | `OPERATIONS.md` §3; `rollback-prod.sh` implements verify → plan → snapshot → retag → recreate → smoke |
| Independent of undocumented local state | **PASS** | needs only local Docker image tags + `releases/<sha>/manifest.json`, both produced by `deploy-prod.sh`. No registry, no network |
| Database rollback implications documented | **PASS** | `OPERATIONS.md` §3 states plainly that rolling back code does **not** roll back the database |
| Backup/snapshot recovery documented | **PASS** | `OPERATIONS.md` §2; restore round-trip proven twice (dev and production) |
| Operator knows when to invoke | **PASS** | `deploy-prod.sh` prints the exact rollback command on smoke failure |

### The three operations, kept distinct

1. **Rollback of application images** — moving `sccit/{app,web}:prod` onto a
   retained `:prod-<sha>` tag and recreating the services. No rebuild, no
   network. **Implemented; never exercised.**
2. **Rollback of database schema** — **not provided, and deliberately so.**
   Migrations are forward-only; `migrate:rollback` on a production dataset is a
   data-loss operation. When the target release expects fewer migrations, the
   script says so and continues, and the older image ignores what it does not
   know about. **This is not claimed to be safe and has not been verified.**
3. **Restoration from backup/snapshot** — `restore.sh` with a snapshot
   directory. Destructive, typed-confirmation gated. **Round-trip proven into a
   scratch database; never run against live production.**

### Verified failure behaviour

```
sh scripts/rollback-prod.sh              -> exit 2, usage + release list
sh scripts/rollback-prod.sh deadbeef     -> exit 1 at stage 1
                                            "image sccit/app:prod-deadbeef is not present locally"
sccit/app:prod after both                -> sha256:de13d793… (UNCHANGED)
```

### Finding: the pre-WP-2.7d rollback images are unusable by this tooling

Two images exist from WP-2.6b — `sccit/app:rollback-preWP26b` and
`sccit/web:rollback-preWP26b`, created **manually** 41 hours ago (corroborated
by claude-mem observations #1189–#1192, which record them being imported and
losing container configuration). `rollback-prod.sh` **cannot use them**: they do
not match the `prod-<sha>` naming and have no release manifest.

So the safety net that exists today is manual and undocumented, and the safety
net that is documented has nothing in it. That gap closes on the first real
deployment through `deploy-prod.sh` — and not before.

**Severity: high** — it defeats the entry point WP-2.6b was built for.


authorization.**

`prod-<sha>` naming or carry a manifest, so `rollback-prod.sh` cannot use them.
Until the first tracked deployment, the only usable rollback path is the manual

### F-4 — Three named boundaries lack committed regression coverage

**Severity: medium.** *My Submissions* technician-only, *Administrator Support
Requests*, and administrator QR panel access are **correct** (verified live this
