## 4. Release tag / rollback target — FINDING B1

This is the finding the gate mandated because of F-3, and it is worse than F-3
described.

| Requirement | State |
|---|---|
| A release-tagged image for the current production release | **Does not exist** |
| `releases/` directory | **Does not exist** |
| `releases/current` | **Does not exist** |
| `releases.sh list` | *"No releases recorded yet"* |
| Rollback candidates that do exist | Only `:rollback-preWP26b`, already declared unusable by **F-3** |

**Why this matters mechanically.** `compose.prod.yaml` pins
`image: sccit/app:prod`. `deploy-prod.sh` moves that floating tag onto the new
build. The moment it does, image `de13d793201d` **loses its only name** and
becomes dangling. `rollback-prod.sh <release>` reads
`releases/<sha>/manifest.json`, which does not exist for the current release, so
the scripted rollback has no target.

**It is worse than a missing tag:** `deploy-prod.sh` computes
`PREVIOUS="$(cat releases/current …)"`, so on a failed smoke test it will print
**no rollback command at all** — the operator is left with a live, unverified
deployment and no scripted way back.

**What is not lost.** Three mitigations exist, and they are why this is YELLOW
rather than RED:

1. The old image survives as a **dangling image by ID**; `docker tag
   de13d793201d sccit/app:prod` would restore it manually.
2. Retention pruning only walks recorded releases, and there are none, so
   nothing will prune it during this deploy.
3. The image IDs are already recorded in a real artifact —
   `backups/prod/20260901T044951Z-gate-verify/manifest.json` lists
   `app: sha256:de13d793201d…` and `web: sha256:b8bd04e3c427…`.

**Remediation (not performed — reporting as instructed).** Before deploying,
tag the current production images as a release and record a manifest, so that
`rollback-prod.sh` has a real target:

```
Previous production release  →  sccit/{app,web}:prod-2df17db   (to be created)
New Phase 2.7 release        →  sccit/{app,web}:prod-6cd219e   (built by deploy)
```

This is a deployment-environment preparation step, not a code change. It needs
your explicit authorization because it writes tags and a `releases/` entry.

## 5. Rollback analysis — F-2

`rollback-prod.sh` was read in full. Its design is sound: retag `:prod` onto an
immutable `:prod-<sha>`, recreate services, **always** finish with the smoke
test, and refuse a mismatched schema pairing rather than discover it live. It
correctly states that rolling back code does **not** roll back the database, and
requires `--restore-db` for that, confirmed separately.

| # | Scenario | Behaviour | Assessment |
|---|---|---|---|
| 1 | Deployment fails **before** migration (step 5) | Services recreated on the new image; database still at 30; old image untagged | **Unsafe today (B1)** — no scripted rollback target. Safe once B1 is remediated |
| 2 | Image starts but `/up` fails | Step 5 waits for the health check; failure aborts before migrating. Database untouched at 30 | Safe — the most benign failure |
| 3 | **Migration 31 fails** | `migrate --force` is not transactional across migrations, but *this* migration is a single `ALTER TABLE` + `CREATE INDEX`; a failure leaves 30 applied and `dedupe_key` possibly added. Old code tolerates an extra nullable column | Recoverable; snapshot restores exactly |
| 4 | **Migration 32 fails** | 31 applied, 32 partially applied. Its two statements are the CHECK swap and the table create; a failure between them could leave the widened CHECK without the table. The widened CHECK is harmless to old code (it only *permits* more) | Recoverable; snapshot restores exactly |
| 5 | Startup fails **after** migration | Database at 32, code rolled back to a 30-era image. Both migrations are **additive**, so old code ignores the extra column and table | Survivable; `rollback-prod.sh` warns about the mismatch rather than hiding it |
| 6 | Database healthy, web container fails | `nginx_prod` serves the built SPA only; app and data unaffected. Retag/recreate web alone | Low severity |
| 7 | **Rollback image unavailable** | Script exits with the release list and a non-zero code — it does not guess | Correct behaviour, but **this is today's state (B1)** |
| 8 | Rollback image incompatible with applied migrations | Script detects the migration-count mismatch and says so plainly | Correct; and both migrations being additive makes the mismatch survivable |

**Unsafe/ambiguous condition identified: scenario 1 and 7 — the same one.**
Every other path is safe or recoverable. All eight become safe once a valid
rollback target exists.

## 7. Migration 31 → 32 analysis

| | Migration 31 | Migration 32 |
|---|---|---|
| Filename | `2026_09_05_100000_add_dedupe_key_to_notifications.php` | `2026_09_07_100000_add_digest_channel_and_digest_log.php` |
| Purpose | Per-user notification idempotency (WP-2.7a, DD-60) | Digest channel + at-most-once digest record (WP-2.7e, DD-63) |

| Indexes | `notifications_dedupe_unique` — partial unique `(user_id, dedupe_key) WHERE dedupe_key IS NOT NULL` | `notification_digests_unique` — `UNIQUE (user_id, digest_date)` |
| Constraints | — | `notification_preferences_channel_check` widened to `('in_app','email','digest')`; FK `user_id → users` cascade |
| Dependencies | None | `users` (present in production) |
| Production compatibility | `notifications` exists | `notification_preferences` exists; `notification_digests` absent; CHECK still two-value |
| Existing-data compatibility | **0 rows** | **0 rows** |
| Failure behaviour | Single ALTER + CREATE INDEX | CHECK swap, then table create |
| `down()` | Drops index and column (loses `dedupe_key`) | Drops table, deletes `digest` preference rows, restores narrow CHECK — **executed and verified during WP-2.7e** |

**Order 31 → 32 is correct** and is what Laravel will apply — filename order,
one `migrate` invocation. They touch **disjoint tables**, so no dependency binds
them; the order is safe either way.

**Production at 30 can safely receive both.** Both are additive, both meet the
schema they expect, and both act on **empty tables** — no backfill, no lock
contention, and nothing for the CHECK swap to revalidate. DD-63's `down()`
data-loss hazard has nothing to delete in production today.

**A safety property observed, not relied upon:** `migrate --pretend` inside the
production container returned *"Command cancelled"* — Laravel's production
confirmation guard refused without an interactive confirmation. Nothing ran;
production's `migrations` table still reads 30.

## 9. Network-reachable environment

**The current production stack is not network-reachable, and is not configured
to be.** Every published port binds to loopback:

```
nginx_prod     127.0.0.1:8081 -> 80
mailpit_prod   127.0.0.1:8026 -> 8025
app/queue/scheduler   9000/tcp   (no host binding)
postgres_prod  5432/tcp          (no host binding)
redis_prod     6379/tcp          (no host binding)
```

**No development-only service is publicly reachable — because nothing is.**
Postgres, Redis and PHP-FPM are container-internal; Mailpit's UI is loopback.

Deploying Phase 2.7 to this stack is therefore a **local production-parity
deployment**, and is what the tooling supports today. Making the environment
genuinely network-reachable is a **separate change** with unresolved
prerequisites, none of which exist yet:

| Prerequisite | State |
|---|---|
| Hostname / DNS | Not defined |
| HTTPS / TLS termination | **None** — nginx serves plain HTTP |
| `APP_URL` | `http://localhost:8081` — drives redirects, signed URLs and the links inside digest and notification emails |
| `SESSION_SECURE_COOKIE` | Unset — must be `true` over HTTPS |
| Trusted proxies | Unconfigured — required behind a TLS terminator |
| Real SMTP | **Absent** — mail goes to Mailpit, which captures and never delivers. Every notification and the daily digest would silently go nowhere |
| Firewall / port exposure | Loopback-only today; would need deliberate opening |
| Reverb / WebSocket | Not applicable — FR-NOT-007 unimplemented |

Nothing was exposed and no network configuration was changed.
