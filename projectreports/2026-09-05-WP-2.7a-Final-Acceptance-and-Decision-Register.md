## 4. Security status

**Boundary.** A notification belongs to exactly one person. Every query is
scoped on `user_id`; `NotificationPolicy` re-asserts the same rule per record,
so the list rule and the single-record rule are the same rule — a notification
absent from a list is unreachable by its uuid. **There is deliberately no
administrator override**, and no `notifications.*` permission was invented
(the §8.4 matrix is unchanged, preserving the OD-4 precedent).

**Content rule.** A notification carries structural facts; free text a person
typed is never copied into one. Asserted **against the stored payload** so a
field cannot leak back in through a later resource change: transition remarks,
comment bodies, technicians' explanations, administrators' decline and
clarification reasons, and other people's names are all excluded. Internal
notes never notify a Teacher — not even the fact of them. Lockout notices carry
the duration and never the IP, user agent or attempt count. `action_url` is
always a relative `/app/…` path (FR-QR-011). `dedupe_key`, `user_id` and
internal ids never leave the application.

**Existing authorization was not weakened.** No policy, visibility service,
permission or transition map was modified.

## 7. Decision D1 — daily digest (FR-NOT-008)

**Recorded as APPROVED (Option A). Not implemented. No migration created, no
schema changed.** The following is the specification for the future work
package.

### 7.1 The existing constraint, verbatim from the live schema

```sql
-- table: notification_preferences
notification_preferences_channel_check
  CHECK (((channel)::text = ANY ((ARRAY[
    'in_app'::character varying,
    'email'::character varying
  ])::text[])))
```

Two sibling constraints are **not** in scope and must not be touched:

```sql
notification_preferences_notification_type_check   -- the nine NotificationType values
notifications_type_check                           -- the same nine values
```

### 7.2 The required change

| | |
|---|---|
| Affected table | `notification_preferences` — **only** |
| Affected constraint | `notification_preferences_channel_check` — **only** |
| Change | drop and re-add, widened to `('in_app', 'email', 'digest')` |
| Affected column | `channel` — type unchanged (`varchar`), nullability unchanged |
| Rows rewritten | **none** — a CHECK change does not rewrite the table |
| Other tables | **none**. `notifications` is untouched: a digest creates no notification row, it aggregates unread ones |
| `notifications_type_check` | **unchanged** — digest is a channel, not a type. This is precisely why Option A was correct and Option B was not |

```sql
ALTER TABLE notification_preferences DROP CONSTRAINT notification_preferences_channel_check;
ALTER TABLE notification_preferences ADD  CONSTRAINT notification_preferences_channel_check
  CHECK (channel IN ('in_app', 'email', 'digest'));
```

### 7.3 Migration safety

| Concern | Assessment |
|---|---|
| Atomicity | Postgres DDL is transactional and Laravel wraps each migration in a transaction, so the drop and the re-add commit together. **There is no window in which the column is unconstrained.** |
| Validation cost | `ADD CONSTRAINT … CHECK` validates existing rows with a full scan under `ACCESS EXCLUSIVE`. The predicate is a **widening**, so every existing row satisfies it by construction — validation cannot fail. |
| Table size | `notification_preferences` holds **0 rows in development and 0 rows in production** (verified 2026-09-05). The scan is empty and the lock is momentary. |
| Data loss | None. No column is dropped, retyped or defaulted. |
| Ordering | Additive and independent — no dependency on any other pending change. |

### 7.4 Rollback implications — the part that needs stating plainly

**A naive `down()` will fail once anybody has opted into the digest.**
Re-narrowing the CHECK re-validates the table, and a row with
`channel = 'digest'` violates the narrowed predicate, so `ADD CONSTRAINT` is
refused and the rollback aborts.

The `down()` must therefore **delete `channel = 'digest'` rows before
re-adding the narrow constraint**, and say so in its docblock. That is an
acceptable, bounded loss — a user's digest opt-in, recoverable by opting in
again — and it is strictly better than a rollback that fails halfway through a
release.

**The enum case must be removed in the same rollback.** Leaving
`NotificationChannel::Digest` in PHP against a narrowed CHECK would let the API
offer a channel the database refuses, turning a user's preference save into a
constraint violation.

Rolling back is safe today at zero cost, because both stacks hold zero
preference rows.

### 7.5 Integration with the existing architecture

`NotificationChannel` is the only place the channel set is enumerated, which is
what makes this a small change — but three call sites need deliberate handling
and **one of them fails hard if it is missed**.

**① `ProjectNotification::via()` — breaks immediately.** The routing map is an
exhaustive `match` with no default arm:

```php
$channels[] = match ($channel) {
    NotificationChannel::InApp => 'database',
    NotificationChannel::Email => 'mail',
};
```

Adding `Digest` to the enum without changing this throws
`\UnhandledMatchError`. Because the preference model is **opt-out**, digest
would be "allowed" for every user who has never visited the preferences
screen — which is all of them — so the failure would hit **every notification
to every recipient**, not an edge case. The dispatcher would swallow it and
report it, so the business actions would survive and the system would simply go
silent. **This must be fixed in the same change as the enum case.**

The correct handling is not a new Laravel channel. **Digest is a preference,
not a per-notification delivery route**: nothing is sent *via* digest at the
moment a ticket is assigned. `via()` must skip `Digest` explicitly, and a
scheduled command must read the preference and mail the aggregate.

**② The original table migration builds its CHECK from the enum at run time.**
`create_administration_tables.php:42` calls
`$table->enum('channel', NotificationChannel::values())`. So adding the enum
case silently changes what a **fresh** database gets from `migrate:fresh`,
while an **existing** database keeps the narrow constraint until the new
migration runs. The two would diverge, and a test database rebuilt with
`migrate:fresh` would accept `digest` before the widening migration exists.
Both paths must be made to agree.

**③ `tests/Unit/NotificationTopicTest.php:55`** asserts
`NotificationChannel::values() === ['in_app', 'email']` and will fail. That is
the intended tripwire, not an obstacle — it exists so the channel set cannot
change unnoticed.

**Adapting automatically, no change needed:** the preference matrix (2 × 9 → 3 × 9
= 27 cells), `meta.channels` on the preferences endpoint,
`UpdateNotificationPreferencesRequest`'s `Rule::in`, the model cast, and the
factory. `AccountLocked::forcedChannels()` is unaffected.

**Semantics to settle when the work is authorized:** a digest preference is
per-**type**, so it reads as *"include maintenance notifications in my daily
digest"*. Whether a type enabled for digest should also stop sending immediate
email — digest as a *replacement* rather than an *addition* — is a product
question this register does not answer.

### 7.6 What is still needed before FR-NOT-008 can be built

The digest also needs a scheduled command, an aggregate mail template, a
"since when" watermark so a digest does not repeat yesterday's items, and a
decision on send time. **None of that is in scope here** and none of it was
built.

## 8. Decision D5 — announcements (WP-2.7c)

**Recorded. Not implemented.**

> **Publishing an announcement creates an in-app notification. It does not send
> email.**

Constraints recorded for WP-2.7c to honour:

- **Audience targeting is an authorization boundary, not a display filter.**
  Content must never reach a user outside `announcements.audience`
  (all / teachers / technicians / admins).
- **User notification preferences apply** where applicable — the `announcement`
  type already exists in `NotificationType`, so the existing gate covers it with
  no new mechanism.
- **Authorization** is `system.announcements.manage`, which already exists and is
  administrator-only. **No new permission is required** and the §8.4 matrix does
  not change.
- **The existing notification security and content rules apply unchanged** —
  structural facts, no borrowed prose, relative `action_url`.

**Consequence for sequencing:** because publishing notifies, **WP-2.7c depends
on WP-2.7a**, which is now delivered. No email path is needed, which removes the
school-wide-blast risk that motivated the recommendation.

The infrastructure already carries this: `NotificationTopic` needs one case,
and the trigger is one listener on an announcement-published event. Nothing in
the channel driver, gate, dispatcher or policy has to change.
