## 3. Architecture impact

**None to the application.** No domain, model, route, policy, resource, enum or
permission was added, changed or removed. The Domains layout, the flat
`App\Models`, the UUID route keys and the RBAC matrix are exactly as WP-2.6b
left them.

Four additions sit *around* the application:

1. **`scripts/lib/stack.sh` — a new shell convention.** Every operational script
   sources it and calls `dc` / `app_exec` / `db_exec`. This exists because the
   root `.env`'s `COMPOSE_PROJECT_NAME=sccit` overrides the `name:` inside
   `compose.prod.yaml`, so any production command missing `-p sccit_prod`
   silently manages the development stack. The flags now live in one file that
   cannot forget them.

2. **`backend/app/Console/Commands/`** — a new directory. The project's
   convention is that commands live with their domain and are registered in
   `bootstrap/app.php`. Verification tooling belongs to no domain, so it uses
   Laravel's auto-discovered path instead; `bootstrap/app.php` is unchanged.

3. **`backend/config/verification.php`** — a new config file, so the fixture
   password is read through `config()` rather than `env()`. The production
   entrypoint runs `config:cache` on every boot, after which `env()` returns
   null outside `config/` — a fixture password that became null would be a null
   password, not a missing one. Larastan enforces this and caught it.

4. **`frontend/e2e/`** — a fourth TypeScript project (`tsconfig.e2e.json`),
   referenced from `tsconfig.json` so `tsc -b` type-checks the harness. An
   unchecked test harness rots faster than the code it guards.

## 5. Deployment tooling changes

`scripts/deploy-prod.sh` replaces the ad-hoc `prod-build → prod-up → migrate`
sequence with eight stages:

| # | Stage | Aborts on |
|---|---|---|
| 1 | Preflight | dirty tracked tree (a release tag names a commit; `--allow-dirty` overrides) |
| 2 | Quality gates | any gate failing — **nothing has been touched yet** |
| 3 | Pre-deploy snapshot | — |
| 4 | Build + tag | build failure — the running deployment is untouched |
| 5 | Deploy | — |
| 6 | Migrate | `migrate --force` failure |
| 7 | Smoke test | any HTTP check; prints the exact rollback command |
| 8 | Record release | — |

Nothing is pruned until the smoke test has passed.

`scripts/smoke.sh` verifies a *running* target over HTTP only: `/up`,
`/api/health` (database and Redis **from inside the app**), the SPA document,
the hashed bundle it references, the SPA fallback, four security headers, and
that a bad login is refused rather than returning 500. Exit status is the
failure count.

`scripts/gates.sh` runs the nine `CLAUDE.md` §6 gates cheapest-first, always
attempting every one so a single invocation reports everything broken, and never
in parallel — the suites share one test database, and concurrent Pest runs
fabricate failures that look like real regressions.

## 6. Rollback strategy

**The problem.** `compose.prod.yaml` pins `image: sccit/app:prod`. Building
overwrites that tag in place, so the moment a bad build finished, the previous
image had no name and rollback was impossible. This is the concrete weakness
WP-2.6b exposed.

**The fix.** Every build is tagged with its commit *first*:

```
sccit/app:prod-<sha>   immutable, retained
sccit/web:prod-<sha>   immutable, retained
sccit/app:prod         floating — what the stack runs
```

Rollback moves the floating tag onto a retained one and recreates the services.
No rebuild, no registry, no network — which is the point, because rollback has
to work when the thing that broke *is* the build.

`scripts/rollback-prod.sh`: verify the artifact still exists → show the plan →
**snapshot the current state before discarding it** → retag and recreate →
smoke test. `releases/current` is updated only *after* the smoke test passes, so
an unverified rollback is never recorded as good.

**What is deliberately not automatic.** Rolling back code does **not** roll back
the database. Migrations here are forward-only, and `migrate:rollback` against a
production dataset is a data-loss operation, not a safety net. When the target
release expects fewer migrations than are applied, the script says so plainly
and continues — every Phase 2.4–2.6b migration is additive, so the older image
ignores what it does not know about. `--restore-db` goes back to the data too,
and is confirmed separately.

**Retention.** The 5 most recent releases, plus an absolute guarantee: the
currently deployed release and the one it would roll back to are never pruned,
whatever `--keep` says. Pruning the rollback target to save disk is how a
retention policy quietly becomes a single point of failure.

`backups/` and `releases/` are gitignored — they hold real rows, real uploads
and local image ids. The tooling is tracked; the artifacts are machine-local.

## 7. E2E coverage

**18 tests, all passing (exit 0)**, run against a node image rebuilt from the
Dockerfile with the `node_modules` volume discarded.

| Area | Tests | What is proved |
|---|---|---|
| Three-role sign-in | 3 | each role reaches the workspace shell, with a **server-side** session |
| Wrong password | 1 | refused **and no cookie issued** behind the error |
| Sign-out | 1 | the session ends on the server, not just in client state |
| Anonymous access | 1 | `/app` redirects to sign-in; `/api/user` → 401 |
| Authorization boundaries | 3 | the full 200/403 matrix per role, at the API |
| Guarded-route surfaces | 2 | teacher and technician typing an admin URL get the 403 page |
| QR scan entry | 4 | FR-QR-010 non-disclosure, FR-QR-011 storage and single-use consumption |
| QR authorization boundary | 3 | teacher refused the panel; unknown label refused without disclosure |

Two mechanics were necessary and are commented where they live, because both
cost real time to discover:

- **Chromium's `--host-resolver-rules`** keeps the browser's origin at
  `localhost:<port>` so Sanctum's cookies stay first-party, while packets reach
  the container that can answer (`nginx:80` for dev; `host.docker.internal:8081`
  for production, whose network the dev containers deliberately cannot route to).
- **API assertions run as `fetch` inside the page.** Playwright's `page.request`
  runs in Node, outside the browser, where that resolver mapping does not apply —
  it fails with `ECONNREFUSED` before reaching the application.

Deterministic data comes from `sccit:e2e-fixtures`: three named accounts, a
fixed QR label (`PC-E2EFIXTURE`) on a PC unit carrying an in-progress
maintenance record assigned to the fixture technician. It is idempotent on
natural keys and refuses to run under `APP_ENV=production`.

## 9. Security / authorization verification

No permission, policy or role changed. What was added is verification.

**Authorization boundaries, asserted twice.** Every boundary is checked at the
API through the page's own session *and* at the surface the user sees. A UI that
hides a link while the endpoint stays open is the vulnerability; a UI that shows
a link to an endpoint that refuses it is a bug. Only checking both tells them
apart. The matrix below was **probed against the running application** before it
was written into the suite:

| Endpoint | administrator | technician | teacher |
|---|---|---|---|
| `/api/tickets/mine` | 200 | 200 | 200 |
| `/api/tickets/feed` | 200 | **403** | 200 |
| `/api/admin/tickets` | 200 | **403** | **403** |

| `/api/qr/PC-E2EFIXTURE/panel` | 200 | 200 | **403** |

The technician's `/api/tickets/feed` → 403 is asserted specifically as a
**refusal, not an empty list**.

**Non-disclosure (FR-QR-010).** Verified at the rendered document, not the API
payload — the leak this guards against would be client-side. An anonymous scan
of the fixture label routes to sign-in with the PC name, unit code and room name
all absent from the page. An anonymous scan of a *known*, an *unknown* and a
*revoked* label were confirmed to return the identical `{"next":"sign-in"}`, so
the answer itself discloses nothing.

**Fixture safety.** `sccit:e2e-fixtures` refuses to run under
`APP_ENV=production` and creates nothing when it does. The production image
bakes `app/`, so this command ships inside it; these accounts share one
documented password, which on a production target would be a back door rather
than a fixture. The guard has a dedicated test asserting both the exit code and
that no rows were written.

**Secret scan:** clean. The only credential in the diff is the deliberately
documented local fixture password, in the three places it belongs
(`config/verification.php`, its test, `docs/TESTING.md`), overridable via

### Defects found in this work package's own code, and fixed

Reported because each would have degraded the harness silently:

1. **Vitest was running the Playwright specs.** Its default `include` matches
   `*.spec.ts`, so `e2e/` was imported into jsdom — four failing files that said
   nothing about the application. Vitest is now scoped to `src/`.
2. **PHPStan: `env()` outside `config/`.** See §3.3 — the rule is enforcing
   something real.
3. **Two redundant nullsafe accesses** on non-nullable enum properties.
4. **Label locators.** `Field` renders a required marker inside the `<label>`,
   making its text `"Password *"`; exact matching found nothing, and loose
   matching also matched the visibility toggle's "Show password".
5. **`page.request` bypasses the browser** — see §7.
6. **Production smoke asserted "no console errors"**, which fails on *correct*
   behaviour: Chromium logs a console error for the SPA's anonymous session
   probe (`/api/user` → 401). Ignoring console errors wholesale would have
   blinded the check entirely; failures are now attributed by URL and status.
7. **CRLF line endings** introduced by tooling, caught by Pint.

## 14. Remaining risks

### R1 — A real defect found, deliberately not fixed *(needs your decision)*

**The post-sign-in redirect is broken, and it is not QR-specific.** Reproduced
deterministically in three independent probes:

```
scan label        → /sign-in → [login 200] → /app/qr/PC-E2EFIXTURE → /app
/app/tickets/mine → /sign-in → [login 200] → /app/tickets/mine      → /app
```

The application navigates to the correct destination and is then immediately
bounced to the dashboard. `SignInPage` is **not** at fault — it consumes the
stored code and navigates correctly. `GuestRoute` is still mounted on `/sign-in`
when the auth state flips and renders `<Navigate to="/app" replace />`, whose
effect runs *after* the imperative navigation and overwrites it.

Impact: **FR-QR-011** — a technician scans a sticker, signs in, and lands on the
dashboard instead of the machine — plus the ordinary return-to-intended-page
behaviour dating from WP-2.1.

Recorded as an executable `test.fail()` with the evidence in its comment, so the
gate stays green while the defect stands and turns **red** the moment somebody
fixes it. Fixing it changes WP-2.6b/WP-2.1 application behaviour and is outside
WP-2.7d's approved scope. **Authorization required.**

### R2 — Documentation reconciliation owed

The SPMP has **no WP-2.7d row**, and this scope overlaps **WP-2.11** ("security
review, WCAG AA audit, perf/load test, backup ops, prod deploy"). WP-2.6b also
carried "axe/WCAG regression automation" and "browser visual regression" forward
as deferred — the first is now delivered; **visual regression is not**. Per your
documentation rule, nothing was written to the SRS/SDD/SPMP. All three remain

### R3 — E2E runtime

The full browser suite takes ~6 minutes and the accessibility suite ~13, single-

in `gates.sh` and `workflow_dispatch`-only in CI. Parallelising would require
per-worker database isolation, which is not in scope.

### R4 — Deployment tooling is exercised, but not yet used for a real release

`deploy-prod.sh` and `rollback-prod.sh` were verified by component — snapshot,
restore round-trip, smoke, release listing, retention logic — and by reading.
Neither has yet driven a full production release end to end, because WP-2.7d
changed no application code and there was nothing to deploy. **The first real
exercise should be the WP-2.7a deployment**, and it should be treated as a test
of the tooling as much as of the feature.

### R5 — `make` is unavailable on this host

executable path under Git Bash. Both are documented.

### R6 — Third flake newly characterised
