Two things found during implementation are worth reading before the detail,
because both corrected the approved design rather than merely implementing it.

**DD-63's fix would have been wrong.** It anticipated giving `via()` a `digest`
arm. Routing a notification to a digest at dispatch time contradicts what a
digest *is* — it aggregates rows that already exist. The delivered design moves
the channel mapping onto the enum as `driver()` and has `via()` skip any channel
without one, so `Digest` is a preference the daily command reads later, never a
route.

**Catching the unique violation was a latent outage.** The first implementation
of the idempotency claim caught PostgreSQL's unique violation. That works once:
Postgres **aborts the surrounding transaction** on a constraint error, so the
first already-sent recipient would have poisoned the run and silently denied the
digest to everyone after them (`SQLSTATE 25P02`). Replaced with
`INSERT … ON CONFLICT DO NOTHING`. There is a regression test named for it.

## 4. Database changes

One migration, `2026_09_07_100000_add_digest_channel_and_digest_log`, carrying
two changes that are meaningless apart.

**Widened channel domain.**

```
notification_preferences_channel_check
  channel IN ('in_app','email')  ->  channel IN ('in_app','email','digest')
```

Built from `NotificationChannel::values()`, the DD-18 / DD-32 technique, so the
enum and constraint cannot drift. A test asserts the constraint text contains
every enum value.

**New table.**

```
notification_digests
  id, user_id (FK users cascade), digest_date date,
  sent_at timestamptz null, created_at, updated_at
  UNIQUE (user_id, digest_date)   -- notification_digests_unique
```

| Property | Assessment | Verified |
|---|---|---|
| Additive | Strict superset; new table | ✔ |
| Destructive | No | ✔ |
| Reversible | Yes, with a data step | **`down()` executed against a live `digest` row** |
| Re-runnable `up()` | `DROP CONSTRAINT IF EXISTS` | ✔ |
| Compatible with existing rows | dev held 1, prod holds 0 | ✔ |

**DD-63's rollback hazard was tested, not assumed.** A `digest` preference row
was inserted, `migrate:rollback` was run, and it succeeded — the constraint
returned to two values and the table was dropped. The migration deletes those
rows first, which **discards real user preferences**; that is unavoidable and is
stated in the migration and the SDD rather than left to be discovered.

`digest_date` is the day **summarised**, not the day of delivery.

## 5. Notification architecture changes

`NotificationChannel` gains `Digest`, plus `driver()` — one exhaustive match
over all three cases returning `null` for `Digest` — and `isDispatchable()`.

`ProjectNotification::via()` now asks each channel for a driver and skips any
without one. The inline two-arm match is gone; adding a fourth channel is a
compile-time question in the enum instead of a runtime failure in dispatch.

**Why this ordering was non-negotiable.** The preference gate is opt-out: an
absent row means *enabled*. The moment `Digest` exists as a case, the gate
reports it allowed for every user with no preferences, `via()` reaches its
exhaustive match, and throws `UnhandledMatchError` on the next notification to
**anybody**. DD-63 predicted a failure "on the first digest-enabled user"; the
real blast radius was every user immediately. The enum case and the `via()`
change are therefore a single commit (`f42d7e6`).

Nothing else in the notification stack changed: no new topic, no new type, no
notification rows created, `notifications_type_check` untouched, and the
dispatcher, gate, policy and database channel are as they were.

## 6. Scheduler changes

```php
Schedule::command('notifications:send-digest')
    ->dailyAt('07:00')
    ->timezone(DailyDigest::TIMEZONE)
    ->withoutOverlapping()
    ->onOneServer();
```

Registered in `bootstrap/app.php` alongside the three existing domain commands.

**Verified live:** `schedule:list` resolves it to `0 23 * * *` — 23:00 UTC is
07:00 Asia/Manila, which is the conversion working correctly.

**The timezone is a constant, not a settings query.** `routes/console.php` loads
on every artisan invocation; a query there would run during `migrate`, during
`queue:work` boot and in every test, and would fail outright during
`migrate:fresh` before the table exists. A test asserts the constant still equals
the seeded `system.timezone`, so the two cannot drift quietly.

**No queue change.** The existing worker and `--tries=3 --backoff=5` are
unchanged; the digest sends synchronously inside the command precisely so the
command knows whether SMTP accepted, and so a retry cannot resend.

## 7. Idempotency implementation

Claim → send, with the claim committed first.

```php
$claimed = NotificationDigest::query()->insertOrIgnore([...]);  // ON CONFLICT DO NOTHING
return $claimed === 1;
```

`insertOrIgnore` rather than a caught exception, for the reason in §1: catching
a unique violation aborts the PostgreSQL transaction and takes the rest of the
run down with it. The unique index — not the scheduler's Redis lock — is the
authoritative guarantee. `withoutOverlapping()` stops runs *colliding*, which is
a different question from stopping a second run *succeeding*.

Proven for all five scenarios decision E named: a second scheduler tick, a
manual re-invocation, a worker retry, a container restart and a redeploy all
reduce to the same thing — the command runs again against a database that
already holds the claim.

## 8. At-most-once delivery behaviour

The bargain, and both halves of it, are tested.

**The protection.** A claimed day is never sent again. Live: the first run sent
21 digests; the immediate re-run reported `0 sent, 21 already sent`.

**The price.** `sent_at` is stamped before SMTP is contacted, so a transport
failure spends that user's day — the command logs it, counts it, and does not
retry. `it('does not resend a digest whose mail failed, because the claim was
already committed')` asserts exactly this, so the cost is deliberate and visible
rather than discovered in production.

**`sent_at` means committed, never confirmed delivered.** Recorded in the model,
the migration, the SRS and DD-63, because a column named `sent_at` invites the
wrong reading.

One recipient's failure does not abort the run — each is isolated in its own
try/catch, the DD-59 posture.
