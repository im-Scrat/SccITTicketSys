### 3.2 Answers to the specific audit questions

| Question | Answer (verified in repository) |
|---|---|
| How are QR codes generated? | `QrService::issue()` — `PC-`/`AS-` prefix plus `strtoupper(Str::random(10))`, collision-checked in a `do...while`. CSPRNG-backed (`Str::random` uses `random_bytes`). Approximately 51 bits of entropy over a 36-symbol alphabet, non-uniform (letters twice as likely as digits). |
| Where are QR identifiers stored? | `qr_codes.code` (unique). `pc_units.qr_identifier` (unique, nullable) is a **denormalized copy written only by `QrService`** (FR-QR-002). |
| Does each PC have exactly one *active* QR identity? | **By application logic, not by the database.** `generate()` returns the existing active code rather than duplicating; `regenerate()` revokes-then-issues in a transaction. **There is no partial unique index** — `\d qr_codes` shows only `code`/`uuid` uniques and plain FK indexes. A concurrent double-`generate()` is theoretically racy. |
| Can QR codes be revoked? | Yes — `revoke()` sets every active code for the target to `revoked` and nulls `pc_units.qr_identifier`. |
| Can they be regenerated? | Yes — the old row is **revoked, never mutated**, and a new row inserted (FR-QR-007, verified by test). |
| Do old identifiers remain invalid? | The old row persists with `status='revoked'`. **Nothing yet consumes that status** — there is no scan path to reject it. Enforcement is WP-2.6b's job. |
| Relationship to `pc_units` | `qr_codes.pc_unit_id` FK **ON DELETE CASCADE**; CHECK `num_nonnulls(pc_unit_id, asset_id) = 1`. |
| Existing QR tables | `qr_codes`, `qr_scan_logs` (both baselined 2026-06-30). |
| `qr_codes` fields | `id, uuid, pc_unit_id, asset_id, code, payload, location_label, status, generated_at, last_scanned_at, created_at, updated_at`. |
| `qr_scan_logs` fields | `id, qr_code_id, pc_unit_id, asset_id, maintenance_record_id, scanned_by, scan_result, ip_address, latitude, longitude, scanned_at, created_at`. **No `uuid`. No `user_agent`.** |
| Existing QR permissions | None specific. `assets.update` (Administrator-only) via `manageQr`. |
| Existing QR frontend | Label management panel only. **There is no `/qr/:code` route in `frontend/src/App.tsx`** — that path currently falls to the `*` catch-all rendering `NotFoundPage` under `PublicLayout`. |
| Existing QR tests | 9 tests, generation/print/revoke only. **Zero scan tests.** |

## 6. Current authentication / authorization audit

### 6.1 Authentication architecture (must be reused — DD-47, "do not invent a parallel system")

- **Laravel Sanctum 4, SPA cookie auth, single origin.** `bootstrap/app.php` calls `$middleware->statefulApi()`, so `EnsureFrontendRequestsAreStateful` runs on the **whole** `/api` group — including public routes. A public scan endpoint will therefore see `$request->user()` when a session cookie is present, with no special wiring.
- **Middleware stack for feature routes:** `auth:sanctum` then `active` then `AuthenticateSession` then `password.current`.
- **CSRF:** stateful requests are CSRF-validated. The SPA client (`frontend/src/services/api.ts`) sets `withXSRFToken` and has a **419 to refresh-cookie to retry-once** interceptor, so a cold visitor's first `POST` self-heals.
- **Frontend redirect-back:** `ProtectedRoute` passes `state={{ from: location }}`; `SignInPage` reads `location.state.from.pathname` — **router state, never a URL query parameter**. This is the DD-48 shape already in place.
- **`GuestRoute` unconditionally redirects an authenticated visitor to `/app`** — SDD §24 already flags this as needing to learn about a pending scan.

### 6.2 Authorization architecture

- **Deny-by-default RBAC** via `Gate::before` calling `PermissionResolver` (Redis-cached).
- **Seeded matrix (§8.4 of the SRS) verified against `database/seeders/PermissionSeeder.php`** — they agree:

| Module | Administrator | Technician | Teacher |
|---|:--:|:--:|:--:|
| `assets.*` | all | **none** | **none** |
| `locations.*` | all | **none** | **none** |
| `maintenance.*` | all | **all** | **none** |
| `tickets.*` | all | view, update, comment | view, create, comment, vote |

- **Two established patterns for a shared permission:** `TicketVisibility` (DD-40) and `MaintenanceVisibility` (DD-55) — one service consulted by the policy *and* by every query, so a row absent from a list is unreachable by identifier.
- **No `wsr.*` or `qr.*` permission exists.** Inventing one would change the Client's §8.4 matrix (see §32, OD-4).
- `PcUnitPolicy` has **no `viewScanned` method** — DD-49 requires it.

### 8.3 Acceptance criteria that gate the package

- **AC-QR-006** — a revoked code scans as `expired` with no panel; an unknown code logs `invalid`.

### 8.4 Discrepancies found — reported, not resolved

**D-1 — The task brief refers to "React/Inertia architecture". The repository has no Inertia.**
The frontend is a standalone **React 19 with React Router 7 and TanStack Query 5** SPA consuming a **Laravel JSON API** over Sanctum SPA cookie auth, served single-origin behind nginx. `frontend/package.json` contains no Inertia dependency and `backend/` has no Inertia middleware or root view. **The instruction "do not create a separate frontend architecture" is honoured by following the existing SPA plus JSON API pattern.** This report plans accordingly. Flagged because the brief's wording, taken literally, would produce a wrong implementation.

**D-2 — The "six notification triggers" do not enumerate to six distinct dispatches.**

- SDD §26 lists: *"request submitted; administrator notified; approval with reschedule; clarification requested; decline with explanation; technician notified of the decision."* Items 1 and 2 are two halves of one event (a submission notified to administrators); items 3 to 5 are the three decisions and item 6 is their common recipient.
- FR-NOT-003's new clauses are **two**: submission to Administrators, and a decision (approved with a new schedule, clarification requested, or declined with a reason) to the submitting Technician. Plus the separately listed *"maintenance rescheduled"*.
- Concretely this is **four** recipient-distinct dispatches (one administrator-facing plus three technician-facing), or **five** counting `maintenance rescheduled`.

**Not silently resolved.** §21 proposes a concrete six and marks the sixth a recommendation. See §32, OD-5.

**D-3 — `ScanResult::Mismatch` has no representable trigger in the current schema.**
FR-QR-006 defines `mismatch` as *"code resolves but points to a different/moved target than claimed"*. `qr_codes` binds `pc_unit_id` directly and the scan URL carries **only** the code — there is **no caller-supplied claim** to compare against, and DD-48 forbids introducing one (nothing but the code may travel). As specified, `mismatch` is unreachable. **Not silently resolved.** See §32, OD-6.

**Minor observations (not discrepancies):**

- Route-file and `ActivityAction` comments label Maintenance *"Phase 2.7"*. This is **correct** under the CLAUDE.md offset (SPMP WP-2.6 equals conversational Phase 2.7). No action.
- SDD §24 asserts `qr_scan_logs.maintenance_record_id` *"already exists in the baseline schema"* — **verified true**.
- SDD §24's note that *"the current `GuestRoute` does exactly that [bounces to `/app`] and has to learn about the pending scan"* — **verified true** against `frontend/src/features/auth/guards/GuestRoute.tsx`.

## 9. WP-2.6b exact scope

**IN SCOPE — and nothing else.**

4. **Scan-scoped PC panel** — `ScannedPcUnitResource` under `PcUnitPolicy::viewScanned`. *(FR-QR-012, DD-49)*

6. **Scan-bound idempotency.** *(FR-MNT-012)*
7. **Work support requests** — entity, line items, submission, six-state transition map, technician withdrawal. *(FR-WSR-001/002/003/004/014, DR-020, DD-51/DD-54)*
8. **Administrator decision set** — approve-and-reschedule (propagating to `maintenance_records.scheduled_for`, prior value preserved in history, related ticket to a held state), request face-to-face (record, not calendar), decline with a **server-enforced required** reason. *(FR-WSR-006/007/008)*
9. **Both tracking surfaces** — technician submissions page, administrator request inbox, with navigation entries. *(FR-WSR-005/009/010)*
10. **Audit** — every transition to `activity_logs` with actor and before/after. *(FR-WSR-011)*
11. **Minimum notification infrastructure** — project `database` channel driver, dispatch service honouring `notification_preferences`, the workflow triggers. *(FR-WSR-012, FR-NOT-003 partial, DD-52)*
12. **Procurement bridge column only** — `procurement_request_id` on the request, no procurement logic. *(FR-WSR-013)*

## 11. QR identity design

### 11.1 Recommendation: no change to the QR data model. Keep `qr_codes.code` exactly as it is.

Evaluating the four options against the evidence:

| Option | Verdict | Reasoning |
|---|---|---|
| **Opaque random identifier** *(current)* | **Keep** | Already implemented, tested, printed on existing labels, and matching the OI-08 client decision (`/qr/{code}`). CSPRNG-backed, collision-checked, approximately 51 bits — resistant to enumeration when combined with FR-QR-013 rate limiting. |
| UUID | Reject | Longer, no security gain over 51 bits plus rate limiting, and worse for the human-transcribable label FR-QR-001 calls for. Would invalidate every printed sticker. |
| **Signed identifier** (Laravel signed URLs) | Reject | OI-08 explicitly weighed and rejected it: *"a signed token in a printed label cannot be rotated without reprinting every sticker."* Signing also adds nothing here — the code is not a capability (DD-47), so tamper-evidence protects nothing that authorization does not already protect. A tampered code simply fails to resolve and logs `invalid`. |
| Hashed / tokenized | Reject | Solves a problem the design does not have. The code is not a secret; authentication is the boundary. |

**A signed URL would provide integrity against URL tampering but does not replace authentication or authorization** — and since the design already treats the code as valueless without a session, the integrity it buys is redundant.

### 11.2 One recommended additive hardening (RECOMMENDATION, not a requirement)

`\d qr_codes` confirms **no database constraint enforces "one active code per target."** `QrService::generate()`'s idempotency is application-level; two concurrent requests could interleave between the `activeCodeFor()` read and the `issue()` insert.

**Recommendation:** two partial unique indexes in an additive migration:

```sql
CREATE UNIQUE INDEX qr_codes_one_active_per_pc_unit
  ON qr_codes (pc_unit_id) WHERE status = 'active' AND pc_unit_id IS NOT NULL;
CREATE UNIQUE INDEX qr_codes_one_active_per_asset
  ON qr_codes (asset_id)   WHERE status = 'active' AND asset_id IS NOT NULL;
```

This makes FR-QR-002's "the canonical scannable value" single-valued **by construction** and mirrors the existing `pc_component_installations_one_active_per_asset` and `technician_assignments_one_active_per_ticket` indexes. **Not specified in the current Version 1.0 documentation** as a requirement — offered as a recommendation. It must be preceded by a check for pre-existing duplicates (development holds 20 QR codes; a duplicate would fail the migration).

## 12. QR scan / authentication flow

### 12.1 The sequence (realizing SDD §24 and §35.4, DD-47, DD-48)

```
Phone camera -> http://<origin>/qr/{code}
       |
SPA public route /qr/:code  (QrLandingPage — outside ProtectedRoute)
       |
POST /api/qr/{code}/scan     [public route; statefulApi resolves the session if present]
       |
ScanQrCode service:
   - resolve code -> QrCode -> target
   - classify deterministically -> ScanResult
   - write qr_scan_logs (ALWAYS; scanned_by nullable)
   - update qr_codes.last_scanned_at on success
   - decide the answer FOR THIS CALLER
       |
Response (three shapes, nothing else):
   { next: "sign-in",  scan_id: null }              <- unauthenticated (whatever the classification)
   { next: "refused",  scan_id: null }              <- authenticated but unauthorized, OR bad code
   { next: "panel", scan_id: "<uuid>", code: "..." } <- authenticated AND authorized AND success
       |
   next=sign-in -> navigate("/sign-in", { state: { qrCode: code } })
                   + sessionStorage["sccit.pendingQrCode"] = code
       |  (sign in normally — no change to AuthService)
   GuestRoute / SignInPage: pending code present -> navigate(`/app/qr/${code}`)
       |
GET /api/qr/{code}/panel   [auth:sanctum + active + AuthenticateSession + password.current]
   -> authorize('viewScanned', $pcUnit)
   -> ScannedPcUnitResource
       |
/app/qr/:code -> ScannedPcPanelPage -> proof-of-work form + support-request form
```

### 12.2 Route placement (backend)

```php
// PUBLIC — outside auth:sanctum. statefulApi() still resolves the session
// when a cookie is present, so one endpoint serves both states.
Route::post('/qr/{code}/scan', [QrScanController::class, 'scan'])
    ->middleware('throttle:qr-scan')
    ->where('code', '[A-Za-z0-9-]{1,64}');   // shape-bounded, never a URL

// AUTHENTICATED — inside the existing stack, alongside maintenance.
Route::get('/qr/{code}/panel',  [QrScanController::class, 'panel']);
Route::post('/qr/{code}/proof', [QrProofOfWorkController::class, 'store']);
```

The `where()` constraint means a tampered value cannot even reach the controller as a path traversal or a URL. `POST` for `scan` follows SDD §24 verbatim.

### 12.3 Preserving the destination — only the code, never a URL (FR-QR-011, DD-48)

Two carriers, both code-only:

1. **Router state** `{ qrCode }` — the mechanism `ProtectedRoute` and `SignInPage` already use. Survives client-side navigation.
2. **`sessionStorage["sccit.pendingQrCode"]`** — survives a full page reload (a real risk: a phone user may reload the sign-in page).

**Both are validated before use** against the same regular expression the route enforces, and **the destination is rebuilt by the application** as `/app/qr/{code}`. The key is cleared immediately on consumption and on sign-out.

**Open redirect is unrepresentable, not merely blocked:** there is no code path that accepts a URL, a path, a host or a `redirect` parameter. The worst a tampered stored value can do is fail the regular expression (ignored) or fail to resolve (logged `invalid`). This is DD-48's "make it unrepresentable" stance.

### 12.4 Edge-case behaviour matrix

| Situation | Behaviour | Log | Response |
|---|---|---|---|
| Unauthenticated, valid active code | Send to sign-in | `success`, `scanned_by=null` | `next: sign-in`, **no target data** |
| Unauthenticated, unknown code | Send to sign-in — **indistinguishable** | `invalid`, `qr_code_id=null` | `next: sign-in` |
| Unauthenticated, revoked or inactive code | Send to sign-in — **indistinguishable** | `expired` | `next: sign-in` |
| Unauthenticated, target retired or disposed | Send to sign-in — **indistinguishable** | `expired` | `next: sign-in` |
| Authenticated Technician, authorized | Panel | `success`, `scanned_by=<id>` | `next: panel` plus `scan_id` |
| Authenticated Technician, **no work on that unit** | Refusal shown | `success` (the code resolved) | `next: refused` |
| Authenticated Teacher | Refusal | `success` | `next: refused` |
| Authenticated Administrator | Panel (unrestricted) | `success` | `next: panel` |
| Authenticated, revoked code | Refusal, **explicit** ("this label is no longer valid") | `expired` | `next: refused`, with reason |
| Session expired mid-flow | 401, `api.ts` clears the principal, `ProtectedRoute` sends to sign-in with the code preserved | logged on retry | resumes |
| Direct URL entry, no scan | **Identical to a scan** — the URL *is* the scan; there is no "was it really scanned" claim (FR-QR-013: a code is never proof of presence) | logged | same |
| Repeated scans | Each writes its own `qr_scan_logs` row; the panel is idempotent (a GET) | N rows | same |
| Browser refresh on the panel | Re-GETs the panel; no new scan row unless `/qr/:code` is re-entered | — | same |
| Back button from the panel to `/qr/:code` | Re-runs the scan (a genuine new attempt, correctly logged) | new row | same |

**The precise classification always reaches the log; the response never distinguishes.** Collapsing the two is exactly what turns a log into an enumeration oracle (SDD §35.4).

### 12.5 Session fixation

Handled by the existing architecture, unchanged: Laravel's `SessionGuard::login()` regenerates the session ID on authentication, and `AuthenticateSession` is already in the stack. **The scan flow must not create, adopt or carry any session identifier** — it carries a `code` only. No new surface.

### 12.6 Camera note (not a blocker)

`docker/nginx/security-headers.dev.conf` and `security-headers.prod.conf` set `Permissions-Policy: camera=()`. FR-QR-009 requires the workflow to work with the **phone's native camera app resolving the URL**, which needs no browser camera permission at all. **No header change is needed.** If an in-app scanner were ever wanted, that header would have to be relaxed; that is out of scope and flagged only so it is not discovered late.

## 13. PC-specific information model

### 13.1 The authorization boundary

`ScannedPcUnitResource` is a **third** projection, sitting between `AssetOptionResource` (label-only lookup) and `PcUnitDetailResource` (the Administrator's record). It is authorized by **`PcUnitPolicy::viewScanned`** and **never** by any `assets.*` permission (DD-49, DD-41, FR-AST-013).

### 13.2 `viewScanned` rule (RECOMMENDATION — the predicate is not spelled out in Version 1.0)

FR-QR-012 says *"A Technician's panel shall be limited to units reachable through their assigned work; an Administrator's is unrestricted."* It does not define "reachable". Recommended definition, derived from what the schema can prove:

Administrator                                              -> allow
Otherwise, the actor must hold maintenance.view OR tickets.update, AND at least one of:
  - an OPEN maintenance record on this pc_unit_id where technician_id = actor OR created_by = actor

Otherwise                                                  -> deny

This must live in **one service** consulted by the policy *and* by the panel query — the DD-40/DD-55 pattern — so "which units" cannot drift into two answers.

## 14. Proof-of-work workflow

### 14.1 The decision table (FR-MNT-009, DD-50, verified against WP-2.6 code)

| Question | Answer |
|---|---|
| Does proof create a `MaintenanceRecord`? | **No — the default and primary path is to attach.** |
| Does proof attach to an existing record? | **Yes** — the existing **active** record for the scanned unit that this technician is authorized to work. |
| Does proof attach to a Ticket? | **Indirectly** — through `maintenance_records.ticket_id`, which WP-2.6 already populates. No direct ticket write. |
| Is a record *ever* created here? | **Only** where WP-2.6 already permits technician-initiated corrective maintenance **and** the technician holds `maintenance.create`. Otherwise: **refuse with an explanation and create nothing** (AC-MNT-009). |
| How is technician ownership established? | `MaintenanceVisibility::canWork()` — the *same* call the maintenance module makes. Never re-derived. |
| How is PC identity established? | Server-side from the scanned `code` to `qr_codes.pc_unit_id`. **The client never supplies a PC identifier.** |
| What evidence is required? | At least one `repair_images` typed `before`/`during`/`after`, through `AttachmentSecurity::PROFILE_MAINTENANCE` (FR-MNT-010). |
| What text is required? | `resolution` — required for **every** maintenance type, already enforced by `MaintenanceLifecycle::completionBlockers()`. |
| How is completion status affected? | The submission may request completion; `MaintenanceLifecycle::transition(..., Completed, ...)` is the **only** path, so the existing gates (required checklist items, resolution, evidence for non-preventive types) apply unchanged. |
| Record already completed? | `canWork()` is false for `completed`, so **refused**. A further visit is a further record (WP-2.6 client decision). |
| PC under another active maintenance? | Permitted by design (WP-2.6 decision: preventive and corrective may coexist). The panel shows the actor's own record; if **more than one** is actor-workable, the submission must name which — see §32, OD-8. |
| Technician not assigned? | `canWork()` false, so refused. |
| QR revoked? | The scan is classified `expired`, the panel is refused, and the submission is never reachable. |
| QR belongs to a PC the technician cannot access? | `viewScanned` false, so refused; and the proof endpoint re-checks independently. |

### 14.2 Server-side sequence

```
POST /api/qr/{code}/proof   { scan_id, resolution, outcome, complete?, maintenance_id?, evidence[] }

DB::transaction:
  1. SELECT ... FOR UPDATE the qr_scan_logs row by scan_id
     (owned by the caller; belongs to this code; still 'success')
  2. If scan.maintenance_record_id IS NOT NULL  -> IDEMPOTENT REPLAY:
        re-target that same record, update it, DO NOT create or re-link
  3. Else resolve the actor-workable active record for qr.pc_unit_id
        - exactly one   -> use it
        - more than one -> 422, naming them (OD-8)
        - none          -> if the actor can('create', MaintenanceRecord) and the
                           workflow permits technician-initiated corrective work
                             -> CreateMaintenanceRecord (ticket_id from the actor's
                                open assignment on that unit, else null)
                           else -> 422 "no active maintenance record you may work",
                                   CREATE NOTHING
  4. Attach evidence via AttachRepairImage (PROFILE_MAINTENANCE)
  5. Apply resolution and outcome via UpdateMaintenanceRecord
  6. If complete=true -> MaintenanceLifecycle::transition(Completed) — gates apply
  7. Write qr_scan_logs.maintenance_record_id  (the DD-50 join)
  8. AuditLogger::activity(MaintenanceProofSubmitted, subject: record,
                           properties: { scan: <uuid>, code, evidence_count, ... })
```

**Nothing in this path duplicates WP-2.6.** Every write goes through an existing Action or the existing lifecycle.

## 15. Idempotency design

### 15.1 What FR-MNT-012 actually requires

> *"a repeated scan of the same code, a resubmission of the same scan, or a repeat submission against the same active record shall **update** that record rather than create a second one; the operation shall be idempotent **on the scan**"*

The idempotency boundary is therefore **the scan event**, not the HTTP request. DD-50: *"the technician taps submit twice on a bad signal and gets one record."*

### 15.2 Layered design (multiple layers, as the brief anticipates)

| Layer | Mechanism | Protects against | Enforcement |
|---|---|---|---|
| **L1 — Scan identity** | `qr_scan_logs.uuid` (**new additive column**) returned as `scan_id` | The client having no stable handle on the physical event | Schema |
| **L2 — Scan-to-record binding** | `qr_scan_logs.maintenance_record_id`, a single nullable FK, set once | Two records from one scan | **Column cardinality — structural** |
| **L3 — Concurrency** | `SELECT ... FOR UPDATE` on the scan-log row for the whole transaction | Double-click, double-tap, network retry, parallel requests | **Database row lock** |
| **L4 — Attach-only rule** | DD-50: creation only when *no* actor-workable active record exists, re-checked **inside** the locked transaction | Repeated scans manufacturing records | Application, under lock |
| **L5 — Lifecycle no-op** | `MaintenanceLifecycle::transition()` returns early when `from === target` | Spurious audit rows on a repeated complete | Existing code |
| **L6 — Frontend** | Disabled button plus TanStack Query mutation key | UX only | **Never the boundary** |

### 15.3 Why not a database unique constraint on "one open record per PC"

Because **WP-2.6 explicitly decided against it, with client approval.** `ConcurrentMaintenanceFinder`'s docblock:

> *"A unique index would be the obvious implementation and the wrong one: a machine may legitimately carry a scheduled preventive visit and an active corrective repair at the same time."*

Adding one now would contradict a recorded decision and break legitimate workflows. **L2 plus L3 give the database-enforced guarantee where it is well posed (per scan); L4 bounds the rest.** This is exactly the distinction `ConcurrentMaintenanceFinder` anticipated:

> *"Hard idempotency belongs to WP-2.6b, where it is well posed: a scan is a single physical event."*

The residual — two *different* scans by the same technician on the same unit in quick succession — is closed by L4, not by a constraint. §32, OD-8 records the remaining ambiguity.

### 15.4 Idempotency for work support requests

A different boundary, and simpler: an `Idempotency-Key`-style client token is **not** proposed. Instead the transition map (DD-54) makes every decision a **named operation with its own authorization**, and each transition asserts the current state under a row lock. A replayed `approve` on an already-`approved` request is refused by the map (`approved` reaches only `closed`), not silently re-applied. **No prior decision is overwritten in place** (FR-WSR-004).

## 16. QR scan logging design

### 16.1 Existing fields and their use

| Field | Written when | Value |
|---|---|---|
| `qr_code_id` | resolved | the code's id; `null` for an unknown code |
| `pc_unit_id` | resolved | denormalized target, so the log survives `qr_code_id` being nulled by a cascade |
| `asset_id` | resolved | as above |
| `maintenance_record_id` | on proof submission | the DD-50 join (L2) |
| `scanned_by` | always | actor id, **`null` when unauthenticated** (FR-QR-005) |
| `scan_result` | always | the **precise** `ScanResult` — never the response's answer |
| `ip_address` | always | `$request->ip()` |
| `latitude` / `longitude` | if supplied | optional, CHECK-validated |
| `scanned_at` | always | `now()` |

### 16.2 Answers to the audit questions

| Question | Answer |
|---|---|
| Does logging happen before or after authentication? | **Before.** The log is written by `ScanQrCode` before any authorization decision, and independently of it. |
| Is the scan logged when authentication fails or is absent? | **Yes — always** (FR-QR-005: *"record every scan attempt ... authenticated or not"*; AC-QR-010: *"the scan is logged with a null scanner"*). |
| Is the authenticated user recorded? | Yes, when a session exists. |
| Is PC/QR identity recorded? | Yes — both `qr_code_id` and the denormalized `pc_unit_id`/`asset_id`. |
| IP and user agent? | IP is required and present. **`user_agent` has no column and is not required by any FR.** A recommended additive column for parity with `activity_logs` and `login_history` — see §22. |
| Are duplicate scans logged? | **Yes, every one.** That is what makes an enumeration attempt visible (DD-47). |
| Relation to `activity_logs` | **Deliberately separate, no duplication.** `qr_scan_logs` records *attempts* (including anonymous ones and failures). `activity_logs` records *actor-initiated business events* (proof submitted, request decided). A scan alone writes **no** `activity_logs` row — it is not a business action, and duplicating it would double the audit surface for no gain. This mirrors the existing `login_history` versus `activity_logs` split. |

### 16.3 One additive change required

`qr_scan_logs` has **no public identifier**. The proof endpoint needs a stable, non-enumerable handle on a scan (L1 above). Every other public-facing table in this schema uses `uuid` — adding it is the codebase convention, not a novelty.

### 16.4 Rate limiting (FR-QR-013, NFR-SEC-009)

```php
RateLimiter::for('qr-scan', fn (Request $r) => [
    Limit::perMinute(config('security.rate_limits.qr_scan_per_minute', 20))
        ->by($r->ip() ?? 'unknown'),                                      // per client
    Limit::perMinute(config('security.rate_limits.qr_scan_per_user_per_minute', 30))
        ->by((string) ($r->user()?->getKey() ?? $r->ip() ?? 'unknown')),  // per account
]);
```

FR-QR-013 requires **both** *"per client and per account"* — Laravel supports an array of limits on one limiter. Values belong in `config/security.php` beside the existing ticket limits.

## 18. Administrator decision workflow

### Decision A — Approve and reschedule (FR-WSR-006)

```
POST /api/admin/work-support-requests/{uuid}/approve
     { rescheduled_to (required, ISO8601, future), reschedule_reason? }
```

In one transaction:

1. Assert `submitted` or `clarification_requested` under a row lock.
2. Write `status=approved`, `decided_by`, `decided_at`, `rescheduled_to`, `reschedule_reason`.
3. **If a maintenance record is linked:** update `maintenance_records.scheduled_for`, capturing the **previous value into `activity_logs.properties`** (never overwritten silently) and emitting `ActivityAction::MaintenanceRescheduled` — the verb already exists.
4. **If a ticket is linked:** move it to a **held or awaiting** state via `TicketLifecycle`, never to resolved or closed. See §32, OD-2 — the existing transition map has **no `open` to `on-hold` edge**.
5. `AuditLogger::activity(WorkSupportRequestApproved, ...)`.
6. Notify the submitting technician (T2) plus the maintenance-rescheduled notification (T5).

### Decision B — Request face-to-face explanation (FR-WSR-007, OI-10)

```
POST /api/admin/work-support-requests/{uuid}/request-clarification
     { clarification_reason (required), proposed_meeting_at? }
```

**Records the request, not a calendar** — no availability, no invitations, no reminders (OI-10 decision). Status becomes `clarification_requested`, visible to the technician on their tracking page with the message. Notify (T3).

### Decision C — Decline (FR-WSR-008)

```
POST /api/admin/work-support-requests/{uuid}/decline
     { decline_reason (required, non-empty after trim) }
```

**Three independent layers refuse a reasonless decline:**

1. FormRequest — `required|string|min:1` with a trim rule.
2. The transition service — re-asserts before writing (safe when called from a job or command with no request).
3. **The database** — DR-020: *"A decline shall be refused at the database level as well as the application level when no reason is present."*

```sql
CHECK (status <> 'declined' OR (decline_reason IS NOT NULL AND btrim(decline_reason) <> ''))
```

The technician sees the decline, the reason, the PC unit, the job context and the status (FR-WSR-008).

### Do administrator decisions need separate entities?

**No — RECOMMENDATION: reuse `activity_logs`.** The decision *fields* live on the request row (DR-020 names them); the decision *history* lives in `activity_logs` via the subject morph, exactly as the maintenance `/audit` endpoint already serves. This is DD-55 restated. Introducing a `work_support_request_decisions` table would create a second place for the truth to live.

## 19. Technician tracking workflow

**Route:** `/app/my-submissions` · **Navigation label:** "My submissions" · **Gate:** `maintenance.view` (see OD-4)

## 21. Notification scope

### 21.1 What WP-2.6b builds (SDD §26 "Sequencing", client-approved)

1. **The project `database` channel driver** (DD-52) — writes `App\Models\Notification` with `user_id`, enum `type`, NOT NULL `title`, `message`, `data` jsonb, `action_url`, `read_at`. Registered via the channel manager in a service provider. **Laravel's stock `DatabaseChannel` is not used and would fail on the first insert.**
2. **`NotificationService`** — consults `notification_preferences` (unique per user, channel, type) **before** dispatch (FR-NOT-002). Since the preferences UI is WP-2.7, the **default when no row exists is enabled** for `in_app` and enabled for `email`. See OD-5.
3. **The workflow triggers**, as queued notification classes (`ShouldQueue`, redis — the queue containers are already running in both stacks).

### 21.2 The concrete trigger list

**§8.4 D-2 applies**: the documentation's "six" does not enumerate to six distinct dispatches. Proposed concrete set:

| # | Trigger | Recipient | Type | Documented? |
|---|---|---|---|---|
| T1 | Work support request **submitted** | All Administrators | `maintenance` | Yes — FR-NOT-003, FR-WSR-012 |
| T2 | Request **approved** with a new schedule | Submitting Technician | `maintenance` | Yes — FR-NOT-003, FR-WSR-012 |
| T3 | **Clarification requested** | Submitting Technician | `maintenance` | Yes — FR-NOT-003, FR-WSR-012 |
| T4 | Request **declined** with reason | Submitting Technician | `maintenance` | Yes — FR-NOT-003, FR-WSR-012 |
| T5 | **Maintenance rescheduled** (the propagated `scheduled_for` change) | Assigned Technician | `maintenance` | Yes — FR-NOT-003 |
| T6 | Request **cancelled or withdrawn** by the technician | All Administrators | `maintenance` | **RECOMMENDATION — not a requirement.** Without it an administrator's inbox holds a stale pending item. |

**`NotificationType` mapping — RECOMMENDATION:** reuse the existing `maintenance` case for all six. FR-NOT-005 fixes the type set to nine values, and `notifications.type` is `varchar` plus a `CHECK`, so a new case would require both a migration **and** a requirement change. Reuse avoids both.

### 21.3 Delivery, persistence, failure

- **Channels:** `in_app` (always, subject to preference) plus `email` (subject to preference). The mail transport is Mailpit in both stacks.
- **Persistence:** rows in `notifications` with `read_at` null; the `notifications_unread` partial index already exists.
- **Read/unread:** `read_at` is written; **no read/unread UI and no mark-read endpoint** — FR-NOT-004's surface is WP-2.7.
- **Queue:** redis, `ShouldQueue`.
- **Retry:** Laravel defaults (`tries`, backoff) — recommend `tries = 3` with backoff.
- **Failure:** **a notification failure must never fail the business transaction.** Dispatch **after commit** (`DB::afterCommit` or the queue's `afterCommit` option), so a mail outage cannot roll back an administrator's decision. Failures land in `failed_jobs`.

### 21.4 Explicitly NOT built

Notification centre UI, unread badge, mark-read endpoints, preferences screen, digest, Reverb push, announcements. **All WP-2.7 or WP-4.1.**

## 26. Security threat model

| # | Threat | Mitigation | Where enforced |
|---|---|---|---|
| 1 | **QR cloning** (photograph a sticker) | The code is an identifier, never a credential (DD-47). A cloned code grants exactly nothing without a session **and** authorization for that unit. | `viewScanned`, server |
| 2 | **QR URL tampering** | Route regex `[A-Za-z0-9-]{1,64}`; a tampered code resolves to nothing, logging `invalid` and returning a non-disclosing refusal. No signature needed because possession confers nothing. | Route plus `QrScanResolver` |
| 3 | **PC identifier enumeration** | The scan URL never carries a PC UUID — only the opaque code (~51 bits). Rate-limited per IP **and** per account. Unknown, revoked and retired answer **identically**. | `throttle:qr-scan`, response shaping |
| 4 | **IDOR** (maintenance, request, evidence, PC) | One visibility service per domain, consulted by policy **and** query. Children addressed **through** their parent (`/{record}/evidence/{image}` 404s on mismatch — the existing pattern). | `MaintenanceVisibility`, `WorkSupportRequestVisibility`, `ScannedPcAccess` |
| 5 | **Unauthorized technician access** | Scanning a unit with no assigned work is refused (AC-QR-012). Re-checked on the panel **and** independently on every submission. | `viewScanned` |
| 6 | **Teacher access** | Teachers hold no `maintenance.*`, so they are refused at the route gate before any policy runs. Tested per role. | Route `can:` plus policy |
| 7 | **Revoked QR reuse** | `status='revoked'` classifies as `expired`; the panel is refused and the submission unreachable (AC-QR-006). | `QrScanResolver` |
| 8 | **Expired QR** | Status-based, not date-based (FR-QR-006, OI-04). Also `expired` when the target is `retired` or `disposed`. | `QrScanResolver` |
| 9 | **Replayed submissions** | Scan-bound idempotency L1 to L3 (§15). A replay updates the same record. | `qr_scan_logs.uuid` plus `FOR UPDATE` |
| 10 | **Duplicate submissions** | The same; plus the attach-only rule (L4) and the lifecycle no-op (L5). | §15 |
| 11 | **Open redirect** | **Unrepresentable.** Only a `code` travels; the application rebuilds `/app/qr/{code}`. No `redirect` parameter, no stored URL, no referrer use, client **and** server (DD-48, AC-QR-010). | `pendingScan.ts`, `SignInPage` |
| 12 | **CSRF** | `statefulApi()` plus `ValidateCsrfToken` on all stateful `/api` requests; `withXSRFToken` and the 419-retry in `api.ts`. Every WSR decision is a `POST`. | Existing middleware |
| 13 | **Session fixation** | Laravel regenerates the session ID on login; `AuthenticateSession` is already in the stack. **The scan carries no session identifier.** | Existing |
| 14 | **Privilege escalation** | No new permission is granted. `viewScanned` is a *narrower* ability than `assets.view`, granted by the *workflow's* permission (the FR-AST-013 pattern). Scanning never widens anything. | Policy design |
| 15 | **Forged technician identity** | `technician_id` is `$request->user()`, never a request field. Ownership is `MaintenanceVisibility`'s existing predicate. | Actions |
| 16 | **Forged maintenance identifier** | The record is resolved **server-side from the scanned code**, not supplied. Where `maintenance_id` disambiguates (OD-8), it is re-validated through `canWork()`. | `SubmitProofOfWork` |
| 17 | **Forged support-request identifier** | UUID route key plus `WorkSupportRequestVisibility` gives **404** for another technician's request (AC-WSR-008). | Policy plus query |
| 18 | **Attachment / evidence abuse** | `AttachmentSecurity` — the **single** trust boundary (DD-45/DD-53). **No weaker QR-specific upload path is created.** | `AttachRepairImage` |
| 19 | **Malicious file upload** | Server-side `finfo` detection against `PROFILE_MAINTENANCE` (png/jpeg/webp/pdf); `getClientMimeType()` never read; server-composed storage path; SHA-256 stored; size ceiling. | `AttachmentSecurity::detect()` |
| 20 | **Unauthorized evidence download** | Private disk with no public URL; the policy is re-checked per request; the image must belong to the named record or 404; `Content-Type` re-derived, PDFs forced to `attachment`, `nosniff` plus `default-src 'none'; sandbox`. | `AttachmentSecurity::stream()` |
| 21 | **Request-status tampering** | **No status field is ever accepted.** Each transition is a named endpoint with its own FormRequest and ability; the map decides (DD-54, AC-WSR-008). | `WorkSupportRequestLifecycle` |
| 22 | **Administrator-decision tampering** | `decided_by` and `decided_at` are written server-side; terminal states have no outbound edges; every transition is audited with before/after; a superseded schedule stays in `activity_logs`. | Lifecycle plus `AuditLogger` |

## 30. Recommended implementation order

## 32. Open decisions

### MUST DECIDE BEFORE IMPLEMENTATION

**OD-1 — Approve the DR-020 schema (§22 M2/M3).**
DR-020 states the exact schema *"shall be proposed and approved before implementation."* §22 is that proposal. **Not a discretionary call** — the documentation requires the approval.

**OD-2 — Which ticket state is the "held or awaiting" state, and what happens when the ticket is `open`?**
*Not specified in the current Version 1.0 documentation.* FR-WSR-006 requires the related ticket to *"move to a held/awaiting state rather than being resolved or closed"* but names no slug. The seeded statuses include `on-hold`, and `TicketLifecycle` permits `assigned` to `on-hold` and `in-progress` to `on-hold` for an administrator — but there is **no `open` to `on-hold` edge**.
**RECOMMENDATION:** use `on-hold`; when the linked ticket is `open` (not yet assigned), **leave it unchanged and record why in `activity_logs`** rather than adding a transition edge. Adding `open` to `on-hold` would change a WP-2.6 transition map that was verified and shipped.

**OD-3 — Where does work-support-request evidence live?**
*Not specified in the current Version 1.0 documentation.* FR-WSR-002 and FR-WSR-003 permit optional evidence through the single attachment boundary; **DR-020's entity list contains no attachment child table.**
**RECOMMENDATION:** add `work_support_request_attachments`, mirroring `asset_attachments`, reusing `AttachmentSecurity::PROFILE_MAINTENANCE` — no new profile, no new upload path (DD-45/DD-53). *(Alternative: defer evidence to a later package and refuse uploads for now — clean, but it narrows FR-WSR-002.)*

**OD-4 — Which permission floors the work-support-request surfaces?**
*Not specified in the current Version 1.0 documentation.* No `wsr.*` permission exists in the §8.4 matrix, and inventing one would change the Client's matrix.
**RECOMMENDATION:** technician surfaces gated on `maintenance.view` / `maintenance.update` (the consuming workflow's own permission — the FR-AST-013 pattern); the administrator surface gated on `maintenance.view` **plus** a role check in `WorkSupportRequestPolicy::viewAdministrative`, exactly as `MaintenanceDirectoryController` already does. **No new permission is created.**

### CAN BE DECIDED DURING IMPLEMENTATION

**OD-5 — The concrete notification trigger list and the default preference.**
See §8.4 D-2. **RECOMMENDATION:** the six of §21.2 (T6 flagged as a recommendation and droppable), all mapped to the existing `NotificationType::Maintenance`, with **enabled-by-default** when no `notification_preferences` row exists (the preferences UI is WP-2.7, so a default of *disabled* would silently deliver nothing).

**OD-6 — What to do about `ScanResult::Mismatch`.**
See §8.4 D-3. **RECOMMENDATION:** implement the other three classifications; document `mismatch` as **reserved** — reachable only if a future design introduces a claimed target (which DD-48 currently forbids). Do **not** manufacture a claim parameter to make the enum case reachable; that would reintroduce caller-supplied state into the scan.

**OD-7 — Do serial number, MAC, IP, hostname and asset tag belong on the scan panel?**
*Not specified in the current Version 1.0 documentation.* FR-QR-012's approved list names *"the PC unit identifier and name"* and *"the relevant technical specification"*; these five fields sit between the two.
**RECOMMENDATION:** include `unit_code` (the identifier the technician reads off the label) and **exclude** serial number, MAC, IP, hostname and asset tag — they are register data, not repair data, and DD-49's "no field exists" stance is cheaper to widen later than to narrow after a leak.

**OD-8 — What happens when a technician has more than one actor-workable active record on a scanned unit?**
*Not specified in the current Version 1.0 documentation.* WP-2.6 deliberately permits concurrent records on one machine.
**RECOMMENDATION:** the panel lists them; the proof submission **requires** a `maintenance_id` naming one, re-validated through `canWork()`. Submitting without one when several exist returns **422 naming the candidates**. Never guess — a guess would attach evidence to the wrong job.

**OD-9 — Who closes an approved or declined request, and when?**
*Not specified in the current Version 1.0 documentation.* FR-WSR-004 says only that `closed` *"records that the request is finished or its job has completed."*
**RECOMMENDATION:** an Administrator may close explicitly; **and** a request auto-closes when its linked maintenance record reaches `completed` or `cancelled`, the transition audited with `system` as the actor — the `TicketLifecycle` `ACTOR_SYSTEM` precedent.

### DEFERRED

**OD-10 — `qr_codes.expires_at` / time-based expiry.** SRS **OI-04, still open.** `expired` stays status-based (FR-QR-006). Out of scope.

**OD-11 — In-app camera scanner.** Not required by FR-QR-009 (the native camera resolves the URL). Would require relaxing `Permissions-Policy: camera=()`. Deferred.

**OD-12 — Surfacing scan history in the UI.** No FR requires a scan-history *surface*; FR-QR-005 requires the *log*. Deferred to WP-2.7 or reporting.

**OD-13 — The `qr_codes` one-active-per-target partial unique index (§11.2, M5).** A recommended hardening, not a requirement. Deferrable to a later hardening pass if the Client prefers a minimal migration set.

## 33. Final WP-2.6b implementation recommendation

**Proceed — after OD-1 through OD-4 are decided.**

The package is unusually low-risk for its size, because three things are already true:

1. **The documentation is complete and the decisions are made.** OI-08 to OI-11 are resolved; DD-47 to DD-54 and DD-57 specify the design; DR-020, UCS-11 and four acceptance criteria define done. Very little needs inventing — and §32 lists honestly the thirteen places where something does.
2. **The foundations are built and verified.** QR generation, the attachment trust boundary, `MaintenanceVisibility`, `MaintenanceLifecycle` with its completion gates, `AuditLogger`, the RBAC gate, the SPA authentication flow. WP-2.6b is mostly *composition*, not construction. `MaintenanceLifecycle`'s own docblock anticipates this caller by name.
3. **The patterns to follow are established and proven twice.** DD-40 (Tickets) and DD-55 (Maintenance) give the row-scope shape; DD-43 and DD-54 give the transition-map shape; DD-45 and DD-53 give the upload shape. WP-2.6b introduces **no new architectural pattern** — three new services, each with a named precedent and a stated reason.

**The one genuinely new thing is the authorization surface**: a Technician reaching a PC unit outside the Administrator-only Asset module, through an ability that no `assets.*` permission grants. That is why the SPMP split this package out, and why **§30 places a hard approval gate immediately after sub-WP C**, before any UI is built on top of it.

**Two things recommended against**, both because a recorded decision already rules them out:

- A **signed or tokenized QR payload** — OI-08 weighed it and rejected it; a signed token in a printed sticker cannot be rotated without reprinting the estate, and the code is not a capability anyway.
- A **database unique constraint** to enforce "one maintenance record per job" — WP-2.6 decided, with Client approval, that a machine may legitimately carry concurrent records. §15's layered design gives the database-enforced guarantee where it is well posed (per scan) and bounds the rest with the attach-only rule.

**Honest limitation to carry into the completion report:** production holds **zero PC units, assets, QR codes and maintenance records**. Structural parity (migrations, routes, containers, build, configuration, channel registration) is verifiable there; record-level QR, proof-of-work and work-support behaviour is verifiable **only in development** unless the Client explicitly authorizes seeding production.
