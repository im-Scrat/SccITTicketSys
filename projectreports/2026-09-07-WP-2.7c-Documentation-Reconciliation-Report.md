## 2. SRS changes

**§22.1 Announcements — the passage that was factually wrong.** It read:

> *Implementation status — not implemented; deferred to WP-2.7c … No
> announcement domain code, publishing surface or trigger exists.*

Replaced with a satisfied status that records what was built:

- **FR-NOT-010 — satisfied.** Administrators holding
  `system.announcements.manage` create, edit, publish, withdraw, re-notify and
  delete announcements targeted at `all` / `teachers` / `technicians` /
  `admins`, with the optional window and pin flag. Records that **publication is
  a named operation, not a writable field** — `is_active` cannot be set by any
  request body, so no edit can notify an audience as a side effect — and that
  creating an announcement produces a **draft**.
- **FR-NOT-011 — satisfied.** The reader at `/app/announcements` lists the
  announcements addressed to the caller, pinned first, with a per-announcement
  page reachable from the notification.
- **Decision D5 (2026-09-05), as implemented.** All four pre-recorded
  constraints are marked met, with the audience constraint strengthened to what
  the code actually guarantees: one visibility rule answers both the list
  question and the single-record question, so an announcement absent from a
  reader's list is **equally unreachable by its uuid**.
- **How the no-email guarantee is enforced** — added, because this is the part
  the pre-implementation text could not have known. Preferences are opt-out, so
  the gate alone could not deliver it; the guarantee lives in the dispatch path
  ([SDD DD-66](#)). Explicitly records that it was **not** solved by seeding
  preferences.
- **Plain text, no attachments, no external URLs, no read receipts** — recorded,
  with read/unread state remaining owned by the notification system.
