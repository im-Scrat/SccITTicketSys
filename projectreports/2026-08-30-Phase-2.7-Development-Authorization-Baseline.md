## 3. D1 Resolution — Notification Preference Storage

**Your decision — a dedicated `notification_preferences` model rather than
columns on `users` — is confirmed correct and already supported by the baselined
schema.**

### Exact fields (live production schema)

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | bigint | NO | identity |
| `user_id` | bigint | NO | — |
| `channel` | varchar | NO | — |
| `notification_type` | varchar | NO | — |
| `is_enabled` | boolean | NO | **`true`** |
| `created_at` / `updated_at` | timestamptz | YES | — |

### Relationship to users

`notification_preferences_user_id_foreign` → `users(id)` **ON DELETE CASCADE**.
Preferences are owned by the user and disappear with them — no orphan rows, and
no cleanup step required.

### Defaults

`is_enabled` defaults to **`true`**, which makes this an **opt-out** model: a
user receives everything until they turn something off, and an absent row means
*enabled*. The service must treat "no row" as enabled rather than as disabled,
or every notification will be silently suppressed for every user who has never
visited the preferences screen.

### Per-channel? Yes — and per-type

`UNIQUE (user_id, channel, notification_type)` with two CHECK constraints:

- `channel` ∈ `in_app`, `email`
- `notification_type` ∈ `info`, `success`, `warning`, `error`, `ticket_update`,
  `assignment`, `announcement`, `maintenance`, `system`

Preferences are therefore a **user × channel × type** matrix — 2 × 9 = up to 18
rows per user. This is finer-grained than "email on/off" and matches FR-NOT-002
exactly.

### Digest opt-in — **the constraint you need to see**

You directed that digest opt-in live in `notification_preferences`. **That is
sound, but it cannot be done today without a schema change**, because:

- `digest` is **not** a valid `channel` (CHECK allows only `in_app`, `email`), and
- there is **no** `digest` value in `NotificationType` (9 cases, none of them digest).

So a digest preference row cannot currently be inserted. Three honest options:

| Option | Change | Assessment |
|---|---|---|
| **A** | Add `digest` to the `channel` CHECK + `NotificationChannel` enum | Cleanest conceptually — digest *is* a delivery channel. One additive migration. **Recommended** |
| **B** | Add a `digest` value to `NotificationType` | Wrong shape — digest is not a kind of notification, it is a delivery mode |
| **C** | A `users.digest_enabled` column | Contradicts your D1 decision |

**Recommendation: Option A**, and it should be an explicit approval rather than
an implementation detail, because it widens a CHECK constraint on a baselined
table.

### SRS conflict

**Yes — one.** FR-NOT-008 says the digest is controlled by
**`notifications.digest_enabled`**. That column does not exist on
`notifications` (columns: `id, uuid, user_id, type, title, message, data,
action_url, read_at, created_at`), and your decision places the setting
elsewhere regardless. The SRS wording is wrong on both counts.

### Reconciliation required

**Yes, after implementation:** amend FR-NOT-008 to name the real location; add an
SDD `DD-` entry recording the digest-as-channel decision; note the CHECK widening
in the SPMP work-package row. **Version stays 1.0**, amended in place.

## 11. Security and Disclosure Rules

Binding rules for WP-2.7a, derived from the matrix:

1. **A notification may never contain data the recipient's own visibility rules would withhold.** Content is filtered per recipient, not per event.
2. **Internal ticket comments never notify a teacher.**
3. **Maintenance notifications carry only the FR-QR-012 approved operational field list** — never price, supplier, warranty or procurement data.
4. **Announcement audience is an authorization boundary**, not a display filter.
5. **Lockout notifications disclose the lockout and duration only** — never source IP or attempt detail.
6. **Email content carries no secrets and minimal PII** (FR-NOT-006) — it leaves the system boundary.
7. **The actor is not notified of their own action.**
8. **Queue payloads carry identifiers, not sensitive content** — payloads persist in Redis.
9. **Preference endpoints take no user identifier** — they read the session, following the `TechnicianSubmissionController` precedent.

Each rule gets a test. Rule 1 gets a dedicated per-role disclosure test file,
matching the project's "negative cases, role by role" convention.
