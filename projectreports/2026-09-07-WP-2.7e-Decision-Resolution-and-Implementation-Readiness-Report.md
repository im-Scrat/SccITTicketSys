## 3. Database scope

**Approved scope expansion, stated explicitly as required.** DD-63's original
design was *"one constraint widened"* on a table then holding zero rows. Decision
**E** enlarges that to:

> **one widened CHECK constraint + one new table.**

This is a deliberate, owner-approved expansion beyond DD-63 as written, and DD-63
must record it when amended (§10).

**Delta 1 — widen the channel domain.**

```
notification_preferences_channel_check
  channel IN ('in_app','email')  ->  channel IN ('in_app','email','digest')
```

Additive (strict superset), non-destructive, reversible only with a data step,
`up()` re-runnable, and compatible with existing rows — dev holds 1 row
(`email`), production 0. The repository already contains the exact technique in
`2026_08_26_100000_extend_asset_status_domain.php`: `DROP CONSTRAINT IF EXISTS`
then `ADD CONSTRAINT … CHECK (col IN (…))` driven from the enum's `::values()`,
with a `down()` that normalises offending rows first. WP-2.7e should follow it
rather than invent a pattern.

**Delta 2 — `notification_digests`.**

| Column | Type | Note |
|---|---|---|
| `id` | bigint identity | Project convention |
| `user_id` | bigint, NOT NULL | FK → `users(id)` **cascade**, matching `notifications` and `notification_preferences` |
| `digest_date` | **`date`** | The **Manila calendar day being summarised** — not the delivery date (§5) |
| `sent_at` | `timestamptz` **nullable** | NULL = claimed but unconfirmed; NOT NULL = delivered |
| `created_at` / `updated_at` | `timestamptz` | `timestampsTz()`, project convention |

```
UNIQUE (user_id, digest_date)   -- the authoritative guarantee
```

A `uuid` column is **not** proposed: the project adds one where a record is
addressable over the API (`HasUuidRouteKey`), and this table is never exposed —
consistent with `notification_preferences`, which also has none.

Migration ordering: this becomes migration **#32**; repo/dev currently hold 31.

## 4. Notification semantics

**What the digest is.** A per-user email aggregating that user's **unread**
notifications created within the previous Manila calendar day. It creates **no
notification row**, produces **no badge count**, and has **no in-app surface**.

**Eligibility, resolved:**

| Question | Resolution | Source |
|---|---|---|
| Which users? | All three roles, **active accounts only**, soft-deleted excluded | G + `NotificationAudience` convention |
| Which items? | The user's own rows, `read_at IS NULL`, `created_at` inside the window, whose `type` has `digest × type` enabled | C |
| Does `email` off disable it? | **No** | C |
| Nothing eligible? | Send nothing, write nothing | D |
| Read before the run? | Excluded — unread is evaluated at run time, which is the plain reading of "aggregating unread items" | FR-NOT-008 |

**Content is constrained by existing rules, not by choice.** DD-61 confines
notifications to structural facts, and `ProjectNotification::mailLines()`
deliberately omits `payload['message']` because "that is where quoted human text
lives and that is exactly what must not be mailed." Therefore **the digest lists
titles and never messages**. Links must be absolute URLs built from `app.url`;
DD-65's `/app/` prefix gate is a *client-side navigation* rule and does not
transfer to an email.

**One structural note.** `notifications.created_at` is nullable. All 605 rows in
dev have it set, and the dispatcher always sets it, but a half-open
`created_at >= start AND created_at < end` filter would silently exclude a NULL
row. That is the correct behaviour; it is recorded so it is a decision rather
than an accident.

## 5. Timezone semantics

Verified in **both** PostgreSQL and PHP/Carbon, which agree exactly.

For a digest delivered **2026-09-08 07:00 Asia/Manila**, summarising the previous
Manila calendar day **2026-09-07**:

```
window start   2026-09-07T00:00:00+08:00  =  2026-09-06T16:00:00Z   (inclusive)
window end     2026-09-08T00:00:00+08:00  =  2026-09-07T16:00:00Z   (exclusive)
delivery       2026-09-08T07:00:00+08:00  =  2026-09-07T23:00:00Z
digest_date    2026-09-07                 (the day summarised)
```

The window is **half-open `[start, end)`** — the boundary rule decision B
requires to be explicit and tested. The day closes **seven hours before**
delivery, so the summarised day is fully settled when the digest runs.

`Asia/Manila` is **UTC+8 with no DST**, so these offsets are stable year-round
and no daylight-saving branch is needed.

**A caution worth stating, because it is easy to get backwards.** During this
check, `date '2026-09-07' AT TIME ZONE 'Asia/Manila'` returned
`2026-09-07 08:00` — the *wrong* direction, because `date` resolved to the
`timestamptz` overload. The correct form is
`(timestamp '2026-09-07 00:00:00' AT TIME ZONE 'Asia/Manila')`. This is precisely
why B demands explicit boundary tests, and the tests should assert the UTC
instants above literally.

**Where the timezone value lives.** Settings are read with a plain query at point
of use (`SystemSetting::query()->where('key',…)->value('value')`) — there is no
cache or config binding. `routes/console.php` is loaded on **every** artisan
invocation, so reading the setting there would put a database query in the boot
path of `migrate`, `queue:work` and every test — and would fail outright during
`migrate:fresh` before the table exists.

Recommended, consistent with A's "explicitly use the school timezone": a
**literal** `->timezone('Asia/Manila')` on the schedule entry, with
`system_settings['system.timezone']` documented as its authority, plus a test
asserting the literal still equals the seeded setting so the two cannot drift
silently. Runtime window computation inside the command may read the setting
normally.

## 6. Scheduler semantics

Defined in `backend/routes/console.php`; executed by dedicated `scheduler` /
`scheduler_prod` containers running `php artisan schedule:work`. No host cron.

Proposed entry, matching the three existing jobs' house style:

```php
Schedule::command('notifications:send-digest')
    ->dailyAt('07:00')
    ->timezone('Asia/Manila')
    ->withoutOverlapping()
    ->onOneServer();
```

`onOneServer()` requires a shared lock store — `cache.default = redis`, satisfied.
`withoutOverlapping()` prevents a slow run colliding with the next; neither guard
prevents a *second successful* run, which is why E's table is the actual
guarantee.

**Queue.** `queue.default = redis`; workers run
`queue:work --tries=3 --backoff=5 --max-time=3600 --sleep=3`. **No queue change
is required.** Note that `--tries=3` makes retry a certainty rather than a
possibility, which is the whole reason E's guarantee must be in the database.

*Observation, unchanged from planning:* `failed_jobs` holds 27 rows dated
2026-08-27 → 2026-09-05, all `ChannelManager::$app` — WP-2.7a-era development
residue in the dev database. Not touched, not a WP-2.7e concern.

## 7. Idempotency design

Decision E gives the guarantee a home. The mechanism that satisfies every clause
of E is **claim → send → confirm**, and it is the reason E specifies both
`created_at` *and* `sent_at`:

1. **Claim.** `INSERT INTO notification_digests (user_id, digest_date) … ON CONFLICT DO NOTHING`.
   The unique index makes the claim atomic: concurrent or repeated runs cannot
   both claim the same `(user_id, digest_date)`. A claim that inserts 0 rows means
   somebody already holds it.
2. **Send.** Deliver the email.
3. **Confirm.** `UPDATE … SET sent_at = now()`.

**Eligibility rule:** a user is eligible when **no row exists** for that
`digest_date`, or a row exists with **`sent_at IS NULL`** (a prior attempt that
never confirmed). A row with `sent_at` set is never re-sent.

This satisfies E's five named scenarios outright:

| Scenario | Outcome |
|---|---|
| Scheduler runs twice | Second run's claim conflicts → skipped |
| Command invoked manually twice | Same |
| Worker retries (`--tries=3`) | Same |
| Container restarts | Claim survives in Postgres |
| Application redeployed | Same |

**Handled send failures stay retryable.** If SMTP throws, the command catches it
per recipient (the DD-59 isolation posture), leaves `sent_at` NULL — or releases
the claim — and that user is eligible again, while the rest of the run continues.

`digest_date` is the **Manila calendar day summarised** (2026-09-07 for the
2026-09-08 07:00 delivery). Using the delivery date instead would make the key
ambiguous across a re-run near midnight.

The single case this does **not** cover is raised in §13.

single migration keeps `up()`/`down()` symmetric for a feature that is
meaningless with only half of it applied.

## 13. Remaining unresolved decisions

**One, and it is narrow.** Two clauses of decision E cannot both hold absolutely,
because SMTP is an external system that cannot enlist in a database transaction:

> "the idempotency record is only considered successfully sent **after** the email
> has actually been accepted/sent"

> "A successful recipient must **never** receive a duplicate digest … even if …
> a container restarts"

The claim→send→confirm design (§7) satisfies every scenario E names **except one
irreducible window**: an unhandled crash (SIGKILL, container death, OOM) between
*SMTP accepting the message* and *`sent_at` committing*. In that window the row
reads unconfirmed, so a retry re-sends — one duplicate.

Ordinary, *handled* failures are fully solved and stay retryable, exactly as E
requires. Only an abrupt process death in a sub-second window is at issue.

**The choice:**

| Option | Behaviour in the crash window | Trade |
|---|---|---|
| **(i) Confirm before sending** — set `sent_at` at claim time | **At-most-once.** Never duplicates; a crash means that user silently misses one day's digest | Favours "never duplicate", which E states most emphatically and repeats five times |
| **(ii) Confirm after sending** — as §7 | **At-least-once.** Never silently skips; may duplicate once in the crash window | Favours literal compliance with "only considered sent after the email has been accepted" |

**Recommendation: (i).** E's own words — "The database constraint is the
authoritative guarantee" — and the five enumerated no-duplicate scenarios read as
a clear preference for never duplicating over never missing. A missed digest is
recoverable next day; a duplicate school-wide mailing is not.

This does **not** block implementation of anything else: stages e-1 through e-2
and the whole test plan are unaffected, and the choice touches a handful of lines
in one command.
