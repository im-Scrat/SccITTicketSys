## 16. F-5 classification

# B — STRONG EVIDENCE, CAUSATION NOT PROVEN

Unchanged from the prior report, now on far stronger experimental footing.

**Why not A.** Three reasons, each sufficient on its own:

1. **A1 passed at the highest peak CPU of all twelve runs (1052.73%).** If CPU
   saturation were straightforwardly causal, the most saturated run should not
   be the one that passed. Peak CPU is not the discriminator.
2. **Reducing `maxWorkers` changes more than CPU load** — worker scheduling,
   per-worker memory and GC pressure, and event-loop contention all move
   together. The experiment varied a compound, not an isolated cause.
3. **n = 3 per condition.** 2/3 versus 0/9 is a strong signal (Fisher exact
   ≈ 0.045) but is **not** conclusive at this sample size for an intermittent
   fault.

**Why not C.** The evidence is far beyond inconclusive: a clean monotonic
relationship across four conditions, a reproducible failure confined to one
condition, a second independent signal in the transform timings, and three
candidate mechanisms positively excluded.

**F-5 is not fixed, and is not claimed to be fixed.**

## 19. Is a remedy justified by the evidence?

**Evidence-based answer: a remedy is supported, but the choice is not mine and
nothing was applied.**

The diagnostic shows a concurrency limit eliminated the failures in every run
observed, at a measurable cost:

| Option | Observed result | Cost |
|---|---|---|
| `--maxWorkers=4` | 3/3 pass | +~4 s (≈ +25%) |
| `--maxWorkers=2` | 3/3 pass | +~14 s (≈ +90%) |
| `--no-file-parallelism` | 3/3 pass | +~40 s (≈ +270%) |

`--maxWorkers=4` gives the observed benefit at the smallest cost. **This is
recorded as evidence for a future owner decision only.** Per §12, no remedy was
applied: `maxWorkers` unchanged, `fileParallelism` unchanged, no timeout raised,
no test architecture altered, no dependency, Docker or Vite setting touched.

I note one caveat against over-reading this: since causation is not proven, a
concurrency cap may be **masking** the sensitivity rather than removing it. It
would make the gate green without establishing that nothing is wrong.

## 22. Exact limitations

1. **n = 3 per condition.** Adequate to show a clear signal; not adequate to bound the failure rate of an intermittent fault.
2. **Compound variable.** `--maxWorkers` moves scheduling, memory and CPU pressure together; no single cause was isolated.
3. **The dev server was a constant, not a control.** Per §6 it could not be stopped, so "no background load" was never tested.
4. **A1 is unexplained** — a pass at the highest peak CPU recorded. Left as an open contradiction rather than smoothed over.
5. **Single host.** All measurements are from one Docker Desktop for Windows machine with 12 CPUs. No cross-machine evidence exists.
6. **Sampling granularity.** `docker stats --no-stream` yields roughly one sample per 1.5–2 s; brief spikes between samples would be missed, so the peaks reported are lower bounds.
7. **No margin data at reduced concurrency**, since nothing failed there.
