## 1. Recovery classification — B (STRONG), and why not A

**Exact (A) recovery was proven for two of the three exports, and it
*contradicted* the third.**

Transcript line 1144 is an **`Edit` tool result carrying `originalFile`** — the
complete file immediately before that edit. Applying its own
`oldString` → `newString` therefore yields the exact file state at
**2026-09-05T12:39:01.551Z**, with no inference:

```
result: 8967 chars · 10 exports
EMAIL_LABEL PASSWORD_LABEL apiFetch apiJson apiLogin apiStatus goto settle signIn signOut
```

That state contains `apiLogin` and `apiJson` — **but not `json`.**

### 1.1 The contradiction

Tracing all three edits showed why:

| Edit | Time | Effect |
|---|---|---|
| `0c8043a1:939` | 12:19:29 | **adds** `apiLogin` and `json` |
| `0c8043a1:989` | 12:26:22 | unrelated; `json` still present |
| `0c8043a1:1144` | **12:39:01** | **replaces `json` with `apiJson`** — `oldString` contains `export function json`, `newString` contains `export async function apiJson` |

`json` was **deliberately removed** and `apiJson` put in its exact slot. The
export ordering confirms an in-place substitution:

```
12:26 state:  … apiFetch  apiLogin  json     apiStatus  signOut
12:39 state:  … apiFetch  apiLogin  apiJson  apiStatus  signOut
```

So the exact final `app.ts` should **not** export `json`. Yet
`notifications.spec.ts` imports it, and I was instructed not to change any spec.

### 1.2 Why all three were nevertheless restored

`notifications.spec.ts` was edited **four times after** that refactor — the last
at 2026-09-06T21:24 — and **no edit ever touched its import line or its `json`
usage** (verified across every edit payload). The 2026-09-08 sign-off recorded
44 E2E tests passing. A file importing a non-existent symbol cannot pass, so the
`app.ts` in force on 2026-09-08 must have exported all three.

The applied file is therefore a **composite**:

| Symbol | Source | Grade |
|---|---|---|
| `apiLogin` | exact reconstruction of the 12:39 state | **A** |
| `apiJson` | exact reconstruction of the 12:39 state | **A** |
| `json` | byte-exact body from the 12:19 `newString`, placed in the slot the 12:26 state shows it occupied | **A (symbol)** |
| **The combination** | inferred from the spec's requirements, not directly attested | **B** |

Each symbol is byte-exact from transcript evidence. The *combination* is not
directly attested in any single snapshot, so the whole is classified
**B — STRONG RECOVERY**, not A. Nothing was invented, improvised or written from
Playwright convention.

## 7. The 3 failures — classified

**None is an application defect. All three are harness / stale-spec artifacts.**

### 7.1 `notifications.spec.ts:265` and `:304` — harness artifact

```
Error: Expected JSON, got 200: {"data":[{"id":"0d57413f-…","type":"ticket_update", …
  at json (/app/e2e/fixtures/app.ts:168:11)
```

**The API returned HTTP 200 with valid JSON.** The failure is in the helper:
`apiFetch` truncates response bodies to 2,000 characters by design, and a
teacher's notification list exceeds that, so `JSON.parse` fails on a truncated
fragment.

**This is precisely the bug the 12:39 refactor fixed.** The recovered `apiJson`
doc comment states it verbatim:

> *"`apiFetch` truncates the body to 2000 characters on purpose … That truncation
> is fatal to a parser: a page of twenty notifications is comfortably past the
> limit … Parsing in the browser avoids the problem rather than raising the
> limit, which would only move it."*

So restoring `json` — which the on-disk spec demands — necessarily reintroduces
the defect that `apiJson` was written to eliminate. **This is positive proof that
`notifications.spec.ts` on disk is itself a stale, pre-refactor copy**: its true
final version must call `apiJson`.

Classification: **harness artifact caused by a stale spec.** Not an application
defect; the endpoint behaved correctly.

### 7.2 `auth.spec.ts:75` — stale-spec artifact

```
TimeoutError: locator.fill: Timeout 20000ms exceeded.
  waiting for getByLabel('Password', { exact: true })
```

The spec uses a literal `'Password'` with `exact: true`. The shared helper uses
a constant that exists for exactly this reason:

```ts
export const PASSWORD_LABEL = /^Password/      // prefix match
await page.getByLabel(PASSWORD_LABEL).fill(password)
```

Every other test that fills this field — including seven further `auth.spec.ts`
tests and all the sign-in flows — **passes**, because they route through
`signIn()` and its regex. Only this one test bypasses the constant with an exact
literal.

Ruled out: my formatting never touched this line (`git diff` shows no change to
any `Password` locator), and the field plainly works everywhere else.

Classification: **stale-spec artifact.** The `PASSWORD_LABEL` constant was
introduced because the exact literal stopped matching; this spec predates that
change. Not an application defect.
